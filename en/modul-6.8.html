6.8 Final Project — Small Company Server

Combine everything on one server: users, shared directory, web site, firewall, backup, timer, and a verified delivery report.

What will you learn in this module?

  • You plan the whole server first and take a VM snapshot before you change anything.
  • You build users alice, bob, carol, the groups staff and admins, and a shared directory /srv/company with setgid.
  • You publish a site with nginx, label it correctly (SELinux) or check AppArmor, and open ports 80/443 without locking yourself out of SSH.
  • You automate a backup with a script and a systemd timer.
  • You verify every step with a checklist and write a delivery report.

1. Plan and safety first

The target: a small company server called linux-lab. Three people work on it: alice (admin), bob and carol. Everything lives under /srv/company: shared (team files), admin (admins only), web (the site), backup and scripts.

Work in the VM, never on a production machine. This project creates users, changes permissions, SELinux labels, firewall rules and systemd units. Before you start, take a snapshot (module 0.2). If a step goes wrong you roll back in seconds.

The built-in terminal cannot run useradd, nginx, firewall-cmd or systemctl. So the simulator tasks rebuild the files of the project (permission tree, script, unit files, report) under ~/srv/company, while the VM tasks do the real thing in /srv/company.

Order of work: 1) plan + snapshot, 2) users and directories, 3) web, 4) firewall, 5) backup + timer, 6) verify + report. RHEL/Rocky and Debian/Ubuntu differ in only a few commands; both are shown.

cat /etc/os-release

What is it for?
Shows distribution name and version.
Where is it used?
Before you choose dnf or apt commands.
Why does it matter?
Tells you which variant of the guide applies.
cat /etc/os-release

What is it for?
Prints the SELinux mode: Enforcing, Permissive or Disabled.
Where is it used?
RHEL, Rocky, Alma, Fedora.
Why does it matter?
You must know the mode before testing the web label; keep it Enforcing.
getenforce

What is it for?
Shows which AppArmor profiles are loaded and in which mode.
Where is it used?
Debian and Ubuntu.
Why does it matter?
Ubuntu uses AppArmor instead of SELinux; here you only check it.
sudo aa-status

id

What is it for?
Shows user id and group memberships.
Where is it used?
When you check who may use the shared directory.
Why does it matter?

id student
💡 Tip

Keep a notes file while you work. Every command you run becomes a line in your delivery report later.

⚠️ Warning

Take a VM snapshot now and name it before-company-project. Do not run this project on a real server that others use.

2. Users, groups and the shared directory

Create the groups staff (alice, bob, carol) and admins (alice only). Use useradd -m -G for the users. Deleting users is not part of this project (userdel -r would remove home directories).

A shared directory needs two things. Setgid (chmod 2770) makes new files inherit the directory group staff, so bob can edit carol's files. Mode 770 keeps everybody else out. Optionally add a default ACL (setfacl -d -m g:staff:rwx) so new files are group-writable even with a strict umask.

Use least privilege: web is 755 (nginx must read it), scripts is 750, backup is 700. In the simulator you practise the same modes with chmod on ~/srv/company; a normal user cannot chgrp there, so the group part is VM only.

sudo useradd -m -s /bin/bash -G staff alice

What is it for?
Creates a user with home directory, shell and extra group.
Where is it used?
Once for each of alice, bob, carol.
Why does it matter?
Real accounts with their own home directories.
sudo useradd -m -s /bin/bash -G staff alice

sudo chgrp staff /srv/company/shared

What is it for?
Sets the owning group of the directory.
Where is it used?
On the shared and admin directories.
Why does it matter?
Group ownership is what setgid passes on to new files.
sudo chgrp staff /srv/company/shared

chmod 2770

What is it for?
Sets rwx for owner and group, nothing for others, plus the setgid bit.
Where is it used?
On the shared and admin directories.
Why does it matter?
New files inherit the group; outsiders get no access.
chmod 2770 ~/srv/company/shared

sudo setfacl -d -m g:staff:rwx

What is it for?
Sets a default ACL that new files in the directory inherit.
Where is it used?
On the shared directory (package acl).
Why does it matter?
Group stays writable even if a user has umask 077.
sudo setfacl -d -m g:staff:rwx /srv/company/shared

ls -ld

What is it for?
Shows the directory itself, not its content.
Where is it used?
To verify mode and group.
Why does it matter?
drwxrws--- means setgid is active (the s).
ls -ld ~/srv/company/shared
💡 Tip

A capital S in drwxr-S--- means setgid is set but the group has no execute bit; fix the mode.

⚠️ Warning

Never fix permission problems with chmod 777. Everybody could then change or delete the files.

3. Web site with nginx, SELinux and AppArmor

Install nginx and let it serve /srv/company/web. We add a server block named company.local in /etc/nginx/conf.d/company.conf (works on both families) and test with a Host: header, so the default site does not interfere.

RHEL/Rocky: SELinux labels every file. A new directory under /srv gets a generic label, so nginx gets 403 Forbidden although the Unix permissions are fine. The fix is the right label: semanage fcontext stores the rule, restorecon applies it. Do not use setenforce 0 as a shortcut; that switches protection off for the whole system.

Debian/Ubuntu: there is no label to set. AppArmor is active but nginx is normally not confined by a profile; you only check the status with aa-status. A 403 there is a normal permission problem (check the directory modes up to /srv).

sudo dnf install -y nginx

What is it for?
Installs nginx (RHEL, Rocky, Alma). On Ubuntu use sudo apt install -y nginx.
Where is it used?
First step of the web chapter.
Why does it matter?
Package manager handles files and dependencies.
sudo dnf install -y nginx

sudo semanage fcontext -a -t httpd_sys_content_t "/srv/company/web(/.*)?"

What is it for?
Stores a rule: files below web get the web-content label.
Where is it used?
RHEL family (package policycoreutils-python-utils).
Why does it matter?
The label survives a relabel; chcon does not.
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/company/web(/.*)?"

sudo restorecon -Rv /srv/company/web

What is it for?
Applies the stored label rule to existing files.
Where is it used?
Right after semanage fcontext.
Why does it matter?
Without it the rule exists but files keep the old label.
sudo restorecon -Rv /srv/company/web

ls -Zd /srv/company/web

What is it for?
Shows the SELinux label of the directory.
Where is it used?
To verify the label.
Why does it matter?
You want to see httpd_sys_content_t.
ls -Zd /srv/company/web

sudo nginx -t

What is it for?
Tests the nginx configuration without restarting.
Where is it used?
Before every start or reload.
Why does it matter?
A typo would otherwise take the site down.
sudo nginx -t
💡 Tip

To see why SELinux blocked something: sudo ausearch -m avc -ts recent. Read the log before you change anything.

⚠️ Warning

setenforce 0 is a diagnosis tool at best, never a fix. Label the files instead.

4. Firewall: open 80 and 443, keep SSH

RHEL/Rocky uses firewalld, Ubuntu uses ufw. Both can block you out of your own server when you are connected over SSH. Rules: keep SSH allowed, test with a runtime rule first, make it permanent only after the test.

firewalld: rules without --permanent vanish at reload or reboot; with --timeout=300 they remove themselves. ufw: rules are saved at once, so allow SSH before ufw enable.

Always keep a second SSH session open (or the VM console) while you change the firewall. If the new rules lock you out, the open session or the console still works.

sudo firewall-cmd --list-services

What is it for?
Lists the services allowed in the active zone.
Where is it used?
Before and after every change.
Why does it matter?
Confirms that ssh is still there.
sudo firewall-cmd --list-services

sudo firewall-cmd --permanent --add-service={http,https}

What is it for?
Stores permanent rules for ports 80 and 443.
Where is it used?
After the runtime test worked.
Why does it matter?
Survives reload and reboot; apply with --reload.
sudo firewall-cmd --permanent --add-service={http,https}

sudo ufw allow OpenSSH

What is it for?
Allows SSH (port 22) in ufw.
Where is it used?
Ubuntu, always before ufw enable.
Why does it matter?
Prevents the lockout when the firewall is switched on.
sudo ufw allow OpenSSH

sudo ufw allow 80/tcp

What is it for?
Allows HTTP; repeat with 443/tcp for HTTPS.
Where is it used?
Ubuntu web server.
Why does it matter?
Opens only the ports the site needs.
sudo ufw allow 80/tcp

ss -tulpn

What is it for?
Lists listening TCP/UDP ports with the process.
Where is it used?
To see what the server really offers.
Why does it matter?
Every unexpected port is a finding for your report.
ss -tulpn
💡 Tip

Practise reading ss output in the simulator: the audit files in your home directory contain a sample listing you can analyse with grep and cut.

⛔ Danger

Never remove the ssh service or deny port 22 while connected over SSH. Check --list-services or ufw status for ssh before firewall-cmd --reload or ufw enable. Use the VM console if you are locked out, and restore the snapshot if needed.

5. Backup script and systemd timer

The backup is a short script (modules 6.5/6.6) that writes a dated tar.gz archive of shared, web and admin to /srv/company/backup and deletes archives older than 7 days. A second disk or remote copy is better in real life; a local folder is enough for the project.

systemd runs the script: a .service of Type=oneshot describes what to run, a .timer describes when (OnCalendar=, Persistent=true). Enable the timer, not the service. After creating or changing unit files run systemctl daemon-reload.

On RHEL/Rocky a script in /srv/company/scripts has a generic label and systemd may refuse to run it (status 203/EXEC). Give it the label bin_t with semanage fcontext and restorecon, like you did for the web directory.

tar -czf

What is it for?
Creates a compressed archive.
Where is it used?
In the backup script.
Why does it matter?
One dated file per backup is easy to store and restore.
tar -czf /srv/company/backup/company-test.tar.gz -C /srv/company shared web admin

systemctl daemon-reload

What is it for?
Makes systemd read new or changed unit files.
Where is it used?
After writing the service and timer.
Why does it matter?
Otherwise systemd does not know the new units.
sudo systemctl daemon-reload

systemctl enable --now company-backup.timer

What is it for?
Enables the timer at boot and starts it now.
Where is it used?
Once, after daemon-reload.
Why does it matter?
The backup then runs every night without you.
sudo systemctl enable --now company-backup.timer

systemctl list-timers

What is it for?
Shows timers with next and last run.
Where is it used?
To verify the schedule.
Why does it matter?
You see when the next backup will run.
systemctl list-timers company-backup.timer --no-pager

chmod 755 backup.sh

What is it for?
Makes the script executable.
Where is it used?
Whenever you create a script.
Why does it matter?
Without the x bit the service cannot start it.
chmod 755 ~/srv/company/scripts/backup.sh
💡 Tip

Run the service once by hand with sudo systemctl start company-backup.service and look at ls -l /srv/company/backup before you wait for the timer.

⛔ Danger

find ... -delete cannot be undone. Test the line with -print instead of -delete first and run it only on /srv/company/backup.

6. Verification checklist and delivery report

A server is only finished when you have proof. Go through the checklist: users and groups, setgid shared directory, site answers with 200, SELinux label or AppArmor status, firewall has ssh/80/443, timer is enabled, a backup file exists, backup directory is 700.

A small script prints OK: or FAIL: per check, so the result is easy to read and to paste. The delivery report /srv/company/REPORT.txt contains host, date, the verification output and the listening ports. This is what you hand over.

If a line says FAIL, go back to that chapter and fix it. Do not edit the report by hand to hide a failure.

getent group staff

What is it for?
Shows the group entry with members.
Where is it used?
To prove group membership.
Why does it matter?
Reads from the real user database.
getent group staff

stat -c '%A %U:%G %n' /srv/company/shared

What is it for?
Prints permissions, owner and group in one line.
Where is it used?
In checks and in the report.
Why does it matter?
Short proof that the mode is drwxrws---.
stat -c '%A %U:%G %n' /srv/company/shared

curl -I

What is it for?
Fetches only the HTTP headers.
Where is it used?
To test the web site locally.
Why does it matter?
200 OK shows nginx answered the local request and content permissions/labels allow access; check firewall rules separately and, if possible, test from another machine.
curl -I -H 'Host: company.local' http://localhost

wc -l

What is it for?
Counts lines.
Where is it used?
To check that the report is not empty.
Why does it matter?
A report needs real content.
wc -l ~/srv/company/REPORT.txt
💡 Tip

Run the checklist after a reboot, too. A service that works only until the next reboot is not finished.

Do it on your own VM

Do the real project in your VM, in this order. First take a snapshot: if anything fails, you go back. Paste the output when a task asks for it. Commands marked for RHEL or Ubuntu: run only your variant.

Web site with the right label

Install nginx, add the server block and the page, test, fix the label (RHEL) or check AppArmor (Ubuntu) and paste the last curl output.

Keep a second SSH session or the console open. Allow web ports without losing SSH, then paste the rule list.

# RHEL / Rocky / Alma (firewalld):
sudo firewall-cmd --list-services
sudo firewall-cmd --add-service={http,https} --timeout=300
curl -sI http://localhost | head -n 1

sudo firewall-cmd --list-services

cockpit dhcpv6-client http https ssh

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status

Status: active
OpenSSH                    ALLOW       Anywhere
80/tcp                     ALLOW       Anywhere

Backup script and timer

Create the backup script and the systemd units, enable the timer, run one backup by hand and paste the timer list.

sudo tee /srv/company/scripts/backup.sh >/dev/null <<'EOF'
#!/bin/bash
set -euo pipefail
DEST=/srv/company/backup
tar -czf "$DEST/company-$(date +%F_%H%M).tar.gz" -C /srv/company shared web admin
find "$DEST" -name 'company-*.tar.gz' -mtime +7 -delete
EOF
sudo chmod 750 /srv/company/scripts/backup.sh

sudo tee /etc/systemd/system/company-backup.service >/dev/null <<'EOF'
[Unit]
Description=Company backup

[Service]
Type=oneshot
ExecStart=/srv/company/scripts/backup.sh
EOF
sudo tee /etc/systemd/system/company-backup.timer >/dev/null <<'EOF'
[Unit]
Description=Daily company backup

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
EOF

# RHEL / Rocky / Alma only (script label):
sudo semanage fcontext -a -t bin_t "/srv/company/scripts(/.*)?"
sudo restorecon -Rv /srv/company/scripts
# both:
sudo systemd-analyze verify /etc/systemd/system/company-backup.service
sudo systemctl daemon-reload
sudo systemctl enable --now company-backup.timer
sudo systemctl start company-backup.service
sudo ls -l /srv/company/backup
systemctl list-timers company-backup.timer --no-pager

Expected output example

-rw-r--r-- 1 root root 2048 ... company-2026-11-12_0215.tar.gz
NEXT                        LEFT   LAST PASSED UNIT                 ACTIVATES
Fri 2026-11-13 02:00:00 CET 23h    -    -      company-backup.timer company-backup.service
My output looks different
  • status=203/EXEC in systemctl status company-backup.service: on RHEL set the bin_t label (first lines of this block) and check the x bit.
  • Do not test the find ... -delete line on other directories; if in doubt replace -delete with -print.
  • If the timer is not listed, you probably forgot daemon-reload.

Verification checklist and delivery report

Write the checklist script, run it as root and build the delivery report. All lines must say OK. Paste the verify output.

sudo tee /srv/company/scripts/verify.sh >/dev/null <<'EOF'
#!/bin/bash
set -o pipefail
chk() { local label=$1; shift; if "$@" >/dev/null 2>&1; then echo "OK: $label"; else echo "FAIL: $label"; fi; }
staff_ok() { id -nG alice | grep -qw staff && id -nG bob | grep -qw staff && id -nG carol | grep -qw staff; }
site_ok() { curl -fsS -H 'Host: company.local' http://localhost | grep -q Company; }
selinux_ok() { if ! command -v getenforce >/dev/null 2>&1 || [ "$(getenforce)" = Disabled ]; then return 0; fi; ls -Zd /srv/company/web | grep -q httpd_sys_content_t; }
firewall_ok() {
  if command -v firewall-cmd >/dev/null 2>&1 && firewall-cmd --state >/dev/null 2>&1; then
    local services
    services=$(firewall-cmd --list-services) || return 1
    for service in ssh http https; do [[ " $services " == *" $service "* ]] || return 1; done
  elif command -v ufw >/dev/null 2>&1; then
    local status
    status=$(ufw status) || return 1
    grep -q '^Status: active' <<<"$status" && grep -Eq '^OpenSSH[[:space:]]+ALLOW' <<<"$status" && grep -Eq '^80/tcp[[:space:]]+ALLOW' <<<"$status" && grep -Eq '^443/tcp[[:space:]]+ALLOW' <<<"$status"
  else
    return 1
  fi
}
backup_ok() { compgen -G '/srv/company/backup/company-*.tar.gz' >/dev/null; }
backup_mode_ok() { [[ $(stat -c %a /srv/company/backup) == 700 ]]; }
chk "alice bob carol are in staff" staff_ok
chk "shared has setgid" test -g /srv/company/shared
chk "site answers with Small Company" site_ok
chk "nginx enabled" systemctl is-enabled --quiet nginx
chk "web label (SELinux) or no SELinux" selinux_ok
chk "firewall allows SSH, HTTP and HTTPS" firewall_ok
chk "timer enabled" systemctl is-enabled --quiet company-backup.timer
chk "backup archive exists" backup_ok
chk "backup dir is 700" backup_mode_ok
EOF
sudo bash /srv/company/scripts/verify.sh

Expected output example

OK: alice bob carol are in staff
OK: shared has setgid
OK: site answers with Small Company
OK: nginx enabled
OK: web label (SELinux) or no SELinux
OK: firewall allows SSH, HTTP and HTTPS
OK: timer enabled
OK: backup archive exists
OK: backup dir is 700
{ echo "Company server delivery report"; echo "Host: $(hostname)"; echo "Date: $(date)"; echo "--- verification ---"; sudo bash /srv/company/scripts/verify.sh; echo "--- listening ports ---"; ss -tulpn; } | sudo tee /srv/company/REPORT.txt
wc -l /srv/company/REPORT.txt
My output looks different
  • Any FAIL: line: go back to the matching chapter, fix it and run the script again.
  • The [ ... = 700 ] line needs the backslash before $(stat exactly as written, otherwise the shell expands it too early.
  • Finally reboot and run the verify script again: everything must still be OK.

Self-test

On Rocky Linux nginx returns 403 for files in /srv/company/web although the mode is 755. What is the most likely cause?

A closed port gives a timeout, not a 403. A generic label under /srv blocks nginx; fix it with semanage fcontext and restorecon, not with setenforce 0.

You are connected over SSH to an Ubuntu server. What is the safe way to switch on ufw?

ufw rules are active at once. Without an allowed SSH rule, enabling the firewall cuts your session.

Why does the shared directory get mode 2770 (setgid)?

The setgid bit on a directory passes its group to new files. 770 keeps others out.

You created company-backup.service and company-backup.timer. What must you do so the nightly backup runs?

systemd must re-read unit files (daemon-reload), and the timer unit has to be enabled and started; the service is started by the timer.

Summary

  • Plan first, take a VM snapshot, work only in the test VM.
  • Shared directory: group staff, mode 2770 (setgid), least privilege elsewhere: web 755, scripts 750, backup 700.
  • nginx on RHEL needs the label httpd_sys_content_t (semanage fcontext + restorecon); on Ubuntu you check AppArmor.
  • Firewall: keep ssh, test with runtime rules or --timeout, keep a second session; ufw: allow OpenSSH before enable.
  • Backup: script + service (oneshot) + timer; daemon-reload, enable --now the timer; on RHEL label the script bin_t.
  • Finish with a checklist (OK/FAIL) and a delivery report file as proof.

Key terms

snapshot
A saved state of the VM you can return to if a step goes wrong.
setgid (on a directory)
New files inherit the directory's group instead of the creator's primary group.
default ACL
An access rule on a directory that new files inherit.
SELinux label
A security context (such as httpd_sys_content_t) on files; decides what a process may access.
semanage fcontext
Stores a permanent file-label rule; restorecon applies it.
AppArmor
Path-based security system of Debian/Ubuntu; checked with aa-status.
firewalld / ufw
Firewall front ends of RHEL-family and Ubuntu systems.
runtime vs permanent
Runtime rules vanish at reload or reboot; permanent rules are stored.
systemd timer
A unit that starts a service on a schedule (OnCalendar=).
delivery report
The file that documents the finished server and the verification results.
