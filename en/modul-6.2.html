6.2 SELinux — Labels, Booleans, AVC

SELinux gives every file and process a label. When a service fails, the culprit is often a wrong label; learn to find the cause instead of switching SELinux off.

What will you learn in this module?

  • You read the SELinux modes (enforcing, permissive, disabled) and explain why disabling it permanently is a bad idea.
  • You read file labels with ls -Z and fix them persistently with chcon, semanage fcontext and restorecon.
  • You manage booleans with getsebool and setsebool -P and resolve AVC denials with ausearch and sealert.
  • You read the Debian/Ubuntu equivalent, AppArmor, with aa-status and tell complain from enforce mode.

What SELinux is, modes

Classic permissions (rwx) look at the owner. SELinux is an extra layer: every process and file has a label (context) and the policy says which label may do what to which. A label looks like user:role:type:level; the type field matters most in daily work (e.g. httpd_t, httpd_sys_content_t).

There are three modes: enforcing (violations are blocked and logged), permissive (only logged, not blocked; for debugging) and disabled (off). RHEL/Rocky/Alma default to enforcing. Debian/Ubuntu use AppArmor instead.

getenforce

What is it for?
Prints the running SELinux mode.
Where is it used?
First check when a service misbehaves.
Why does it matter?
Narrows down whether SELinux is involved.
getenforce

sestatus

What is it for?
Shows mode, policy type and the mode in the config file.
Where is it used?
When you need a general summary.
Why does it matter?
You see the difference between running and persistent mode.
sestatus

setenforce 0

What is it for?
Switches to permissive for now (resets on reboot).
Where is it used?
To test temporarily whether SELinux is the cause.
Why does it matter?
If the problem vanishes in permissive, SELinux is the culprit; turn it back on with setenforce 1.
setenforce 0

/etc/selinux/config

What is it for?
File holding the persistent mode (SELINUX=enforcing).
Where is it used?
When setting the mode persistently across reboots.
Why does it matter?
If you write disabled, labels go stale and re-enabling needs a long relabel.
cat /etc/selinux/config
💡 Tip

Troubleshooting order: getenforce, test with setenforce 0, read the log, fix, then setenforce 1.

⚠️ Warning

Do not make setenforce 0 or SELINUX=disabled a habit. Use permissive for a temporary test and the right label or boolean for a lasting fix.

Labels: ls -Z, chcon, semanage, restorecon

ls -Z shows a file's label. The web server (httpd_t) can only read web-typed files such as httpd_sys_content_t. If you mv a file from your home directory, it keeps the old user_home_t label and access is denied.

chcon changes the label immediately but not persistently: restorecon or a relabel wipes it. The lasting way has two steps: first write the rule into the policy with semanage fcontext, then apply it with restorecon.

ls -Z

What is it for?
Lists the SELinux label of files.
Where is it used?
When looking at the file type after a denial.
Why does it matter?
You compare the expected type with the actual type.
ls -Z /var/www/html

chcon -t

What is it for?
Changes a file's type temporarily.
Where is it used?
For quick experiments.
Why does it matter?
Proves the label fixes the problem; but it is not persistent.
chcon -t httpd_sys_content_t /srv/web/index.html

semanage fcontext -a

What is it for?
Adds a persistent labeling rule for a path pattern.
Where is it used?
When using a non-standard directory (e.g. /srv/web).
Why does it matter?
The rule stays in the policy and survives a relabel.
semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?"

restorecon -Rv

What is it for?
Restores labels to what the policy says (-R recursive, -v verbose).
Where is it used?
After semanage fcontext or after moving files.
Why does it matter?
Applies the rule to the real files.
restorecon -Rv /srv/web
💡 Tip

A file copied with cp takes the label of the target directory; a file moved with mv keeps its old label. Run restorecon after moving.

⚠️ Warning

Do not run restorecon -R / or other huge paths; it takes long and can surprise you. Look first with -n (dry run).

Booleans

Switches that turn common behaviors on and off without rewriting the policy are called booleans: httpd_can_network_connect lets the web server connect to the network, httpd_enable_homedirs opens home directories.

setsebool alone changes the running state and is lost on reboot. Add -P to make it persistent. Enable only what you need; every boolean is a hole in the wall.

getsebool -a

What is it for?
Lists all booleans and their states.
Where is it used?
When searching for the right switch (| grep httpd).
Why does it matter?
The right boolean saves you from fiddling with labels.
getsebool -a | grep httpd

getsebool

What is it for?
Shows the state of one boolean.
Where is it used?
To verify before and after a change.
Why does it matter?
You see that the change took effect.
getsebool httpd_can_network_connect

setsebool -P

What is it for?
Turns a boolean on/off persistently.
Where is it used?
When a service must reach the network or home directories.
Why does it matter?
Without -P the setting is lost on reboot.
setsebool -P httpd_can_network_connect on

semanage boolean -l

What is it for?
Lists booleans with descriptions and persistent/running state.
Where is it used?
To learn what a boolean does.
Why does it matter?
The description keeps you from enabling the wrong switch.
semanage boolean -l | grep httpd_can_network
💡 Tip

A new port may need more than a boolean: add it to the service type with semanage port -a -t http_port_t -p tcp 8888.

⚠️ Warning

Pick the narrowest boolean; broad switches like httpd_unified grant a lot.

AVC denials: ausearch, sealert, audit.log

When SELinux blocks something, an AVC (Access Vector Cache) record lands in /var/log/audit/audit.log. It has the source label (scontext), target label (tcontext), class (tclass) and the blocked permission ({ read }). If permissive=1, the access was not blocked, only logged.

Reading order: who (comm, scontext), what (name, tcontext), what it tried to do ({ ... }). Then fix: wrong label means restorecon, a behavior permission means a boolean, a new port means semanage port. Generating a module with audit2allow is the last resort.

ausearch -m AVC -ts recent

What is it for?
Searches the audit log for recent AVC records.
Where is it used?
Right after a denial.
Why does it matter?
Finds the relevant records without wading through the raw log.
ausearch -m AVC -ts recent

sealert -a

What is it for?
Analyzes the log and suggests a fix (setroubleshoot package).
Where is it used?
When you want a cause and fix summary.
Why does it matter?
Often suggests the right restorecon or setsebool command.
sealert -a /var/log/audit/audit.log

grep AVC

What is it for?
Filters AVC lines in the audit log.
Where is it used?
Without ausearch or when inspecting a log copy.
Why does it matter?
The simplest method that works everywhere.
grep AVC lab/audit.log

grep -c denied

What is it for?
Counts denied records.
Where is it used?
To measure the size of the problem.
Why does it matter?
Tells you whether it is one repeated denial or many sources.
grep -c denied lab/audit.log
💡 Tip

Without auditd, records may appear in journalctl -t setroubleshoot or dmesg.

⚠️ Warning

Do not load a module with audit2allow -M for every AVC. Try the label and the boolean first; a module can grant needlessly broad access.

Debian/Ubuntu: AppArmor

Ubuntu and Debian use AppArmor instead of SELinux. Instead of labels, each program has a path-based profile. A profile can be in enforce mode (rules applied) or complain mode (only logs, like permissive in SELinux).

The logic is the same: read the status, put a profile in complain if needed, see in the log what was blocked, fix the profile and set enforce again. Denials show up in /var/log/syslog or journalctl as apparmor="DENIED".

aa-status

What is it for?
Lists loaded profiles and their modes (enforce/complain).
Where is it used?
For a status check.
Why does it matter?
You see which programs are confined.
sudo aa-status

aa-complain

What is it for?
Puts a profile in complain mode.
Where is it used?
When a profile blocks something, for a temporary test.
Why does it matter?
Logs without blocking; you see what is needed.
sudo aa-complain /usr/sbin/nginx

aa-enforce

What is it for?
Returns a profile to enforce mode.
Where is it used?
After the test is done.
Why does it matter?
Protection is active again.
sudo aa-enforce /usr/sbin/nginx

grep DENIED

What is it for?
Filters AppArmor denial lines in the log.
Where is it used?
When inspecting a denial.
Why does it matter?
Shows which path was blocked.
sudo grep DENIED /var/log/syslog
💡 Tip

Rocky vs Ubuntu: getenforce is like aa-status, setenforce 0 is like aa-complain, setenforce 1 is like aa-enforce.

⛔ Danger

Turning a profile off with aa-disable or setting SELinux permanently disabled removes a security layer. Find the cause with complain/permissive instead.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Do this part on a Rocky/Alma VM (SELinux ships there). On Ubuntu go to v06. Before anything else take a VM snapshot (module 0.2). Work in a fresh lab, not on a live server.

Read the mode

Find the running and persistent SELinux mode. Do not change the mode in this task.

getenforce
sestatus | head -5
grep ^SELINUX= /etc/selinux/config

Expected output example

Enforcing
My output looks different
  • If you get command not found, you are on Ubuntu; go to v06.
  • If it says Disabled, SELinux is off in the VM; use a Rocky/Alma image.

See the labels

Read file and process labels. Compare the web content directory and your home directory.

ls -Zd /etc /home/student /var/www
ls -Z ~/
ps -eZ | head -5

Expected output example

unconfined_u:object_r:user_home_dir_t:s0 /home/student
My output looks different
  • If /var/www is missing, httpd is not installed; install with sudo dnf install -y httpd and retry.
  • A different :s0 ending (MLS) is normal.

Persistent label rule

Define and apply a persistent label for a non-standard directory. Make sure you took a snapshot first; work only in this test directory.

sudo mkdir -p /srv/web
echo hello | sudo tee /srv/web/index.html
ls -Zd /srv/web/index.html
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?"
sudo restorecon -Rv /srv/web
ls -Zd /srv/web/index.html

Expected output example

Relabeled /srv/web/index.html from ...:var_t:s0 to ...:httpd_sys_content_t:s0
My output looks different
  • If semanage: command not found, run sudo dnf install -y policycoreutils-python-utils.
  • If the rule already exists, use -m instead of -a.

Change a boolean

Read a boolean, turn it on persistently and verify. Restore the old value at the end.

getsebool httpd_can_network_connect
sudo setsebool -P httpd_can_network_connect on
getsebool httpd_can_network_connect
sudo setsebool -P httpd_can_network_connect off

Expected output example

httpd_can_network_connect --> on
My output looks different
  • -P can be slow (policy is rebuilt); wait a minute.
  • If the boolean is not found, search with getsebool -a | grep httpd.

Find an AVC record

Search the audit log for denials. If there are none, that is fine; breaking a label on purpose to produce one is optional.

sudo ausearch -m AVC -ts recent
sudo grep -c AVC /var/log/audit/audit.log
sudo sealert -a /var/log/audit/audit.log | head -20

Expected output example

type=AVC msg=audit(...): avc:  denied  { read } ...
My output looks different
  • <no matches> is normal on a clean system.
  • If sealert is missing, run sudo dnf install -y setroubleshoot-server.

AppArmor (Ubuntu)

On an Ubuntu/Debian VM read the AppArmor status. Do not change profile modes (optional: aa-complain then aa-enforce).

sudo aa-status | head -15
sudo apparmor_status | head -3

Expected output example

apparmor module is loaded.
12 profiles are loaded.
My output looks different
  • If aa-status: command not found, run sudo apt install -y apparmor-utils.
  • Rocky has no AppArmor; v01-v05 are your tasks.

Self-test

A service fails because of SELinux. What is the best first diagnostic step?

First determine the mode and whether SELinux is the cause using temporary permissive, then find the reason in the AVC log. Disabling permanently removes the security layer.

You want the label of /srv/web to survive a relabel. Which is the right way?

chcon is not persistent. semanage fcontext writes the rule into the policy and restorecon applies it to the files.

You ran setsebool httpd_can_network_connect on and after a reboot it was gone. Why?

-P makes the setting persistent. Without it the change only applies to the running system.

On Ubuntu, how do you make a profile only log for now?

In AppArmor, aa-complain makes a profile only log, like permissive in SELinux; aa-enforce brings it back.

Summary

  • SELinux works with labels; the main field is the type (httpd_t, httpd_sys_content_t).
  • Modes: enforcing, permissive, disabled. Use setenforce 0 for tests, never disable permanently.
  • Labels: read with ls -Z, fix persistently with semanage fcontext + restorecon; chcon is not persistent.
  • Booleans: getsebool, persistent with setsebool -P; for a new port use semanage port.
  • AVC: ausearch -m AVC, sealert -a, audit.log; read who, what, what it tried to do.
  • On Ubuntu, AppArmor: aa-status, aa-complain, aa-enforce.

Key terms

SELinux
Label-based mandatory access control (MAC); an extra layer on top of classic permissions.
Context (label)
Security label shaped user:role:type:level; the type is the key field.
Type
The label field the policy writes rules for, e.g. httpd_sys_content_t.
Enforcing
Mode that blocks and logs violations.
Permissive
Debug mode that only logs violations without blocking.
Boolean
Policy switch for a common behavior; persistent with -P.
AVC
Access Vector Cache; the audit log record of an SELinux denial.
restorecon
Command that restores a file label to what the policy rule says.
AppArmor
Path-based profile system on Debian/Ubuntu; has enforce and complain modes.
