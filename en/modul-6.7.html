6.7 systemd Timers — The Modern Alternative to Cron

Schedule the work; the system runs it for you. You will write a service and a timer, verify the time expression, watch the run with journalctl and compare it with cron.

What will you learn in this module?

  • You write a .service file (Type=oneshot, ExecStart) and a .timer file (OnCalendar, Persistent=true).
  • You verify a time expression with systemd-analyze calendar before it ever runs.
  • You install and monitor a timer with daemon-reload, enable --now, list-timers and journalctl -u.
  • You read a cron line (30 2 * * *) and write the equivalent timer.
  • You know user timers (systemctl --user) and how to decide between cron and a timer.

Why timers? Comparison with cron

Running a script by hand is easy; real automation means running it at the right time. The classic way is cron: five time fields and a command on one line. The modern way is a systemd timer: two files, one saying what runs (backup.service), the other when it runs (backup.timer).

A cron line: 30 2 * * * /home/student/bin/backup.sh = every day at 02:30. Fields: minute, hour, day of month, month, day of week. The timer's advantages: output goes to the journal (journalctl -u), Persistent=true catches up a missed run at boot, RandomizedDelaySec spreads load, and systemctl list-timers shows the next run.

In this module you write the files in the simulator and check their content; systemctl and journalctl only work on a real VM. Cron's advantage is simplicity: one line, available everywhere.

crontab -e

What is it for?
Opens your own cron table in an editor.
Where is it used?
For simple one-line scheduled jobs.
Why does it matter?
The reference point: you recognise the old job before moving it to a timer.
crontab -e

crontab -l

What is it for?
Lists the current cron lines.
Where is it used?
When taking inventory of jobs to migrate.
Why does it matter?
You see which jobs to convert to timers.
crontab -l

printf (cron line)

What is it for?
Writes a cron line to a file: minute hour day month weekday command.
Where is it used?
To practise cron syntax and keep it in a file.
Why does it matter?
You get used to the right field order.
printf '30 2 * * * /home/student/bin/backup.sh\n' > backup.cron

systemctl list-timers

What is it for?
Lists active timers with their next and last run times.
Where is it used?
When verifying a timer is really scheduled.
Why does it matter?
You catch a silently idle timer immediately.
systemctl list-timers --all
💡 Tip

For a simple one-off user job, cron is enough. Choose a timer when you want logs, dependencies, catch-up and monitoring.

The service unit: what runs?

The service file defines the command. For scheduled jobs use Type=oneshot: the command runs and finishes. ExecStart requires an absolute path; write /usr/local/bin/backup.sh, not backup.sh.

System units go to /etc/systemd/system/ (root needed). You cannot write there in the simulator; use the ~/units/ folder instead, the content to copy is identical. Make the script executable first: chmod +x.

Note: a .service does not need an [Install] section; scheduling belongs to the timer. To test by hand, sudo systemctl start backup.service is enough.

printf > backup.service

What is it for?
Writes the service unit line by line.
Where is it used?
In ~/units/ in the sim, under /etc/systemd/system/ on the VM.
Why does it matter?
You create the file reproducibly without opening an editor.
printf '[Unit]\nDescription=Nightly backup\n\n[Service]\nType=oneshot\nExecStart=/home/student/bin/backup.sh\n' > backup.service

cat

What is it for?
Shows the content of the file you wrote.
Where is it used?
After every write.
Why does it matter?
You spot typos (Type=oneshot, path) before starting.
cat backup.service

chmod +x

What is it for?
Gives the script execute permission.
Where is it used?
For every script called by ExecStart.
Why does it matter?
Without it the service fails with 203/EXEC.
chmod +x backup.sh

systemd-analyze verify

What is it for?
Checks the unit file's syntax and paths.
Where is it used?
Before daemon-reload.
Why does it matter?
Catches a wrong path or typo without running anything.
systemd-analyze verify /etc/systemd/system/backup.service
💡 Tip

Run the unit once by hand with sudo systemctl start backup.service; if it works, scheduling it is safe.

⚠️ Warning

On RHEL/Rocky (SELinux) a service may be unable to run a script under /home (203/EXEC, Permission denied). Put the script in /usr/local/bin; on Debian/Ubuntu (AppArmor) this is rarer, but the same path is recommended.

The timer unit: when does it run?

A timer file contains the time in [Timer] and the line WantedBy=timers.target in [Install]. The name matches the service: backup.timer → backup.service.

OnCalendar= is calendar time: *-*-* 02:30:00 every day at 02:30, Mon *-*-* 08:00:00 every Monday at 08:00; hourly, daily, weekly are shortcuts. OnBootSec= waits after boot, OnUnitActiveSec= after the last run.

Persistent=true: a run missed while the machine was off happens right at the next boot. RandomizedDelaySec= delays the start randomly, so many machines do not hit a shared resource at once.

OnCalendar=

What is it for?
Defines calendar-based time.
Where is it used?
For jobs at fixed times such as nightly or weekly.
Why does it matter?
It is the readable counterpart of cron's five fields.
printf '[Timer]\nOnCalendar=*-*-* 02:30:00\n' | cat

OnBootSec= / OnUnitActiveSec=

What is it for?
Waits a relative time after boot or after the last run.
Where is it used?
For jobs like "10 min after boot, then every hour".
Why does it matter?
Solves interval-based jobs that have no calendar.
printf '[Timer]\nOnBootSec=10min\nOnUnitActiveSec=1h\n' | cat

Persistent=true

What is it for?
Catches up a missed run at the next boot.
Where is it used?
On laptops, VMs or machines switched off at night.
Why does it matter?
Gives anacron-like safety, which cron lacks.
printf '[Timer]\nOnCalendar=daily\nPersistent=true\n' | cat

RandomizedDelaySec=

What is it for?
Adds a random delay to the start.
Where is it used?
On many servers running at the same time.
Why does it matter?
Prevents sudden load spikes on a shared repository or network.
printf '[Timer]\nOnCalendar=daily\nRandomizedDelaySec=5min\n' | cat

systemd-analyze calendar

What is it for?
Interprets a time expression and shows the next elapse.
Where is it used?
Before and after writing a timer.
Why does it matter?
A wrong expression silently never runs; here you see it at once.
systemd-analyze calendar "Mon *-*-* 08:00:00"
💡 Tip

Lists like Mon,Fri *-*-* 08:00 and *-*-* *:00/15:00 (every 15 min) work; test them all with systemd-analyze calendar first.

Install, start, monitor

The order is fixed: write the files → systemd-analyze verify and calendar → sudo systemctl daemon-reload → start the service by hand and check journalctl → enable --now the timer → verify with list-timers.

enable --now applies to the timer (backup.timer), not the service. If you forget daemon-reload after a new or changed file, systemd keeps using the old state.

Read the output with journalctl -u backup.service; -f follows live, --since today filters the day. A failed run shows a Failed with result line.

sudo systemctl daemon-reload

What is it for?
Makes systemd re-read the unit files.
Where is it used?
After every new or changed .service and .timer.
Why does it matter?
Without it systemd sees an old file or none at all.
sudo systemctl daemon-reload

sudo systemctl start backup.service

What is it for?
Runs the service once, right now.
Where is it used?
To test the job itself before enabling the timer.
Why does it matter?
You find errors without waiting for the timer.
sudo systemctl start backup.service

sudo systemctl enable --now backup.timer

What is it for?
Enables the timer at boot and starts it immediately.
Where is it used?
For every permanent timer.
Why does it matter?
It also runs after a reboot.
sudo systemctl enable --now backup.timer

systemctl list-timers

What is it for?
Shows the next and last runs.
Where is it used?
After installing and when troubleshooting.
Why does it matter?
The NEXT column proves the timer is really scheduled.
systemctl list-timers backup.timer

journalctl -u

What is it for?
Shows the log entries of a unit.
Where is it used?
When reading successful and failed runs.
Why does it matter?
One searchable record instead of cron's mailbox.
journalctl -u backup.service --since today
⚠️ Warning

A service running as root can do great harm with a script that deletes or moves files. Dry-run the script with echo first, verify the path, then schedule it. A wrong OnCalendar gives no error; it simply never runs.

⛔ Danger

Over SSH never stop or disable sshd or network services with systemctl; you lock yourself out. Experiment only with your own units and take a VM snapshot before important changes (Module 0.2).

User timers and the migration decision

You can schedule without root: user units live in ~/.config/systemd/user/ and are managed with systemctl --user (no sudo). They stop when you log out; to keep them running use loginctl enable-linger student.

Decision: one-line job, output irrelevant → cron. Need logs, dependencies (run when the network is up), catch-up (Persistent), random delay or resource limits → timer. Both can coexist; when migrating, comment out the old cron line, verify the new timer, then delete.

On Debian/Ubuntu packages often ship timers instead of cron (apt-daily.timer); on RHEL/Rocky something like dnf-makecache.timer. systemctl list-timers --all is full of ready examples.

mkdir -p ~/.config/systemd/user

What is it for?
Creates the user units folder.
Where is it used?
Before your first user timer.
Why does it matter?
systemd looks for user units here.
mkdir -p ~/.config/systemd/user

systemctl --user daemon-reload

What is it for?
Makes systemd re-read user units.
Where is it used?
After writing the user files.
Why does it matter?
You follow the same flow without sudo.
systemctl --user daemon-reload

systemctl --user enable --now notes.timer

What is it for?
Enables and starts a user timer.
Where is it used?
For personal jobs in your own home.
Why does it matter?
No root needed, so the risk is small.
systemctl --user enable --now notes.timer

loginctl enable-linger

What is it for?
Keeps user units running while you are logged out.
Where is it used?
On a server where a user timer must continue in the background.
Why does it matter?
Otherwise the timer stops when you log out.
sudo loginctl enable-linger student
💡 Tip

A user timer is the safest place to experiment: if you make a mistake only your own account is affected, not the system.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

On your VM (Ubuntu or Rocky/Alma) go through these in order. Take a snapshot first (Module 0.2). You write units under /etc/systemd/system/; only touch your own backup.* files. If something goes wrong, stop it with sudo systemctl disable --now backup.timer.

Write the script and service

First put the script in /usr/local/bin, then write the service file and show its content. Keep the script in /usr/local/bin because of SELinux.

sudo tee /usr/local/bin/backup.sh > /dev/null <<'EOF'
#!/bin/bash
echo "backup done"
EOF
sudo chmod 755 /usr/local/bin/backup.sh

Expected output example

(no output)
sudo tee /etc/systemd/system/backup.service > /dev/null <<'EOF'
[Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
EOF
cat /etc/systemd/system/backup.service

Expected output example

[Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
My output looks different
  • If you get Permission denied, sudo is missing; sudo must come before tee.
  • The EOF line of the heredoc (<<'EOF') must stand alone at the start of its line.

Write the timer

Write a timer that runs every night at 02:30 and catches up missed runs, then paste its content.

sudo tee /etc/systemd/system/backup.timer > /dev/null <<'EOF'
[Unit]
Description=Run backup nightly

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=5min

[Install]
WantedBy=timers.target
EOF
cat /etc/systemd/system/backup.timer

Expected output example

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
...
My output looks different
  • The file must be called backup.timer: same name as the service, different extension.
  • The quoted heredoc ('EOF') stops the * from being expanded.

Verify

Verify the time expression and the unit files without running anything; paste the output.

systemd-analyze calendar "*-*-* 02:30:00"
systemd-analyze verify /etc/systemd/system/backup.service /etc/systemd/system/backup.timer

Expected output example

Normalized form: *-*-* 02:30:00
    Next elapse: Fri 2026-11-13 02:30:00 CET
(verify: usually no output = no problem)
My output looks different
  • If verify prints nothing, there is no problem.
  • On older versions the Next elapse text may differ slightly; the Normalized form line still appears.

Install and schedule

Run daemon-reload, enable the timer and see it scheduled with list-timers. backup.timer must appear in the output.

sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer
systemctl list-timers backup.timer

Expected output example

NEXT                        LEFT     LAST PASSED UNIT         ACTIVATES
Fri 2026-11-13 02:30:00 CET 16h left n/a  n/a    backup.timer backup.service
My output looks different
  • If you see Unit backup.timer not found, you skipped daemon-reload or the file name/path is wrong.
  • Because of RandomizedDelaySec, NEXT may be a few minutes after 02:30.

Run by hand, read the journal

Start the service once by hand and find the backup done line in its journal.

sudo systemctl start backup.service
journalctl -u backup.service --no-pager -n 10

Expected output example

systemd[1]: Starting backup.service - Nightly backup...
backup.sh[1234]: backup done
systemd[1]: backup.service: Succeeded.
My output looks different
  • On Rocky/RHEL the last line may read Deactivated successfully.; that is fine.
  • If you see Failed with result 'exit-code', the script path or permission is wrong (chmod 755, ls -Z for SELinux).

User timer and cleanup

Set up a user timer without sudo, see it in the list; then stop it and the system timer. If no errors, press "Done".

mkdir -p ~/.config/systemd/user
printf '[Service]\nType=oneshot\nExecStart=/usr/bin/touch %h/notes.txt\n' > ~/.config/systemd/user/notes.service
printf '[Timer]\nOnCalendar=hourly\n\n[Install]\nWantedBy=timers.target\n' > ~/.config/systemd/user/notes.timer
systemctl --user daemon-reload
systemctl --user enable --now notes.timer
systemctl --user list-timers

Expected output example

NEXT ... UNIT        ACTIVATES
... notes.timer notes.service
systemctl --user disable --now notes.timer
sudo systemctl disable --now backup.timer

Expected output example

Removed ...notes.timer symlink
My output looks different
  • If you get Failed to connect to bus, run it in your normal login session, not via sudo su; --user needs a non-root session.
  • %h means the home directory inside a unit; the printf is single-quoted so the shell does not expand it.

Self-test

Which file defines when a job runs?

The timer defines 'when', the service defines 'what'; their names match.

What does Persistent=true do?

Persistent stores the last run time on disk; a missed run is made up at boot.

You wrote a new .timer file. What must you do before enable --now?

systemd caches unit files; daemon-reload is required after a change.

Where do you read a service's output and error lines?

systemd writes output to the journal; -u filters by unit.

Summary

  • A timer is two files: .service defines what runs, .timer defines when.
  • Type=oneshot and an absolute ExecStart path are the standard for scheduled jobs.
  • OnCalendar is calendar time, OnBootSec/OnUnitActiveSec an interval; Persistent=true catches up missed runs.
  • Order: file → systemd-analyze calendar/verify → daemon-reload → manual start → enable --now → list-timers.
  • Read output with journalctl -u; the cron line 30 2 * * * = every day at 02:30.
  • User timers work without root via ~/.config/systemd/user and systemctl --user.

Key terms

timer unit
A .timer unit that starts a service at a given time.
service unit
A .service unit that defines the command to run.
oneshot
Type=oneshot: the command runs and finishes; suited to scheduled jobs.
OnCalendar
Calendar-based time expression, e.g. *-*-* 02:30:00.
Persistent
Persistent=true: catches up a missed run at the next boot.
RandomizedDelaySec
Adds a random start delay to avoid load spikes.
daemon-reload
Makes systemd re-read its unit files.
journal
systemd's log store, read with journalctl.
cron
The classic scheduler; crontab lines use five time fields.
linger
loginctl enable-linger: keeps user units running while logged out.
