3.7 Comparison: diff, cmp, comm, patch

Compare two files, two directories and two lists, read the difference, create and apply patches, and use exit codes in scripts.

What will you learn in this module?

  • You read diff output (normal and -u unified), including @@ hunks and +/- lines.
  • You compare directories and files quickly with diff -r, diff -q, cmp and sha256sum -c.
  • You find differences between sorted lists with comm, and common or unique lines with sort | uniq -d/-u.
  • You create patches with diff -u, apply them with patch, undo them with -R, and check exit codes (0/1/2).

diff: line-by-line differences

diff old new compares two text files line by line and prints the changes needed to turn the old file into the new one. In normal output you see a command line such as 2c2 (line 2 changed); < marks lines from the first file, > lines from the second.

In practice the unified format (-u) is the standard: --- is the first file, +++ the second; the hunk @@ -1,3 +1,4 @@ means three lines starting at line 1 in the first file and four lines starting at line 1 in the second. Lines starting with - exist only in the old file, lines with + only in the new one; lines starting with a space are context. Git and patch tools use this format.

Exit code: 0 files identical, 1 differences found, 2 trouble (file missing, unreadable). So diff reports 'failure' when it finds differences; that is not an error. In the simulator diff, cmp, comm and patch do not run; try them on your own VM. Here the simulator only checks that you typed the command, plus the prepared files.

diff

What is it for?
Shows the difference between two files in normal format (with < and > lines).
Where is it used?
When comparing two versions of a configuration file.
Why does it matter?
You see what changed without reading the whole file.
diff v1.txt v2.txt

diff -u

What is it for?
Unified format: ---/+++ header, @@ hunks and +/- lines.
Where is it used?
When sharing changes, in code review, when creating patches.
Why does it matter?
Context lines make clear where the change is.
diff -u v1.txt v2.txt

diff -q

What is it for?
Prints only 'Files ... differ', or nothing.
Where is it used?
When only 'same or not' matters; in scripts.
Why does it matter?
No long output, the exit code is still 0/1.
diff -q v1.txt v2.txt

diff -y

What is it for?
Shows two columns side by side; differences marked with |, <, >.
Where is it used?
When comparing short files by eye.
Why does it matter?
You see both versions next to each other.
diff -y v1.txt v2.txt

diff -w

What is it for?
Ignores whitespace differences (indentation, trailing spaces).
Where is it used?
For files that were only reformatted.
Why does it matter?
Noise disappears, real content differences remain.
diff -w v1.txt v2.txt
💡 Tip

Which file is 'old' and which is 'new'? Order matters: diff old new. Swap them and + and - swap too.

⚠️ Warning

Files created on Windows carry \r (CRLF) at each line end, so every line looks different. Clean up with tr -d '\r' < win.txt > fixed.txt or use diff --strip-trailing-cr.

Comparing directories

diff -r dir_a dir_b compares two directory trees recursively. For files that exist in only one directory it prints Only in dir_a: extra.txt; for files with different content it prints the diff. With -q (or -rq) you see only which files differ; ideal for checking a backup with many files.

You can also compare the output of two commands: diff <(sort a.txt) <(sort b.txt) (process substitution, a bash feature) hands the outputs over like temporary files. It does not work in plain sh.

diff -r

What is it for?
Compares two directories including subdirectories.
Where is it used?
When comparing two project versions or a backup.
Why does it matter?
Missing, extra and changed files in one go.
diff -r dir_a dir_b

diff -rq

What is it for?
Lists only files that differ or exist on one side only.
Where is it used?
For backup verification, in large trees.
Why does it matter?
A short overview; look at single files in detail afterwards.
diff -rq dir_a dir_b

diff <( )

What is it for?
Compares the output of two commands like files (bash).
Where is it used?
For sorted lists or comparing two environments.
Why does it matter?
No intermediate files needed.
diff <(sort list_a.txt) <(sort list_b.txt)
💡 Tip

Direction does not matter, but for readability always write the 'reference' directory first.

cmp and checksums

cmp compares files byte by byte and reports the byte and line number of the first difference. For binary files diff only says 'Binary files differ'; cmp shows the exact position. cmp -s prints nothing, only the exit code (0 same, 1 different, 2 trouble). In scripts: if cmp -s a b; then echo same; fi.

If the files are on different machines you cannot compare them directly; compute a checksum. sha256sum notes.txt produces a hash; identical content gives an identical hash. sha256sum -c sums.txt recomputes stored hashes and prints OK or FAILED. This is how you verify a download is intact. md5sum is outdated; use sha256sum for security.

cmp

What is it for?
Compares two files byte by byte and reports the position of the first difference.
Where is it used?
For binary files and to verify copies.
Why does it matter?
Gives a definite answer even for non-text files.
cmp v1.txt v2.txt

cmp -s

What is it for?
Silent comparison; the result is only in the exit code.
Where is it used?
In scripts as an if condition.
Why does it matter?
Decides 'same?' without output.
cmp -s v1.txt v1.bak; echo $?

sha256sum

What is it for?
Computes the SHA-256 hash of a file.
Where is it used?
For verifying downloads and backups.
Why does it matter?
You compare contents without having the files side by side.
sha256sum v1.txt

sha256sum -c

What is it for?
Checks a hash list; prints OK or FAILED per file.
Where is it used?
For ISO images or backups.
Why does it matter?
Shows automatically whether anything is corrupted or changed.
sha256sum -c sums.txt
💡 Tip

See the exit code with echo $? right after the command; if another command runs in between, the value is gone.

Comparing lists: comm, uniq

comm a b shows two sorted files in three columns: column 1 only in a, column 2 only in b, column 3 in both. -1, -2, -3 hide that column: comm -12 = common lines, comm -23 = only in a, comm -13 = only in b.

Pitfall: if the input is not sorted, comm gives wrong results and warns 'file 2 is not in sorted order'. Sort first: sort list_b.txt > sorted_b.txt.

Without comm, sort a b | uniq -d gives lines present in both lists (duplicated ones) and sort a b | uniq -u gives lines that appear only once. Each list should be free of duplicates itself, otherwise the counting breaks. Both commands also work in the simulator.

comm

What is it for?
Compares two sorted files in three columns.
Where is it used?
When comparing user, package or IP lists.
Why does it matter?
Separates common and unique lines in one command.
comm list_a.txt sorted_b.txt

comm -12

What is it for?
Shows only lines present in both files.
Where is it used?
When you need the intersection.
Why does it matter?
Hides columns 1 and 2, the common one remains.
comm -12 list_a.txt sorted_b.txt

comm -23

What is it for?
Shows only lines present in the first file.
Where is it used?
For the question 'I have it, you don't'.
Why does it matter?
Finds missing or surplus entries.
comm -23 list_a.txt sorted_b.txt

sort | uniq -d

What is it for?
From merged sorted lines, prints the duplicated (common) ones.
Where is it used?
Without comm, or for a quick intersection.
Why does it matter?
Works everywhere with standard tools.
sort list_a.txt list_b.txt | uniq -d

sort | uniq -u

What is it for?
Prints only lines that occur exactly once (symmetric difference).
Where is it used?
When looking for lines that are in only one of the lists.
Why does it matter?
Eliminates the common lines.
sort list_a.txt list_b.txt | uniq -u
💡 Tip

Rule of thumb: always sort before comm; and use the same locale (LC_ALL=C) afterwards, otherwise the sort order may not match.

Create and apply patches: patch

diff -u old new > change.patch writes the difference to a file. Someone else applies it with patch to their old copy: patch work.txt < change.patch. For directory trees you create diff -ruN old/ new/ > all.patch; when applying, -p1 strips the first path component (old/), -p0 uses paths unchanged.

Before applying, try patch --dry-run < change.patch: it changes nothing and tells you whether the hunks fit. On failures a .rej file is created. patch -R < change.patch undoes the patch.

A patch relies on context lines; if the file was changed elsewhere in the meantime, applying can fail or shift (fuzz).

diff -u > file.patch

What is it for?
Writes the difference in unified format to a patch file.
Where is it used?
To hand a change to someone else.
Why does it matter?
Only the changed lines are transported, not the whole file.
diff -u v1.txt v2.txt > change.patch

patch

What is it for?
Applies the changes in a patch file to a file.
Where is it used?
When working a received patch into your copy.
Why does it matter?
Applies only the difference instead of replacing the whole file.
patch work.txt < change.patch

patch --dry-run

What is it for?
Tests the patch without actually applying it.
Where is it used?
Before patching important files.
Why does it matter?
You spot mismatches without changing anything.
patch --dry-run work.txt < change.patch

patch -R

What is it for?
Reverses the patch (undoes it).
Where is it used?
When an applied patch causes problems.
Why does it matter?
Restores the state before the patch.
patch -R work.txt < change.patch
💡 Tip

If the patch is for a directory tree, run it from the project root and try --dry-run first.

⚠️ Warning

patch modifies files in place. For important files make a backup first with cp work.txt work.txt.orig, and on your VM take a snapshot first.

⛔ Danger

Do not apply patches to the root directory (/) or system configuration; work only in your practice folder. A wrong -p value changes the wrong files.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Run the following commands on your own VM in the ~/lab folder. They only create files in this practice folder and do not touch system settings.

diff: normal and unified

Create two small files and see the difference in both formats. Paste the unified output.

mkdir -p ~/lab && cd ~/lab
printf 'port=80\nhost=linux-lab\nmode=prod\n' > v1.txt
printf 'port=8080\nhost=linux-lab\nmode=prod\ndebug=on\n' > v2.txt
diff v1.txt v2.txt
diff -u v1.txt v2.txt

Expected output example

1c1
< port=80
---
> port=8080
3a4
> debug=on
--- v1.txt	2026-11-12 10:00:00
+++ v2.txt	2026-11-12 10:00:01
@@ -1,3 +1,4 @@
-port=80
+port=8080
 host=linux-lab
 mode=prod
+debug=on
My output looks different
  • Date and time will differ; what matters are the @@, - and + lines.
  • If there is no output, the files are identical; re-check the printf lines.

Exit codes

See diff -q, cmp -s and the exit codes. Paste the output.

cd ~/lab
diff -q v1.txt v2.txt; echo "exit=$?"
cp v1.txt same.txt
cmp -s v1.txt same.txt; echo "exit=$?"
diff v1.txt missing.txt; echo "exit=$?"

Expected output example

Files v1.txt and v2.txt differ
exit=1
exit=0
diff: missing.txt: No such file or directory
exit=2
My output looks different
  • If your system language differs, the message may be translated; the exit= values must match.
  • If you see exit=0 on the first line, v2.txt was not created; run v01 again.

comm and uniq

Compare two name lists. First see the warning for unsorted comm, then the right way.

cd ~/lab
printf 'alice\nbob\ncarol\ndave\n' > list_a.txt
printf 'erin\nbob\ncarol\n' > list_b.txt
comm -12 list_a.txt list_b.txt
sort list_b.txt > sorted_b.txt
comm -12 list_a.txt sorted_b.txt
comm -23 list_a.txt sorted_b.txt
sort list_a.txt list_b.txt | uniq -d
diff <(sort list_a.txt) <(sort list_b.txt)

Expected output example

comm: file 2 is not in sorted order
bob
carol
alice
dave
bob
carol
1d0
< alice
...
My output looks different
  • With unsorted input the comm warning may not appear or the output may be incomplete; the result is undefined, so always sort first.
  • If diff <(...) gives a syntax error, your shell is not bash; type bash and try again.

Create, test, apply and undo a patch

Turn a copy of v1.txt into v2.txt with a patch and undo it. Paste the output.

cd ~/lab
diff -u v1.txt v2.txt > change.patch
cp v1.txt work.txt
patch --dry-run work.txt < change.patch
patch work.txt < change.patch
cat work.txt
patch -R work.txt < change.patch
cat work.txt

Expected output example

checking file work.txt
patching file work.txt
port=8080
host=linux-lab
mode=prod
debug=on
patching file work.txt
port=80
host=linux-lab
mode=prod
My output looks different
  • If you see patch: command not found: on Ubuntu sudo apt install patch, on Rocky/Alma sudo dnf install patch.
  • If --dry-run is not supported (very old version), skip that line.
  • If you see Hunk #1 FAILED, work.txt is not identical to v1.txt; start over with cp v1.txt work.txt.

Checksums

Compute hashes, then modify a file and catch the corruption with sha256sum -c. Paste the output.

cd ~/lab
sha256sum v1.txt same.txt
sha256sum v1.txt > sums.txt
sha256sum -c sums.txt
echo 'x' >> v1.txt
sha256sum -c sums.txt

Expected output example

<64 hex characters>  v1.txt
<64 hex characters>  same.txt
v1.txt: OK
v1.txt: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
My output looks different
  • The first two hashes must be identical (v1.txt and same.txt have the same content).
  • On a non-English system the warning text may be translated; OK and FAILED stay the same.
  • If same.txt is missing, run the step from v02.

Self-test

With which exit code does diff a b end when the files differ?

0 identical, 1 differences, 2 trouble. A difference is not an error, but it is not zero either.

What does comm need from its input files to work correctly?

comm expects sorted input; otherwise the result is wrong. Apply sort first.

What does a line starting with + mean in unified diff output?

- was removed from the old file, + added to the new one; lines starting with a space are context.

Which command undoes an applied patch?

patch -R reverses the patch; the patch file is read from standard input.

Summary

  • diff -u old new shows the change; exit code 0 same, 1 different, 2 trouble.
  • diff -rq checks directories, cmp compares bytes, sha256sum -c verifies content integrity.
  • comm works only on sorted input; alternatives: sort | uniq -d (common) and uniq -u (unique).
  • Create a patch with diff -u > change.patch, test with patch --dry-run, apply with patch, undo with patch -R.
  • Pitfalls: unsorted comm, CRLF line endings, diff on binary files.

Key terms

hunk
A change block in unified diff that starts with @@ and includes context lines.
unified diff
The diff -u format: ---/+++ header, @@ hunks, +/- lines.
patch
A file holding diff output; the patch command applies it to files.
exit code
A command's final status, read with $?. For diff: 0 same, 1 different, 2 trouble.
checksum
A hash value computed from content; if the content changes, the value changes.
CRLF
Windows line ending (\r\n); Linux uses only \n.
