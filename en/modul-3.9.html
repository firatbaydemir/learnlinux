3.9 Advanced Basics

Work in bulk, not one by one: find files with find, process them with xargs, redirect streams, build pipelines and write your first small script.

What will you learn in this module?

  • Find files with find by name, type, size, time and permissions
  • Know the difference between -exec ... {} \;, -exec ... {} + and xargs; list first before -delete
  • Redirect stdout/stderr: >, >>, 2>, 2>&1, /dev/null, here-document and tee
  • Summarise logs with pipelines such as sort | uniq -c | sort -nr
  • Recognise the pitfalls of quoting ('...' and "..."), globs and brace expansion
  • Use exit codes, &&/||, shebang, chmod +x and ./script.sh to run small scripts

find: searching in depth

find <start> <conditions> <action> walks the directory tree and processes every path that meets the conditions. With no conditions it lists everything. With no action the default is -print.

Key rule: quote your patterns. If you type find . -name *.log, the shell expands *.log against files in the current directory before find even starts, and the result will surprise you.

List first, act later: before a dangerous action (-delete, -exec rm) run the same command without the action and read the output.

find -name / -iname

What is it for?
Searches file names by pattern; -iname ignores upper/lower case.
Where is it used?
When looking for files with a certain extension in a project.
Why does it matter?
You scan the whole tree in seconds without browsing by hand.
find . -name "*.log"

find -type

What is it for?
Filters by type: f file, d directory, l symbolic link.
Where is it used?
When you only want directories or only files.
Why does it matter?
Lets you set permissions for directories and files separately instead of a blanket chmod -R.
find . -type d

find -size / -mtime / -perm / -user

What is it for?
Filters by size (-size +1M), modification day (-mtime +7 = older than 7 days), permissions (-perm 644) or owner (-user alice).
Where is it used?
In clean-ups, security audits, hunting old logs.
Why does it matter?
Finding the right file is cheaper than deleting the wrong one.
find /var/log -name "*.log" -mtime +7

find -exec ... {} \;

What is it for?
Runs the command for EACH match separately; {} is replaced by the path. End it with + and the paths are collected and passed to a single call.
Where is it used?
When applying chmod, ls -l, wc and the like to every file.
Why does it matter?
Bulk processing without a loop; the + form starts far fewer processes.
find project -name "*.tmp" -exec ls -l {} \;

find -delete

What is it for?
Deletes matches directly; there is no undo.
Where is it used?
When cleaning up temporary files.
Why does it matter?
Faster than -exec rm (one process). Put conditions BEFORE -delete, otherwise everything is deleted.
find project -name "*.tmp" -delete
💡 Tip

Habit: first find ... -print, read the output, then append -delete or -exec.

⛔ Danger

find . -delete with no condition deletes EVERYTHING in the current tree. Order matters: -name first, -delete last.

xargs and command substitution

rm, cp, wc expect file names as arguments and do not read them from a pipe (stdin). xargs turns the lines on stdin into arguments for that command.

File names may contain spaces or newlines. The safe way: find ... -print0 | xargs -0 ...; names are separated by the NUL character. A plain | xargs rm hits the wrong file when names contain spaces.

$(command) inserts a command's output into the command line. It is an alternative to xargs but can hit the argument-length limit on very long lists.

xargs

What is it for?
Runs a command and passes it the input from stdin as arguments.
Where is it used?
When feeding the output of find or grep -l into rm, wc, chmod.
Why does it matter?
Fills the gap of the pipe: output becomes arguments.
find . -name "*.txt" | xargs wc -l

find -print0 | xargs -0

What is it for?
Separates names with NUL and hands them to xargs; safe with spaces and odd characters.
Where is it used?
For irreversible bulk jobs such as deleting and moving.
Why does it matter?
A file called my file.txt is not split into two arguments.
find . -name "*.tmp" -print0 | xargs -0 rm

$(...)

What is it for?
Command substitution: the inner command's output becomes part of the outer command.
Where is it used?
When adding a date to a file name or hostname to a message.
Why does it matter?
You build commands with dynamic values.
echo "host: $(hostname)"
⚠️ Warning

xargs may run the command once even on empty input (GNU: prevent with -r). For dangerous commands first use xargs echo rm to see what would run.

Streams, redirection and pipelines

Every process has three streams: 0 stdin, 1 stdout, 2 stderr. > redirects stdout (1), 2> redirects stderr. 2>&1 means "send stderr to wherever stdout currently goes"; order matters: cmd > f 2>&1 writes both to the file, cmd 2>&1 > f leaves errors on screen.

Throw noise into /dev/null: cmd 2> /dev/null. In Bash, &> redirects both stdout and stderr; the portable form is > f 2>&1.

The classic log-summary pattern: cut -d' ' -f2 run.log | sort | uniq -c | sort -nr. uniq only merges adjacent lines, which is why sort must come first.

2> and 2>&1

What is it for?
2> f writes errors to a file; > f 2>&1 writes output and errors to the same file.
Where is it used?
When collecting script output in a log file.
Why does it matter?
You record errors without losing them; the order is essential.
ls missing.txt notes.txt > both.txt 2>&1

> /dev/null

What is it for?
Throws the output away.
Where is it used?
When you only care about the exit code, not the output.
Why does it matter?
Keeps the screen clean: grep -q or cmd 2> /dev/null.
ls missing.txt 2> /dev/null

<<EOF (here-document)

What is it for?
Feeds several lines into the command's stdin; ends when EOF stands alone on a line.
Where is it used?
When creating scripts or configuration files.
Why does it matter?
With a quoted <<'EOF' variables are not expanded; the text goes in literally.
cat > notes2.txt <<'EOF'
line one
line two
EOF

tee

What is it for?
Writes stdin to the screen and to a file; -a appends.
Where is it used?
When saving an intermediate result in the middle of a pipeline.
Why does it matter?
You see and store at once. | sudo tee f solves the permission problem of sudo cmd > f.
grep ERROR run.log | tee errors.txt

sort | uniq -c | sort -nr

What is it for?
Counts lines and sorts them from most to least frequent.
Where is it used?
In log, IP and error-frequency analysis.
Why does it matter?
One line answers "which occurs most"; add | head -n 3 for the top three.
cut -d' ' -f2 run.log | sort | uniq -c | sort -nr
💡 Tip

wc -l counts lines; head -n 1 gives the first line, tail -n 5 the last five. Combined they make quick log checks.

Quoting, expansion and exit codes

The shell expands before running: $VARIABLE, $(...), globs (*.log) and braces ({a,b}). Quotes control this expansion.

Double quotes "..." expand variables and $(...) but block globbing. Single quotes '...' expand nothing. Always protect values with spaces using double quotes.

Every command returns an exit code: 0 means success, anything else an error. $? shows the last one. && continues only on success, || only on failure.

'...' and "..."

What is it for?
Single quotes leave text unchanged; double quotes allow $ expansion.
Where is it used?
When writing variables, names with spaces and patterns.
Why does it matter?
echo "$HOME" prints the path, echo '$HOME' prints the text $HOME.
echo "$HOME" '$HOME'

* ? [ ] glob

What is it for?
The shell expands the pattern to file names; * is anything, ? one character.
Where is it used?
When selecting several files with one command.
Why does it matter?
Unquoted, the pattern arrives mangled at find -name; if *.log matches nothing it stays as typed.
ls logs/*.log

{a,b} brace expansion

What is it for?
The shell turns {a,b,c} into three words; it does not look at files, it only generates text.
Where is it used?
When creating several files or directories.
Why does it matter?
mkdir -p project/{src,docs} creates two directories with one command.
touch report_{1,2,3}.txt

&& and ||

What is it for?
a && b: b only if a succeeded. a || b: b only if a failed. ; always continues.
Where is it used?
For tasks with a precondition: cd dir && rm ....
Why does it matter?
If cd fails, the following delete does not run in the wrong directory.
grep -q FATAL run.log || echo none
⚠️ Warning

Write cd logs && rm *.tmp instead of cd logs; rm *.tmp: if cd fails, ; still runs rm in the directory you are in.

Your first script: shebang and running it

A script is a text file containing commands. The first line, the shebang (#!/bin/bash), names the interpreter. To run it the file needs the x permission.

./script.sh runs the file from the current directory. If you type just script.sh, the shell only searches the directories in PATH; the current directory is deliberately not in it (security). bash script.sh works even without x.

Script arguments are $1, $2 …, the exit code is $?. In small scripts you can set a default with name="${1:-world}".

#!/bin/bash

What is it for?
First line of the script; tells the kernel the interpreter.
Where is it used?
At the top of every executable script.
Why does it matter?
It is clear which shell runs the script, keeping behaviour consistent across distributions.
printf '#!/bin/bash\necho "Hello $1"\n' > greet.sh

chmod +x

What is it for?
Adds the execute permission to the file.
Where is it used?
Before running your script directly.
Why does it matter?
Without x, ./script.sh says "Permission denied".
chmod +x greet.sh

./script.sh

What is it for?
Runs the script by path; arguments follow.
Where is it used?
For scripts in the current directory.
Why does it matter?
No PATH lookup; exactly the file you chose runs.
./greet.sh alice

echo $?

What is it for?
Shows the exit code of the last command (0 = success).
Where is it used?
When checking a command's success by hand or in a script.
Why does it matter?
&&, || and if all use this code.
grep -q ERROR run.log; echo $?
💡 Tip

For your own scripts you can add ~/bin to PATH: export PATH="$HOME/bin:$PATH". Make it permanent in ~/.bashrc.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Do the following steps on your own VM (Ubuntu, Rocky or Alma). Try everything under ~/adv; never use -delete or rm -r where real data lives.

Set up a practice area and search with find

Build a practice tree, then search with find by name, type and size. Paste the output.

mkdir -p ~/adv/logs ~/adv/project/src
touch ~/adv/logs/app.log ~/adv/logs/old.log ~/adv/project/a.tmp ~/adv/project/src/b.tmp
echo data > ~/adv/project/src/main.txt
find ~/adv -name "*.log"
find ~/adv -type d
find ~/adv -type f -size -1k

Expected output example

/home/student/adv/logs/app.log
/home/student/adv/logs/old.log
/home/student/adv
/home/student/adv/logs
...
My output looks different
  • The order of find output depends on the file system; what matters is that all .log files appear.
  • If your user is not student, the start of the path differs; that is fine.

-exec, + and xargs

Apply first -exec ... \;, then -exec ... + and xargs -0 to the same files. Notice: \; starts one command per file, + batches.

find ~/adv -name "*.tmp" -exec ls -l {} \;
find ~/adv -name "*.tmp" -exec ls -l {} +
find ~/adv -name "*.tmp" -print0 | xargs -0 ls -l

Expected output example

-rw-r--r-- 1 student student 0 Nov 12 10:00 /home/student/adv/project/a.tmp
-rw-r--r-- 1 student student 0 Nov 12 10:00 /home/student/adv/project/src/b.tmp
My output looks different
  • With + the ls -l output usually comes sorted by path, with \; in find order. The content is the same.
  • The message find: missing argument to '-exec' means the trailing \; or + is missing.

List first, then delete

First take a snapshot of your VM. -delete is irreversible: see what would be deleted, then delete only inside ~/adv. Press "Done" afterwards.

# Dry run first
find ~/adv -name "*.tmp" -print
# If correct, delete (condition BEFORE -delete)
find ~/adv -name "*.tmp" -delete
find ~/adv -name "*.tmp"

Expected output example

(the last command prints nothing)
My output looks different
  • If the last command still lists files, -delete may be missing or you are in the wrong directory; check with pwd.

Log analysis: here-document and pipeline

Write a sample log with a here-document, then count the levels and redirect the error stream.

cat > ~/adv/run.log <<'EOF'
10:01 INFO start
10:02 ERROR disk full
10:03 WARN slow disk
10:04 INFO retry
10:05 ERROR timeout
10:06 INFO ok
EOF
cut -d' ' -f2 ~/adv/run.log | sort | uniq -c | sort -nr
ls /nonexistent ~/adv/run.log > ~/adv/both.txt 2>&1
cat ~/adv/both.txt

Expected output example

      3 INFO
      2 ERROR
      1 WARN
ls: cannot access '/nonexistent': No such file or directory
/home/student/adv/run.log
My output looks different
  • If numbers or spacing differ, check the log lines: the second field of each line must be the level.
  • On a localised system the error message is translated; you will see local text instead of No such file.

Your first script

Write the script, try to run it without x, grant the permission, run it again and look at the exit code.

cd ~/adv
cat > hello.sh <<'EOF'
#!/bin/bash
name="${1:-world}"
echo "Hello, $name"
EOF
./hello.sh
chmod +x hello.sh
./hello.sh student
echo $?

Expected output example

bash: ./hello.sh: Permission denied
Hello, student
0
My output looks different
  • If the first ./hello.sh works, your file system (e.g. some WSL mounts) already grants x.
  • If you see hello.sh: command not found, you forgot the ./ prefix; the current directory is not in PATH.

Self-test

What is the difference between find ... -exec rm {} \; and find ... -exec rm {} +?

\; starts one process per match; + collects arguments and gets by with far fewer processes.

Why is find . -name *.log (unquoted) a problem?

The shell does the expanding. Quote the pattern as "*.log" so it reaches find unchanged.

Which command writes both output and errors to out.txt?

stdout is redirected to the file first, then stderr goes "where stdout now goes". In the reverse order the error stays on screen.

How do you safely pass find results to rm when file names contain spaces?

-print0 and xargs -0 separate names with NUL; names containing spaces or newlines are not split.

Summary

  • find walks trees; quote patterns, list first, then add -delete/-exec.
  • -exec ... \; per file, -exec ... + and xargs in batches; the safe pair: -print0 | xargs -0.
  • > stdout, 2> stderr, 2>&1 merges (order matters), /dev/null is the bin, tee shows and saves.
  • sort | uniq -c | sort -nr finds the most frequent entries; combine with head/tail/wc -l.
  • Double quotes expand, single quotes do not; && on success, || on failure.
  • Script = shebang + chmod +x + ./script.sh; exit code $?.

Key terms

glob
File name patterns like *, ?, [...] that the shell expands.
stdout / stderr
Standard output (1) and standard error (2) streams.
here-document
Passing multi-line text as a command's input with <<EOF.
pipe
| connects the output of one command to the input of the next.
shebang
The first script line #!/bin/bash; it names the interpreter.
exit code
Number a command returns when it ends; 0 success, otherwise error. Read with $?.
NUL separator
The \0 byte that separates names; -print0 and xargs -0 use it.
