5.2 Resource Monitoring

Read CPU, load, memory and disk with uptime, free, df, top and friends, and find out what is slowing the system down.

What will you learn in this module?

  • You read the load average relative to the number of CPU cores (nproc).
  • You tell free memory from available memory and understand buff/cache.
  • You check disk usage with df and du and find big folders.
  • You find the top CPU and memory consumers with top, htop and ps.

Load and CPU: uptime, nproc, lscpu

When a server feels slow, look at the load average first. uptime shows three numbers: the average load of the last 1, 5 and 15 minutes. The same values live in /proc/loadavg.

A load number alone means nothing. Read it relative to the number of cores (nproc). On a 4-core machine a load of 4.0 means fully used, 8.0 means processes are waiting in line (saturation). Rule of thumb: load below the core count is fine, load above it means overload.

Compare the three values: 1 min higher than 15 min means the load is rising now; 1 min lower than 15 min means it is calming down.

uptime

What is it for?
Shows the time, how long the system has been up, logged-in users and the load average (1, 5, 15 min).
Where is it used?
As the very first look at a slow server.
Why does it matter?
One line tells you if the machine is busy and in which direction it is going.
uptime

nproc

What is it for?
Prints the number of available CPU cores (threads).
Where is it used?
Together with uptime to judge the load.
Why does it matter?
Load 4.0 is fine on 8 cores but saturated on 2 cores.
nproc

lscpu

What is it for?
Shows CPU details: model, sockets, cores, threads, MHz.
Where is it used?
When you need to know what hardware the VM or server really has.
Why does it matter?
Confirms how many cores you have and whether they are virtual.
lscpu

cat /proc/loadavg

What is it for?
Raw load data: three load values, running/total tasks and the last PID.
Where is it used?
In scripts, or when uptime is not installed.
Why does it matter?
It is the source that uptime and top read from.
cat /proc/loadavg
💡 Tip

Quick check: if the first load value divided by nproc is above 1, the CPU is saturated.

Memory: free, /proc/meminfo, vmstat

free -h shows RAM and swap in readable units. Do not panic about a small free value: Linux uses unused RAM as cache (buff/cache) and gives it back when programs need it.

The column that matters is available: it estimates how much memory new programs can get without swapping. Low *available* plus heavy swap use means real memory shortage. Details are in /proc/meminfo (MemTotal, MemFree, MemAvailable).

vmstat shows memory, swap, I/O and CPU in one table. Columns si/so (swap in/out) above zero for a long time and a high wa (waiting for I/O) are warning signs.

free -h

What is it for?
Shows total, used, free, shared, buff/cache and available RAM and swap in human-readable units.
Where is it used?
When the system is slow and you suspect full RAM.
Why does it matter?
Looking at available instead of free prevents false alarms.
free -h

cat /proc/meminfo

What is it for?
Prints the detailed kernel memory statistics.
Where is it used?
For scripts or when you need exact values like MemAvailable or SwapFree.
Why does it matter?
It is the source behind free.
grep MemAvailable /proc/meminfo

vmstat 1 5

What is it for?
Prints a CPU, memory, swap and I/O line every second, five times.
Where is it used?
To see trends over a few seconds instead of one snapshot.
Why does it matter?
Shows swapping (si/so) and I/O wait (wa) that top hides at first glance.
vmstat 1 5
💡 Tip

Ignore the first line of vmstat; it shows averages since boot. The following lines are live.

Disk: df, du, iostat

A full disk causes strange errors: services crash, logs cannot be written. df -h shows usage per filesystem, du shows which folder uses the space.

Workflow: df -h finds the full filesystem, then du -sh /var/* or du -h /var | sort -h | tail finds the big folders. sort -h understands sizes like 4K, 12M, 3G.

iostat comes from the sysstat package and shows disk activity. High %util and await mean the disk is the bottleneck.

df -h

What is it for?
Shows size, used, available and percentage per mounted filesystem.
Where is it used?
As the first check for 'No space left on device'.
Why does it matter?
You see which mount point is nearly full (Use%).
df -h

du -sh

What is it for?
Shows the total size of a folder (-s summary, -h readable).
Where is it used?
To measure a single folder such as your home or /var/log.
Why does it matter?
Answers 'how big is this?' with one line.
du -sh ~/Documents

du -h | sort -h

What is it for?
Lists sizes of all subfolders, sorted from small to large.
Where is it used?
To find the biggest folders; add | tail -n 5 for the top five.
Why does it matter?
Finds the space hog quickly.
du -h /var/log | sort -h | tail -n 5

iostat -x 1 3

What is it for?
Extended disk statistics every second, three times (needs the sysstat package).
Where is it used?
When the system is slow but CPU and RAM look fine.
Why does it matter?
Shows whether the disk is saturated (%util, await).
iostat -x 1 3
💡 Tip

Install sysstat: Ubuntu/Debian sudo apt install sysstat, Rocky/Alma sudo dnf install sysstat.

⚠️ Warning

du on / can run for minutes and load the disk. Limit it to one folder, for example du -h /var | sort -h | tail.

Processes: top, htop, ps

top is the live task manager of the terminal. The header shows load, tasks, CPU and memory; below is the process list. In top: P sorts by CPU, M by memory, q quits.

htop is the colourful, easier version. It is not installed by default. Ubuntu/Debian: sudo apt install htop. On Rocky/Alma it lives in the EPEL repository: first sudo dnf install epel-release, then sudo dnf install htop.

For scripts and logs use batch mode: top -b -n 1 prints one snapshot and exits. ps aux --sort=-%mem | head lists the top memory consumers, --sort=-%cpu the top CPU consumers (the minus means descending).

top

What is it for?
Live view of load, CPU, memory and processes; refreshes every 3 seconds.
Where is it used?
To see right now who is using resources.
Why does it matter?
Finds the PID of the problem process.
top

top -b -n 1

What is it for?
Batch mode: prints one snapshot and exits.
Where is it used?
In scripts, tickets and when piping to head or grep.
Why does it matter?
You can save or filter the output, for example top -b -n 1 | head -n 15.
top -b -n 1 | head -n 15

htop

What is it for?
Interactive process viewer with colours, bars and mouse support.
Where is it used?
Daily work on servers and VMs.
Why does it matter?
Easier to read and to sort than top.
htop

ps aux --sort=-%mem | head

What is it for?
Lists processes sorted by memory use, highest first, first 10 lines.
Where is it used?
When RAM is nearly full and you look for the culprit.
Why does it matter?
Shows user, PID, %CPU, %MEM and command in a copyable list.
ps aux --sort=-%mem | head

ps aux --sort=-%cpu | head

What is it for?
Lists processes sorted by CPU use, highest first.
Where is it used?
When the load is high.
Why does it matter?
Finds the CPU hog without an interactive screen.
ps aux --sort=-%cpu | head
💡 Tip

In top press 1 to see every core separately and c to see full command lines.

Triage: a fixed order

When a ticket says 'the server is slow', follow the same order each time: 1. uptime and nproc (load vs cores), 2. free -h (available memory, swap), 3. df -h (full disk), 4. top or ps aux --sort=-%cpu | head (who is the culprit), 5. vmstat 1 5 / iostat -x (swap or disk bottleneck).

Decide: high load and high us CPU means a CPU problem. High load with low CPU but high wa means disk or network I/O. Low available memory and swap activity means a RAM problem.

To practise on your VM you need load. Use a time limit: timeout 30 yes > /dev/null & starts one CPU hog that stops after 30 seconds. See the VM section.

💡 Tip

Write down the numbers before you change anything. A ticket answer like 'load 4.5 on 2 cores, python3 uses 85% CPU' is worth more than 'it is slow'.

⚠️ Warning

Load generators such as yes > /dev/null & or stress-ng run until stopped. Always use timeout and clean up with pkill yes afterwards.

⛔ Danger

Never start a load generator or kill processes on a production server. Practise only on your own VM, and take a snapshot first.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Run these on your own VM (Ubuntu, Rocky, Alma or WSL). Monitoring commands are harmless; only the last task creates load. Take a snapshot before it.

Load and cores

Show the load average and the number of cores. Is the 1-minute load below the core count? Paste the output of uptime.

uptime
nproc
cat /proc/loadavg

Memory: free vs available

Look at memory. Compare the free and available columns. Paste the output.

free -h
grep -E 'MemTotal|MemFree|MemAvailable' /proc/meminfo

Expected output example

              total        used        free      shared  buff/cache   available
Mem:          3.8Gi       612Mi       2.4Gi        12Mi       860Mi       3.0Gi
Swap:         2.0Gi          0B       2.0Gi
MemTotal:        3980000 kB
MemFree:         2500000 kB
MemAvailable:    3100000 kB
My output looks different
  • Without swap the Swap line shows 0B; that is fine.
  • On older systems the available column may be missing; use MemAvailable from /proc/meminfo.

Disk usage

Find the filesystem usage and the five biggest folders under /var. Paste the output.

df -h
du -sh ~
sudo du -h /var 2>/dev/null | sort -h | tail -n 5

Expected output example

Filesystem           Size  Used Avail Use% Mounted on
/dev/mapper/rhel-root  20G  4.1G   16G  21% /
...
My output looks different
  • The device names differ (/dev/sda1, /dev/vda2, /dev/mapper/...).
  • On WSL you see extra mounts like /mnt/c; ignore them.

vmstat, iostat and htop

Install the tools and take a short measurement. Debian/Ubuntu: sudo apt install sysstat htop. Rocky/Alma: htop needs EPEL, so first sudo dnf install epel-release.

# Ubuntu / Debian
sudo apt install -y sysstat htop
# Rocky / Alma
sudo dnf install -y epel-release
sudo dnf install -y sysstat htop

Expected output example

Complete! (or: Setting up htop ...)
vmstat 1 5
iostat -x 1 3

Expected output example

procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
My output looks different
  • Run only the block for your distribution; the other one fails.
  • If iostat is not found, sysstat is not installed.
  • Press q to leave htop.

Create load and find the culprit

Warning: this task loads your CPU. Take a VM snapshot first and do this only on your own VM. The timeout stops the load after 30 seconds. Start it, watch it in top, find it with ps, and clean up. Press "Done" when pgrep yes prints nothing at the end.

timeout 30 yes > /dev/null &
sleep 5
uptime
top -b -n 1 | head -n 12
ps aux --sort=-%cpu | head -n 5
pkill yes
sleep 1
pgrep yes

Expected output example

... the `yes` process shows about 100 %CPU at the top ...
(no output from the last command)
My output looks different
  • With several cores one yes uses only about 100% of one core, so the load rises slowly.
  • If pgrep yes still prints a PID, run pkill yes again.

Self-test

Which memory value tells you how much RAM new programs can really get?

free is only unused RAM. Linux also uses RAM as cache; available includes the part it can give back, so it is the right value.

A 4-core machine shows a 1-minute load of 8.0. What does that mean?

Load is read relative to the cores. Load 8 on 4 cores means twice as many runnable tasks as cores.

How do you install htop on Rocky Linux?

On the RHEL family htop is in the EPEL repository, so enable EPEL first. apt is for Debian/Ubuntu.

Which command lists the top memory consumers?

ps with --sort=-%mem sorts by memory descending; head shows the first lines.

Summary

  • Read the load average (1/5/15 min) relative to nproc; load above the core count means saturation.
  • free -h: look at available, not free; buff/cache is reusable.
  • df -h finds the full filesystem, du -sh and du -h | sort -h the big folders.
  • top, htop (EPEL on Rocky/Alma), top -b -n 1 and ps aux --sort=-%mem | head find the culprit.
  • vmstat and iostat (sysstat) reveal swap and disk bottlenecks.
  • Test load only on your own VM, with timeout, after a snapshot.

Key terms

load average
Average number of tasks running or waiting for CPU/I-O over 1, 5 and 15 minutes.
saturation
Load is higher than the core count; work waits in a queue.
buff/cache
RAM used for file caches; the kernel frees it when needed.
available
Estimate of memory that new programs can use without swapping.
swap
Disk space used as an emergency extension of RAM; slow.
EPEL
Extra Packages for Enterprise Linux: additional repository for RHEL, Rocky and Alma.
I/O wait (wa)
Share of time the CPU waits for disk or network.
