4.5 Special Permissions

Setuid, setgid and the sticky bit: what they do where plain rwx permissions are not enough (passwd, shared team folders, /tmp). Try them on your own VM, then reinforce in the simulator.

What will you learn in this module?

  • You recognise the setuid (4), setgid (2) and sticky (1) bits and the leading digit in an octal mode.
  • You read the letters s, S, t, T in ls -l output correctly.
  • You build a team folder with 2775 and explain why new files keep the group.
  • You protect shared writable folders such as /tmp with the sticky bit (1777).
  • You know why setuid is dangerous and audit setuid files with find.

The three special bits and octal notation

Normal permissions are written with three digits (755). In the four-digit form the leading digit carries the special bits: 4 = setuid, 2 = setgid, 1 = sticky. They add up: 3 = setgid + sticky, 6 = setuid + setgid. A leading zero (0755) means no special bit.

ls -l shows the bits in the x position: s in the owner slot (setuid), s in the group slot (setgid), t in the others slot (sticky). If the x permission underneath is missing, the letter becomes uppercase: S or T. An uppercase letter means 'bit set, but not executable', which is usually a mistake.

The meaning differs for files and directories: setuid and setgid on a file mean 'run with the owner's/group's privileges'; setgid and sticky on a directory mean 'inherit the group' and 'restrict deletion'.

stat

What is it for?
Shows the mode as four-digit octal and as letters.
Where is it used?
When verifying special bits.
Why does it matter?
The line Access: (2775/drwxrwsr-x) gives both notations side by side.
stat prog_c

ls -ld

What is it for?
Shows the permissions of the directory itself (not its contents).
Where is it used?
When checking a team folder or /tmp.
Why does it matter?
Without -d it lists the contents instead of the directory's own mode.
ls -ld /tmp

chmod 4755

What is it for?
Sets a four-digit octal mode; the leading digit is the special bit.
Where is it used?
When you want to set a special bit together with the other permissions.
Why does it matter?
You know the exact result, but old special bits are overwritten too.
chmod 4755 prog_a
💡 Tip

Symbolic mode is safer: chmod g+s team only adds setgid and leaves the other permissions alone.

⚠️ Warning

On files, a three-digit chmod 755 notes.txt clears the special bits. On directories GNU chmod keeps setuid/setgid; to remove them use chmod g-s team or the five-digit chmod 00755. Check with ls -ld afterwards.

setuid: run with the owner's privileges

When an executable file has setuid (4000), the program runs with the privileges of the file owner, not the person who starts it. The best-known example is /usr/bin/passwd: owned by root, shown as -rwsr-xr-x. An ordinary user can change their own password because the program, running as root, may update /etc/shadow. sudo and mount work on the same principle.

This power is risky. A small bug in a setuid-root program (or a setuid shell, editor or interpreter) hands root to everyone. That is why you must know your setuid files and audit them regularly.

Two notes: the Linux kernel ignores setuid on shell scripts (#!/bin/bash); chmod u+s on a script does not grant root, it only misleads. Also, setuid does nothing on file systems mounted with nosuid (e.g. many USB sticks, or a separate /tmp partition).

chmod u+s

What is it for?
Adds setuid in the owner x slot (s).
Where is it used?
Rarely on real systems, only for audited, compiled programs.
Why does it matter?
A (very carefully used) way to let normal users perform one privileged task.
chmod u+s backup.sh

ls -l /usr/bin/passwd

What is it for?
Shows the mode of a real setuid program: -rwsr-xr-x root root.
Where is it used?
To see what setuid looks like.
Why does it matter?
The s in the owner x slot is setuid.
ls -l /usr/bin/passwd

find / -perm -4000 -type f 2>/dev/null

What is it for?
Lists all setuid files on the system (-perm -4000 = this bit is set).
Where is it used?
During security audits and hardening.
Why does it matter?
An unexpected setuid file can be a sign of compromise.
find / -perm -4000 -type f 2>/dev/null
💡 Tip

Familiar names like passwd, sudo, mount, su are normal. An unknown setuid file, or one under /home or /tmp, needs investigation.

⛔ Danger

Never run chmod u+s /bin/bash (or on vim, python, find, cp) on a real system. It gives every user a root shell and is a classic privilege escalation. At most try it on your isolated test VM, after a snapshot, and undo it afterwards.

setgid: a team folder that inherits the group

On files, setgid (2000) runs the program with the group's privileges; in practice its main use is on directories. In a directory with setgid, every new file and subdirectory gets the directory's group instead of the creator's primary group. New subdirectories inherit the setgid bit too, so the rule holds across the whole tree.

Without it: alice drops a file into the devs folder, the file belongs to group alice, and teammate bob cannot edit it. With setgid the group stays devs. For members to be able to write group files you also need umask 002; with 022 a new file is rw-r--r-- and the group cannot write.

The simulator does not implement group inheritance; it only sets the bit and shows it in ls -l and stat. You will see the real behaviour in the VM task.

chmod g+s

What is it for?
Adds setgid in the group x slot (s).
Where is it used?
To turn an existing folder into a team folder.
Why does it matter?
Switches on group inheritance without touching other permissions.
chmod g+s team

chmod 2775

What is it for?
setgid + rwxrwxr-x: owner and group full, others read.
Where is it used?
When setting up a team folder.
Why does it matter?
The standard team-folder mode in one command.
chmod 2775 team

umask 002

What is it for?
Keeps the group write bit on new files in this shell.
Where is it used?
Before you work in the team folder.
Why does it matter?
setgid gives the right group, umask lets the group write.
umask 002
💡 Tip

On a directory, rwxrwsr-x is fine: group s (x present + setgid). With rwxrwSr-x the group lacks x and cannot enter the folder; fix it.

⚠️ Warning

umask only affects the current shell. To make it permanent add it to the user profile (e.g. ~/.bashrc); system-wide it is a separate configuration.

Sticky bit: restrict deletion in shared folders

In a folder everyone can write to (777), anyone can delete or rename other people's files, because the right to delete depends on the write permission of the directory, not of the file. The sticky bit (1000) changes that: only the file owner, the directory owner or root may delete or rename.

The classic example is /tmp: mode 1777, shown as drwxrwxrwt. Everyone creates files, but nobody deletes someone else's. Sticky matters on directories; on files it has no effect on modern Linux.

The simulator does not enforce the deletion protection; you check that the bit is set and appears as t. You will try the real protection in the VM with alice and bob.

chmod +t

What is it for?
Sets the sticky bit on a directory; t appears in the others x slot.
Where is it used?
On shared, world-writable drop or exchange folders.
Why does it matter?
Stops users from deleting each other's files.
chmod +t inbox

chmod 1777

What is it for?
Sticky + rwxrwxrwx: the same mode as /tmp.
Where is it used?
When creating a folder everyone may drop files into.
Why does it matter?
The standard shared-folder mode in one command.
chmod 1777 drop
💡 Tip

An uppercase T (drwxrwx--T) means sticky is set but others lack x. For a private team folder 1770 can look like this on purpose.

Recipe: team folder and what comes next

A real team folder is built like this: (1) create the folder, (2) set its group to devs, (3) set 2775 (2770 if outsiders must not read), (4) members work with umask 002. Because root creates the folder, you need sudo.

If you also want sticky, use 3775 / 3770: new files belong to the group, and members cannot delete each other's files.

The method has limits: permissions of new files depend on the umask, and you cannot write per-user rules. That is what default ACLs (setfacl -d) are for, a topic of later modules. For now remember that a setgid folder is the foundation of teamwork without ACLs.

sudo mkdir /srv/project

What is it for?
Creates the shared folder under /srv with root privileges.
Where is it used?
When setting up a permanent team workspace.
Why does it matter?
A normal user cannot write to /srv; sudo is required.
sudo mkdir /srv/project

sudo chgrp devs

What is it for?
Sets the folder's group to devs.
Where is it used?
Before giving the team permissions.
Why does it matter?
This is the group setgid will pass on.
sudo chgrp devs team

chmod 2775

What is it for?
Completes the team folder's permissions.
Where is it used?
After setting the group, before opening it for use.
Why does it matter?
The group can write and new files get the group devs.
chmod 2775 team
⚠️ Warning

Group first, then mode: setting 2775 before the group is devs makes the wrong group inherited. At the end ls -ld should show drwxrwsr-x ... devs.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Work on your own Ubuntu/Rocky/Alma VM. The tasks use /srv and the temporary users alice and bob; take a VM snapshot first. The first two tasks are read-only, tasks 3–5 create users and folders on the system, and the last one cleans up. Do them in order (3 → 4 → 5).

See the special bits

Look at the permissions of /tmp and of real setuid programs and paste the output.

ls -ld /tmp
ls -l /usr/bin/passwd /usr/bin/sudo
stat -c '%a %A %n' /tmp /usr/bin/passwd

Expected output example

drwxrwxrwt 15 root root 4096 ... /tmp
-rwsr-xr-x 1 root root ... /usr/bin/passwd
-rwsr-xr-x 1 root root ... /usr/bin/sudo
1777 drwxrwxrwt /tmp
4755 -rwsr-xr-x /usr/bin/passwd
My output looks different
  • If /usr/bin/sudo is missing (No such file), sudo is not installed; no problem, passwd is enough.
  • On some distributions /tmp is mounted separately; the mode should still be 1777.
  • If you see ls: cannot access, find the real path with which passwd.

Find setuid files on the system

List all setuid files and see how many there are.

find / -xdev -perm -4000 -type f 2>/dev/null | head -20
find / -xdev -perm -4000 -type f 2>/dev/null | wc -l

Expected output example

/usr/bin/passwd
/usr/bin/sudo
/usr/bin/mount
...
12
My output looks different
  • The list depends on the distribution; seeing passwd, mount or su is enough.
  • If find is slow, wait; -xdev scans only the main file system, so it is fast.
  • If you see a path you do not recognise, remember it; in a real audit it would be investigated.

Try a setgid folder for real

Create the users and group, make one folder with setgid and one without; alice writes into both, then compare the groups.

# TAKE A SNAPSHOT! Temporary users and /srv folders are created
getent group devs || sudo groupadd devs
sudo useradd -m -G devs alice
sudo useradd -m -G devs bob
sudo mkdir -p /srv/project /srv/plain
sudo chgrp devs /srv/project /srv/plain
sudo chmod 2775 /srv/project
sudo chmod 0775 /srv/plain
sudo -u alice touch /srv/project/a.txt /srv/plain/b.txt
ls -ld /srv/project /srv/plain
ls -l /srv/project /srv/plain

Expected output example

drwxrwsr-x 2 root devs ... /srv/project
drwxrwxr-x 2 root devs ... /srv/plain
/srv/project:
-rw-r--r-- 1 alice devs ... a.txt
/srv/plain:
-rw-r--r-- 1 alice alice ... b.txt
My output looks different
  • If you see useradd: user 'alice' already exists, the user exists; add it to the group with sudo usermod -aG devs alice and continue.
  • The file in /srv/plain should have group alice, the one in /srv/project group devs. If it is the other way round, check the s with ls -ld.
  • If sudo -u alice fails on Rocky/Alma, check that sudo is installed and your user is in wheel.

Deletion protection with the sticky bit

First try, in the sticky folder, to let bob delete alice's file (must fail), then in the folder without sticky (works).

sudo mkdir /srv/pub
sudo chmod 1777 /srv/pub
sudo -u alice touch /srv/pub/alice.txt
sudo -u bob rm -f /srv/pub/alice.txt
ls -l /srv/pub
sudo chmod 777 /srv/pub
sudo -u bob rm -f /srv/pub/alice.txt
ls -l /srv/pub

Expected output example

rm: cannot remove '/srv/pub/alice.txt': Operation not permitted
-rw-r--r-- 1 alice alice ... alice.txt
(after removing sticky) total 0
My output looks different
  • The error message may be translated (Vorgang nicht zulässig, İşleme izin verilmiyor).
  • If the file was deleted on the first try, check the t with ls -ld /srv/pub; was 1777 set?
  • We use rm -f so the 'write-protected' confirmation prompt does not appear.

See setuid safely and clean up

Give setuid to a copy of the harmless id program and see the effect. Then delete all temporary resources.

# ONLY on your own test VM. Never with bash/vim/python!
sudo cp /usr/bin/id /srv/idtest
sudo chmod u+s /srv/idtest
ls -l /srv/idtest
/srv/idtest

Expected output example

-rwsr-xr-x 1 root root ... /srv/idtest
uid=1000(youruser) gid=1000(youruser) euid=0(root) groups=...
# Cleanup
sudo rm -f /srv/idtest
sudo rm -rf /srv/project /srv/plain /srv/pub
sudo userdel -r alice
sudo userdel -r bob
ls /srv

Expected output example

(empty output or only older content)
My output looks different
  • If euid=0(root) is missing, /srv may be mounted nosuid; check with mount | grep nosuid or try /usr/local/bin.
  • userdel may print a mail spool warning; it is harmless.
  • Delete the group devs with sudo groupdel devs only if you created it yourself.

Self-test

Which bit makes new files in a team folder get the folder's group?

setgid on a directory passes the directory's group to new files and subdirectories; 2775 is the typical team mode.

/tmp has mode 1777. What is the leading 1 for?

The sticky bit prevents deleting or renaming other people's files in a world-writable folder.

ls -l shows -rwSr--r--. What does it mean?

An uppercase S means the bit is set but the underlying x permission is missing; usually a misconfiguration.

Which command lists all setuid files on the system?

-perm -4000 finds files with the setuid bit set; 2>/dev/null hides permission errors.

Summary

  • In four-digit modes the leading digit is: setuid 4, setgid 2, sticky 1; they add up.
  • s/t in the x slot, uppercase S/T means x is missing.
  • setuid runs a file with the owner's privileges (passwd); the kernel ignores it on scripts; a wrong setuid-root is a serious vulnerability.
  • setgid folder: new files get the folder's group; team recipe chgrp devs + chmod 2775 + umask 002.
  • Sticky folder (/tmp, 1777): only the owner or root deletes.
  • Audit setuid files regularly with find / -perm -4000 -type f 2>/dev/null.

Key terms

setuid
On executables, the program runs with the owner's privileges; octal 4000.
setgid
On files, run with group privileges; on directories, pass the group to new entries; 2000.
sticky bit
On directories, only the file/directory owner or root may delete; 1000.
privilege escalation
A normal user gaining root-like privileges without permission.
umask
A mask that decides which permission bits are removed from new files.
nosuid
Mount option; setuid/setgid are ignored on that file system.
