5.6 Services and Logs

Manage services with systemd and systemctl, write a simple unit file, and find the cause of problems in the journal and in /var/log.

What will you learn in this module?

  • You check, start, stop and enable services with systemctl and know the difference between start and enable.
  • You know the service names on RHEL/Rocky and Debian/Ubuntu (sshd/ssh, httpd/apache2, firewalld/ufw).
  • You read a unit file ([Unit], [Service], [Install]) and create a custom unit with daemon-reload.
  • You read logs with journalctl and with classic files in /var/log, and you know logrotate and the persistent journal.

systemd and systemctl

systemd is the first process (PID 1) of almost every modern distribution and manages units. The most common types are service (a daemon such as sshd), target (a group of units, like a run level) and timer (a scheduled job, modern cron alternative).

systemctl is the control tool. start runs a service now, enable only makes it start at boot. They are independent: a service can be running but disabled, or enabled but stopped. enable --now does both at once.

reload makes a service re-read its configuration without a restart (not every service supports it); restart stops and starts it. The state commands status, is-active and is-enabled only read and are always safe.

Changing a service needs root, so use sudo. All systemctl commands are real-VM only; the built-in terminal cannot run them, so in the simulator you only write the command down.

systemctl status

What is it for?
Shows state, PID, boot setting and the last log lines of a unit.
Where is it used?
First step with every service problem.
Why does it matter?
One command tells you whether it runs, whether it is enabled and what its last messages were.
systemctl status sshd --no-pager

systemctl start / stop

What is it for?
Starts or stops a service now; the boot setting does not change.
Where is it used?
When testing a service or freeing a port.
Why does it matter?
Immediate effect without a reboot.
sudo systemctl start chronyd

systemctl restart / reload

What is it for?
restart stops and starts the service; reload only re-reads the configuration.
Where is it used?
After editing a config file.
Why does it matter?
reload keeps connections alive; restart is the fallback.
sudo systemctl reload chronyd

systemctl enable / disable

What is it for?
Turns the start at boot on or off; the running state does not change.
Where is it used?
For services that must always be available.
Why does it matter?
After a reboot the service comes up again without you.
sudo systemctl enable chronyd

systemctl enable --now

What is it for?
Enables the service for boot and starts it right away.
Where is it used?
When installing a new service.
Why does it matter?
Two steps in one; the most common form.
sudo systemctl enable --now chronyd

systemctl is-active / is-enabled

What is it for?
Prints only active/inactive or enabled/disabled; the exit code is usable in scripts.
Where is it used?
In scripts and quick checks.
Why does it matter?
Short answer, easy to test.
systemctl is-active sshd && systemctl is-enabled sshd

systemctl list-units --failed

What is it for?
Lists all units that are in failed state.
Where is it used?
After a boot or when something is wrong with the system.
Why does it matter?
A fast overview of what is broken.
systemctl list-units --failed --no-pager

systemctl mask

What is it for?
Links the unit to /dev/null so it cannot be started at all, even by dependencies.
Where is it used?
When a service must never run.
Why does it matter?
Stronger than disable; undo with unmask.
sudo systemctl mask cups.service
💡 Tip

In systemctl status the line Loaded: shows enabled/disabled, the line Active: shows the running state.

⚠️ Warning

Never run stop, disable or mask on a service you do not know. Stopping the wrong service can take a machine offline.

⛔ Danger

Never stop, disable or mask sshd or the network service on a remote VM. You cut your own connection and cannot reconnect. In this module only read ssh/cron/chronyd state.

Service names on different distributions

The same software has different unit names on different families. On RHEL/Rocky/Alma the SSH service is sshd, on Debian/Ubuntu it is ssh (an alias sshd often works too). The web server is httpd on RHEL and apache2 on Debian/Ubuntu. The firewall is firewalld on RHEL and ufw on Ubuntu.

The cron service is crond on RHEL and cron on Debian/Ubuntu; the time service is chronyd (RHEL) or chrony/systemd-timesyncd (Ubuntu). If a name is not found, search with list-unit-files. /etc/os-release tells you which family you are on.

cat /etc/os-release

What is it for?
Shows the distribution name and version.
Where is it used?
Before you use a service or log name.
Why does it matter?
ID and ID_LIKE tell you whether you are on the RHEL or the Debian family.
cat /etc/os-release

systemctl list-units --type=service

What is it for?
Lists the currently loaded services with their state.
Where is it used?
When you want to know what runs on the machine.
Why does it matter?
You see real names instead of guessing.
systemctl list-units --type=service --state=running --no-pager

systemctl list-unit-files

What is it for?
Lists all installed unit files with their boot setting.
Where is it used?
When a name is unknown or a service is not loaded yet.
Why does it matter?
Also finds stopped and disabled services.
systemctl list-unit-files --type=service --no-pager | grep -E 'ssh|cron|chrony'

systemctl list-timers

What is it for?
Lists timer units with next and last run.
Where is it used?
When looking for scheduled jobs of systemd.
Why does it matter?
Timers replace many cron jobs.
systemctl list-timers --no-pager
💡 Tip

Names that are common on one family may not exist on the other. Use ssh or sshd with tab completion: systemctl status ssh<TAB>.

Unit files and a custom service

A service is described in a unit file with three parts. [Unit] has the description and ordering, [Service] says what is run (ExecStart= with the full path) and how (Restart=on-failure restarts it after a crash), [Install] says where it is hooked in when enabled (WantedBy=multi-user.target).

Packages place their units in /usr/lib/systemd/system (on Debian also /lib/systemd/system). Do not edit those. Your own units and overrides go to /etc/systemd/system, which has priority.

After every new or changed unit file run sudo systemctl daemon-reload, so systemd re-reads the files. Without it you get a warning or the old version keeps running. Minimal example:

[Unit] Description=Linux Lab demo — [Service] ExecStart=/usr/bin/sleep 3600 Restart=on-failure — [Install] WantedBy=multi-user.target. The VM exercises build exactly this unit as linux-lab-demo.service and remove it again.

systemctl cat

What is it for?
Prints the unit file including drop-in overrides.
Where is it used?
When you want to see what a service really runs.
Why does it matter?
Shows ExecStart and the file path without searching.
systemctl cat sshd

systemctl edit

What is it for?
Creates a drop-in override in /etc/systemd/system without touching the original.
Where is it used?
When changing a packaged service.
Why does it matter?
Survives package updates; daemon-reload happens automatically.
sudo systemctl edit chronyd

systemd-analyze verify

What is it for?
Checks a unit file for syntax errors.
Where is it used?
Before you start a new unit.
Why does it matter?
Finds typos like Exec_Start or a relative path.
systemd-analyze verify /etc/systemd/system/linux-lab-demo.service

systemd-analyze blame

What is it for?
Lists units by the time they needed during boot.
Where is it used?
When the boot is slow.
Why does it matter?
Shows the slowest units at the top.
systemd-analyze blame --no-pager | head -n 10
💡 Tip

Typical unit errors: ExecStart=sleep 3600 (relative path, needs /usr/bin/sleep), a typo in a key name, a missing [Install] (then enable says there is no installation config).

⚠️ Warning

Do not copy unit files into /usr/lib/systemd/system and do not delete units of the system. Work only with your own linux-lab-demo.service in /etc/systemd/system.

journalctl and the kernel log

systemd collects all messages in the journal. journalctl reads it. Combine filters: -u for a unit, -b for the current boot, -p err for the priority error and worse, --since for time, -n 50 for the last 50 lines, -f to follow live (end with Ctrl+C).

journalctl -xe jumps to the end with extra explanations; it is what systemctl suggests after a failed start. In scripts and when pasting output use --no-pager.

By default the journal may be kept only in memory (/run/log/journal) and is lost at reboot. For a persistent journal create /var/log/journal (or set Storage=persistent in /etc/systemd/journald.conf) and restart journald. On Ubuntu it is persistent already; on many RHEL systems it is not.

journalctl --disk-usage shows how much space the journal uses. dmesg prints the kernel ring buffer (hardware, drivers, disk errors); on some systems it needs sudo.

journalctl -u

What is it for?
Shows the log of one unit.
Where is it used?
When a service does not start or behaves wrongly.
Why does it matter?
Only the messages of this service, not the whole system.
journalctl -u sshd --no-pager

journalctl -f

What is it for?
Follows new log lines live.
Where is it used?
While you restart a service or reproduce an error.
Why does it matter?
You see the reaction immediately; leave with Ctrl+C.
journalctl -u sshd -f

journalctl -b

What is it for?
Shows only the current boot (-b -1 the previous one).
Where is it used?
After a reboot or crash.
Why does it matter?
Cuts out old noise.
journalctl -b --no-pager | tail -n 20

journalctl -p err

What is it for?
Filters by priority: err and everything worse.
Where is it used?
For a quick list of real problems.
Why does it matter?
Hides info and debug messages.
journalctl -p err -b --no-pager

journalctl --since

What is it for?
Shows entries from a point in time (--until for the end).
Where is it used?
When you know roughly when it happened.
Why does it matter?
Keeps output small.
journalctl --since "1 hour ago" --no-pager

journalctl -n 50 --no-pager

What is it for?
Prints the last 50 lines without the pager.
Where is it used?
For quick checks and for pasting into tickets.
Why does it matter?
No scrolling in less, easy to copy.
journalctl -n 50 --no-pager

journalctl -xe

What is it for?
Opens the end of the journal with explanations.
Where is it used?
Right after a failed start.
Why does it matter?
systemd itself suggests it in the error message.
journalctl -xe --no-pager

journalctl --disk-usage

What is it for?
Shows the disk space used by the journal.
Where is it used?
When /var fills up.
Why does it matter?
Read-only and safe.
journalctl --disk-usage

journalctl --vacuum-time

What is it for?
Deletes journal entries older than the given time.
Where is it used?
When the journal uses too much disk space.
Why does it matter?
Frees space, but the old logs are gone for good.
sudo journalctl --vacuum-time=2weeks

dmesg

What is it for?
Prints the kernel messages.
Where is it used?
For disk, USB, network card or memory problems.
Why does it matter?
The kernel reports hardware issues here first.
sudo dmesg | tail -n 20
💡 Tip

Combine filters: journalctl -u sshd -p err --since "1 hour ago" --no-pager.

⚠️ Warning

--vacuum-time and --vacuum-size delete logs permanently. Do not run them on a VM whose logs you still need for an investigation.

Classic log files, rsyslog and logrotate

Besides the journal there are text logs in /var/log, written mostly by rsyslog. The names differ: on RHEL/Rocky /var/log/messages (general) and /var/log/secure (login and sudo); on Debian/Ubuntu /var/log/syslog and /var/log/auth.log. These files are readable only by root or the adm group, so use sudo.

Typical tools: tail -f follows a file, grep -i error searches it, less scrolls through it (/word searches, q quits). Combine them: sudo grep -i error /var/log/messages | tail -n 20.

logrotate keeps logs from growing forever: it renames, compresses and deletes old files by rules in /etc/logrotate.conf and /etc/logrotate.d/. A rule has the log path and options like weekly, rotate 4 (keep 4 old copies), compress, missingok, notifempty. It is started daily by a timer or cron.

The simulator has the files of a RHEL machine, so you can practise reading logs here.

ls /var/log

What is it for?
Lists the log files and folders.
Where is it used?
To find out which logs exist.
Why does it matter?
File names differ by distribution.
ls /var/log

sudo cat /var/log/secure

What is it for?
Reads a log that only root may read (Ubuntu: /var/log/auth.log).
Where is it used?
When you investigate logins and sudo.
Why does it matter?
Shows who logged in and who failed.
sudo cat /var/log/secure

tail -f

What is it for?
Shows the end of a file and follows new lines.
Where is it used?
While a service is running or being tested.
Why does it matter?
Live view; leave with Ctrl+C.
sudo tail -f /var/log/messages

grep -i

What is it for?
Searches lines case-insensitively; -c counts them.
Where is it used?
To find errors in a big log.
Why does it matter?
Reduces thousands of lines to the relevant ones.
grep -i error /var/log/messages

less

What is it for?
Shows a file page by page; /word searches, q quits.
Where is it used?
For long logs.
Why does it matter?
Scrolling without flooding the terminal.
less /var/log/messages

logrotate -d

What is it for?
Debug mode: shows what logrotate would do without doing it.
Where is it used?
After writing a new rule in /etc/logrotate.d.
Why does it matter?
Tests the rule safely.
sudo logrotate -d /etc/logrotate.conf
💡 Tip

To count the errors: grep -ci error /var/log/messages. To see only the last lines of a long search: add | tail -n 5.

⚠️ Warning

Never delete or truncate a log file with rm or > file while a service writes to it; let logrotate do it. Deleting evidence also makes later troubleshooting impossible.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

These tasks run on your own VM. Most are read-only. Task 4 creates a harmless unit that runs sleep 3600. Take a snapshot first and never stop or change sshd or the network service on a remote VM. Use sshd, crond, chronyd on RHEL/Rocky and ssh, cron, chrony on Ubuntu.

Read service state

Check ssh, cron and your time service without changing anything. Paste the output.

# Rocky/RHEL
systemctl status sshd --no-pager
systemctl is-active crond chronyd
systemctl is-enabled sshd
# Ubuntu
systemctl status ssh --no-pager
systemctl is-active cron
systemctl is-enabled ssh

Expected output example

● sshd.service - OpenSSH server daemon
     Loaded: loaded (/usr/lib/systemd/system/sshd.service; enabled; ...)
     Active: active (running) since ...
active
active
enabled
systemctl list-units --failed --no-pager

Expected output example

0 loaded units listed.
My output looks different
  • Unit sshd.service could not be found on Ubuntu: use ssh instead of sshd.
  • If chronyd is not found, your system uses systemd-timesyncd (Ubuntu); try systemctl status systemd-timesyncd.
  • Failed units in the list are not an error of this exercise; just note them.

Read the journal

Read the journal with filters and check how much space it uses. Paste the output.

journalctl -b -n 10 --no-pager
journalctl -p err -b --no-pager | tail -n 5
journalctl --since "1 hour ago" --no-pager | wc -l
journalctl --disk-usage

Expected output example

... linux-lab systemd[1]: Started ...
1234
Archived and active journals take up 48.0M in the file system.
My output looks different
  • Permission denied or a hint about the systemd-journal group: run the commands with sudo.
  • -- No entries -- for -p err is good news: there were no errors.
  • If the journal only has the current boot, it is not persistent yet (see ls /var/log/journal).

Classic logs and dmesg

Read the end of the general and the login log, then the kernel log. Use the file names of your family.

# Rocky/RHEL
sudo tail -n 5 /var/log/messages
sudo tail -n 5 /var/log/secure
# Ubuntu
sudo tail -n 5 /var/log/syslog
sudo tail -n 5 /var/log/auth.log
# both
sudo dmesg | tail -n 5
ls /etc/logrotate.d

Expected output example

Nov 12 10:01:02 linux-lab systemd[1]: ...
Nov 12 10:02:11 linux-lab sudo[2101]: student : TTY=pts/0 ; ...
[ 12.345678] ...
My output looks different
  • No such file or directory for syslog/messages: the other family's file name, or rsyslog is not installed. The journal has the same data.
  • On Ubuntu, dmesg without sudo may be blocked; use sudo dmesg.

Create your own service

Create linux-lab-demo.service, load it, start it and look at its state and log. Snapshot first. The unit only runs sleep 3600.

sudo tee /etc/systemd/system/linux-lab-demo.service > /dev/null <<'EOF'
[Unit]
Description=Linux Lab demo

[Service]
ExecStart=/usr/bin/sleep 3600
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl start linux-lab-demo.service
systemctl status linux-lab-demo.service --no-pager
systemctl is-enabled linux-lab-demo.service
journalctl -u linux-lab-demo.service -n 5 --no-pager

Expected output example

● linux-lab-demo.service - Linux Lab demo
     Loaded: loaded (/etc/systemd/system/linux-lab-demo.service; disabled; ...)
     Active: active (running) since ...
disabled
... systemd[1]: Started Linux Lab demo.
My output looks different
  • Failed to start ... No such file or directory: check the path with which sleep; on some systems it is /bin/sleep.
  • is-enabled says disabled because you used start only; that is the difference between start and enable.
  • If sudo is missing the heredoc, copy the file in two steps: write it in your home and sudo cp it to /etc/systemd/system/.

Remove your service again

Stop and remove only linux-lab-demo.service, then check that systemd no longer knows it. Do not touch any other unit.

sudo systemctl stop linux-lab-demo.service
sudo rm /etc/systemd/system/linux-lab-demo.service
sudo systemctl daemon-reload
systemctl status linux-lab-demo.service --no-pager

Expected output example

Unit linux-lab-demo.service could not be found.
My output looks different
  • If you also ran enable, run sudo systemctl disable linux-lab-demo.service before the rm.
  • Unit ... not found or inactive (dead) both mean the service is gone or not running.
  • Check the file name in rm twice: it must be exactly the demo file.

Self-test

What is the difference between systemctl start and systemctl enable?

start acts now, enable only changes the boot setting. enable --now does both.

Which pair is the web server service on (RHEL, Ubuntu)?

RHEL/Rocky use httpd, Debian/Ubuntu use apache2. The same applies to sshd/ssh and firewalld/ufw.

Which command shows only errors of the current boot?

-b limits to the current boot, -p err to priority error and worse.

You created /etc/systemd/system/linux-lab-demo.service. What do you do first?

daemon-reload makes systemd read the new or changed unit file.

Summary

  • start/stop act now, enable/disable act at boot, enable --now does both.
  • Names differ: sshd/ssh, httpd/apache2, firewalld/ufw, crond/cron; check with /etc/os-release.
  • A unit has [Unit], [Service] (ExecStart with full path, Restart=), [Install]; own units go to /etc/systemd/system followed by daemon-reload.
  • journalctl -u, -b, -p err, --since, -n 50 --no-pager, -f, -xe find the cause; --disk-usage shows the size.
  • Classic logs: RHEL messages/secure, Debian/Ubuntu syslog/auth.log; logrotate rotates them by /etc/logrotate.d rules.
  • Never stop sshd on a remote VM; never delete or vacuum logs you still need.

Key terms

systemd
The init system (PID 1) that starts and supervises services.
unit
An object managed by systemd: service, target, timer, mount and more.
target
A group of units that describes a system state, e.g. multi-user.target.
timer
A unit that starts another unit on a schedule; alternative to cron.
daemon-reload
Makes systemd re-read unit files after you changed them.
mask
Links a unit to /dev/null so that it cannot be started.
journal
systemd's binary log database, read with journalctl.
rsyslog
The classic syslog daemon that writes text logs to /var/log.
logrotate
Tool that rotates, compresses and deletes old log files by rules.
