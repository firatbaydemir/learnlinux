5.1 Process Basics

Look at the running system with a microscope: what a process is, who started it and what state it is in.

What will you learn in this module?

  • You explain what a process is, what PID and PPID mean and why PID 1 is special.
  • You list processes with ps aux, ps -ef and ps -o, and find them with pgrep.
  • You show parent/child relations with pstree and ps --forest and look into /proc/<pid>.
  • You recognise process states (R, S, D, T, Z) and know what a zombie is and what it is not.

What is a process?

A program on disk (for example bash) is just a file. When you start it, the kernel loads it into memory and it becomes a process. Hundreds of processes run at the same time.

Every process has a unique number, the PID. It also knows who started it: the PPID (parent PID). Processes give birth to each other: your shell starts ps, ps is the child of the shell. At the top is PID 1, the first process of the system, today usually systemd. All others descend from it.

The shell knows its own PID: $$. In the simulator it always prints 4242.

echo $$

What is it for?
Prints the PID of the current shell.
Where is it used?
In scripts and when you need your own PID, e.g. for /proc/$$.
Why does it matter?
You can inspect your own process without searching for it.
echo $$

ps

What is it for?
Lists only the processes of your current terminal.
Where is it used?
For a quick look: normally just bash and ps itself.
Why does it matter?
The smallest snapshot; shows PID, terminal, CPU time and command.
ps
💡 Tip

ps is a snapshot, not a live view. For a live view you use top (next modules).

Reading with ps

ps exists in two styles. ps aux is BSD style (no dash): all users, with %CPU and %MEM. ps -ef is UNIX style (with dash): all processes with a PPID column. ps aux has no PPID column; for relations use ps -ef or -o.

With -o you choose the columns yourself: ps -o pid,ppid,stat,cmd. This is the cleanest way for scripts and the best way to read exactly what you need.

On Rocky/Alma/Ubuntu ps is already installed (package procps / procps-ng).

ps aux

What is it for?
All processes of all users, with user, %CPU, %MEM, state and command.
Where is it used?
When you ask who is using the system and how much.
Why does it matter?
Most common overview; combine with grep or sort.
ps aux | head -n 10

ps -ef

What is it for?
All processes in UNIX format, including the PPID column.
Where is it used?
When you want to know who the parent is.
Why does it matter?
Shows relations; PPID 1 means the process hangs directly under init/systemd.
ps -ef | head -n 10

ps -o

What is it for?
Shows exactly the columns you list.
Where is it used?
In scripts and for focused questions.
Why does it matter?
Short, readable and stable output.
ps -o pid,ppid,stat,comm

ps -p

What is it for?
Shows only the process with the given PID.
Where is it used?
When you know the PID and want to check it.
Why does it matter?
No grep needed; combine with -o.
ps -o pid,ppid,stat,cmd -p $$
💡 Tip

ps aux | grep sshd also finds the grep process itself. pgrep avoids that.

⚠️ Warning

Never rely on column positions in ps aux for the COMMAND field: it contains spaces. Use ps -o in scripts.

Trees and searching: pstree and pgrep

pstree draws the family tree: systemd at the root, then services, your SSH session, your shell and your commands. ps -ef --forest shows the same with a PPID column.

pgrep searches by name and prints only PIDs. It is made for scripts: pgrep -x sshd prints the PID if sshd runs and exits with 1 if not.

pstree comes from the package psmisc, which is not always installed. Rocky/Alma: sudo dnf install psmisc. Debian/Ubuntu: sudo apt install psmisc. pgrep belongs to procps and is always there.

pstree -p

What is it for?
Shows the process tree with PIDs.
Where is it used?
To understand who started whom.
Why does it matter?
At a glance: everything hangs under PID 1 (systemd).
pstree -p | head -n 15

ps -ef --forest

What is it for?
The ps list in tree form with PPID.
Where is it used?
When psmisc is not installed.
Why does it matter?
A tree plus all columns of ps -ef.
ps -ef --forest | head -n 20

pgrep -l

What is it for?
Finds processes by name and prints PID and name.
Where is it used?
In scripts, to check whether a service runs.
Why does it matter?
Cleaner than ps | grep; -x matches the exact name.
pgrep -l sshd

pgrep -a

What is it for?
Prints PID and the complete command line.
Where is it used?
When several processes have the same name.
Why does it matter?
You see the arguments and can pick the right PID.
pgrep -a bash
💡 Tip

Package install: Rocky sudo dnf install psmisc, Ubuntu sudo apt install psmisc.

Inside /proc/<pid>

/proc is a virtual filesystem: it does not live on disk, the kernel generates it. Every process has a directory /proc/<pid>/. That is the source ps itself reads from.

Useful files: status (name, state, PID, PPID, UID), exe (link to the program), cwd (working directory), fd/ (open files), cmdline (the command line). As a normal user you can read your own processes; for others some files are restricted.

/proc/self always means the process that reads it. So cat /proc/self/status shows the status of cat.

cat /proc/$$/status

What is it for?
Shows name, state, PID, PPID and UID of your shell.
Where is it used?
For details that ps does not show.
Why does it matter?
The raw source: State and PPid lines tell the story.
head -n 9 /proc/$$/status

ls -l /proc/$$/exe

What is it for?
A link to the executable of the process.
Where is it used?
When you ask which binary really runs.
Why does it matter?
Uncovers renamed or deleted programs.
ls -l /proc/$$/exe

ls /proc/$$/fd

What is it for?
Lists the open file descriptors (0, 1, 2 ...).
Where is it used?
When debugging open files.
Why does it matter?
0 = stdin, 1 = stdout, 2 = stderr; more means open files.
ls -l /proc/$$/fd
💡 Tip

cat /proc/self/status is a quick test that /proc works, also in WSL.

States, zombies and signals

The STAT column shows the state: R running, S sleeping (waiting, interruptible), D uninterruptible sleep (usually waiting for disk/network; cannot be killed), T stopped (Ctrl+Z), Z zombie. Extra letters: s session leader, + foreground, < high priority.

A zombie is a process that has already finished. Only its entry in the process table remains, because the parent has not yet read the exit status (wait). A zombie uses no CPU and almost no memory, and you cannot kill it, not even with kill -9, because it is already dead. The fix: the parent must collect it, or you stop/restart the parent; then init adopts and reaps the orphan.

Signals: kill sends a signal, default SIGTERM (15, polite request, the program can clean up). SIGKILL (9) cannot be caught; the kernel ends the process immediately without cleanup. PID 1 is special: signals without a handler are ignored for it, even SIGKILL from user space. That protects the system from an accidental kill.

Load average (uptime) shows runnable processes over 1/5/15 minutes. Read it relative to the number of cores (nproc): load 4.0 is full on 4 cores and overload on 2.

ps -eo pid,ppid,stat,cmd

What is it for?
All processes with state and parent.
Where is it used?
When looking for zombies (STAT Z) or stuck processes (D).
Why does it matter?
Pipe to grep or sort for a quick filter.
ps -eo pid,ppid,stat,cmd | head -n 10

uptime

What is it for?
Shows uptime and the load average of 1, 5 and 15 minutes.
Where is it used?
As the first look at 'is the server slow?'.
Why does it matter?
Compare the load with the number of cores.
uptime

nproc

What is it for?
Prints the number of CPU cores.
Where is it used?
To read the load average correctly.
Why does it matter?
Load 2.0 is fine on 8 cores and busy on 2.
nproc

kill -15

What is it for?
Sends SIGTERM (polite stop) to a PID.
Where is it used?
First choice to end a process.
Why does it matter?
The program can save data and clean up.
kill -15 4242

kill -9

What is it for?
Sends SIGKILL; the process is ended immediately.
Where is it used?
Only if SIGTERM did not work.
Why does it matter?
Last resort; no cleanup, data can be lost.
kill -9 4242
💡 Tip

Order for stopping: kill -15, wait a few seconds, check with ps -p PID, and only then kill -9.

⚠️ Warning

Check the PID twice before you kill. pkill name and killall name kill all processes with that name, including ones you did not mean.

⛔ Danger

Do not kill processes you do not know, especially not as root: kill -9 on sshd, systemd-journald or a database can lock you out or corrupt data. Practise only with your own sleep processes.

Do it on your own VM

The real practice happens on real Linux: run the commands in your own virtual machine (VirtualBox, UTM or WSL) and compare the output.

Run these steps on your own VM (Ubuntu, Rocky, Alma or WSL). Steps 1 to 4 only read. Step 5 stops a process: take a snapshot first and only touch your own sleep process.

Your own process

Print the PID of your shell, then show its PID, PPID and state with ps. Paste the output.

echo $$
ps -o pid,ppid,stat,cmd -p $$

Expected output example

2100
    PID    PPID STAT CMD
   2100    2050 Ss   -bash
My output looks different
  • The numbers differ on your system; PPID must be in the header.
  • In a terminal started via SSH the parent is sshd, in a desktop terminal it is the terminal program.

ps aux and ps -ef

Compare both styles. Which one has a PPID column?

ps aux | head -n 5
ps -ef | head -n 5

Expected output example

USER  PID %CPU %MEM ... COMMAND
root    1  0.0  0.3 ... /usr/lib/systemd/systemd
UID   PID  PPID  C STIME TTY TIME CMD
root    1     0  0 08:00 ?   00:00:02 /usr/lib/systemd/systemd
My output looks different
  • On WSL1 or in a container PID 1 may be init or something else.
  • Only ps -ef has PPID; ps aux has %CPU and %MEM.

Process tree

Install psmisc if needed and look at the tree. Who is at the root? Paste the first lines.

# Rocky/Alma: sudo dnf install -y psmisc
# Ubuntu/Debian: sudo apt install -y psmisc
pstree -p | head -n 8
ps -ef --forest | head -n 15

Expected output example

systemd(1)-+-sshd(412)---sshd(2050)---sshd(2090)---bash(2100)-+-pstree(2200)
           |-crond(650)
...
My output looks different
  • pstree: command not found means psmisc is not installed; use the install line above.
  • On WSL you may see init(1) or SessionLeader instead of systemd.

Look into /proc

Read the status of your shell directly from /proc and show where the program lives.

head -n 9 /proc/$$/status
ls -l /proc/$$/exe
ls -l /proc/$$/fd

Expected output example

Name:	bash
Umask:	0022
State:	S (sleeping)
...
PPid:	2050
...
lrwxrwxrwx 1 student student 0 ... /proc/2100/exe -> /usr/bin/bash
My output looks different
  • The Name:, State: and PPid: lines must exist; the order of other lines can differ.
  • exe may show /bin/bash on some systems (a link to /usr/bin).

Start and stop a process safely

Snapshot first. Start your own sleep in the background, find it with pgrep, stop it politely with SIGTERM and check that it is gone. Never use pkill or kill -9 on unknown processes.

sleep 600 &
pgrep -l sleep
kill -15 $!
sleep 1
pgrep -l sleep || echo gone

Expected output example

[1] 2300
2300 sleep
[1]+  Terminated   sleep 600
gone
My output looks different
  • $! is the PID of the last background process.
  • If pgrep still prints a line, another sleep is running; check with pgrep -a sleep before you kill anything.

Self-test

Which PID has the first process of a Linux system (today usually systemd)?

PID 1 is started by the kernel; all other processes descend from it. It also ignores signals it has no handler for, even SIGKILL from user space.

What is true for a zombie process (STAT Z)?

A zombie is already dead; only its table entry remains. The parent must call wait, or you restart the parent.

What does $$ mean in the shell?

$$ is the shell's own PID. The last background PID is $!, the exit code is $?.

Which command shows a PPID column by default?

ps -ef (UNIX style) shows PPID. ps aux (BSD style) does not; for it use ps -o pid,ppid,....

Summary

  • A process is a running program with a PID; its parent has the PPID; PID 1 (systemd) is the ancestor of all.
  • ps aux (BSD) shows CPU/MEM, ps -ef shows PPID, ps -o chooses columns, pgrep finds by name.
  • pstree (package psmisc) and ps -ef --forest show the tree; /proc/<pid> is where the kernel exposes the details.
  • A zombie (Z) is dead and cannot be killed; fix the parent. Use kill -15 first, kill -9 last, never on unknown processes.
  • Read the load average relative to nproc.

Key terms

process
A running instance of a program with its own PID and memory.
PID / PPID
Process ID and the ID of its parent process.
zombie
A finished process whose exit status has not yet been collected by its parent (STAT Z).
signal
A message to a process, e.g. SIGTERM (15) or SIGKILL (9).
/proc
Virtual filesystem through which the kernel exposes process and system information.
load average
Average number of runnable processes over 1, 5 and 15 minutes; read it relative to the CPU cores.
