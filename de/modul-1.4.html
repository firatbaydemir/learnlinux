1.4 Befehlserfolg: $?, &&, || und Fehlermeldungen

Keine Ausgabe bedeutet nicht Fehler. Jeder Befehl hinterlässt einen Exit-Status; in diesem Modul lernst du, ihn zu lesen, Befehle darauf aufbauend zu verketten und Fehlermeldungen zu verstehen.

Was lernst du in diesem Modul?

  • Du liest den Exit-Status des letzten Befehls mit echo $? und unterscheidest 0 von ungleich 0.
  • Du verkettest Befehle bedingt mit true, false, &&, || und ;.
  • Du kennst den Unterschied zwischen stdout und stderr und trennst Fehler mit 2>.
  • Du liest Permission denied, No such file or directory und command not found und findest die Ursache.
  • Du prüfst Dateien, Zahlen und Zeichenketten mit test und [ ].

Exit-Status: $?

Wenn ein Befehl endet, erzeugt er einen Exit-Status. 0 = Erfolg, jede andere Zahl = Fehler. Ein stiller Befehl (z. B. mkdir) kann erfolgreich oder fehlgeschlagen sein; um sicher zu sein, tippe echo $?.

Häufige Codes: 1 allgemeiner Fehler, 2 falsche Verwendung oder fehlender Pfad (ls), 126 nicht ausführbar, 127 Befehl nicht gefunden, 130 mit Strg+C abgebrochen.

Achtung: $? wird nach jedem Befehl überschrieben. Ein direkt danach getipptes echo $? hinterlässt sein eigenes Ergebnis (0); lies den Code unmittelbar nach dem betreffenden Befehl.

echo $?

Wozu dient es?
Gibt den Exit-Status des letzten Befehls aus.
Wo wird es verwendet?
Beim Prüfen von Befehlen ohne Ausgabe.
Warum ist es wichtig?
Zeigt mit einer Zahl, ob der Befehl wirklich funktioniert hat.
pwd; echo $?

true

Wozu dient es?
Tut nichts und endet immer mit 0.
Wo wird es verwendet?
Beim Testen von Ketten, wenn ein „erfolgreicher“ Befehl nötig ist.
Warum ist es wichtig?
Erzeugt den Erfolgszustand mühelos.
true; echo $?

false

Wozu dient es?
Tut nichts und endet immer mit 1.
Wo wird es verwendet?
Beim Ausprobieren des Fehlerpfads.
Warum ist es wichtig?
Erzeugt den Fehlerzustand mühelos.
false; echo $?
💡 Tipp

Keine Ausgabe ist kein Fehler. Die meisten Unix-Befehle schweigen bei Erfolg.

Verketten: &&, || und ;

A && B: B läuft nur, wenn A erfolgreich war (0). A || B: B läuft nur, wenn A fehlgeschlagen ist. A ; B: B läuft in jedem Fall.

Das klassische Muster: mkdir lab && cd lab (wechsle in den Ordner, wenn er angelegt wurde). A && B || C verhält sich wie ein if/else; schlägt aber B fehl, läuft auch C – nutze es nur für einfache Fälle.

&&

Wozu dient es?
Führt die rechte Seite aus, wenn die linke erfolgreich war.
Wo wird es verwendet?
Bei Schritten, die voneinander abhängen.
Warum ist es wichtig?
Verhindert das Weitermachen nach einem fehlgeschlagenen Schritt.
mkdir lab && cd lab

||

Wozu dient es?
Führt die rechte Seite aus, wenn die linke fehlgeschlagen ist.
Wo wird es verwendet?
Für Fehlermeldungen oder Ersatzpläne.
Warum ist es wichtig?
Reagiert automatisch auf Fehler.
cd /nonexistent || echo failed

;

Wozu dient es?
Führt Befehle der Reihe nach aus, unabhängig vom Erfolg.
Wo wird es verwendet?
Wenn du unabhängige Befehle in eine Zeile schreibst.
Warum ist es wichtig?
Die Reihenfolge bleibt, das Ergebnis wird ignoriert.
pwd; whoami; hostname
⚠️ Achtung

Bei Ketten wie rm -r old_project ; ... läuft der zerstörerische Befehl mit ; auch dann, wenn der vorherige Schritt fehlschlug. Verbinde zerstörerische Schritte mit &&.

stdout und stderr

Jeder Befehl hat zwei Ausgabekanäle: stdout (Kanal 1, normale Ausgabe) und stderr (Kanal 2, Fehlermeldungen). Beide erscheinen auf dem Bildschirm, lassen sich aber getrennt umleiten.

> leitet nur stdout in eine Datei; der Fehler bleibt auf dem Bildschirm. 2> leitet Fehler in eine Datei. 2>/dev/null wirft Fehler weg. 2>&1 schickt stderr dorthin, wohin stdout geht. Beachte: Umleitung ändert den Exit-Status nicht; auch wenn der Fehler versteckt ist, ist der Befehl fehlgeschlagen.

2>

Wozu dient es?
Schreibt Fehlermeldungen (stderr) in eine Datei.
Wo wird es verwendet?
Um Fehler später zu untersuchen.
Warum ist es wichtig?
Trennt normale Ausgabe von Fehlern.
ls /nonexistent 2> errors.txt

2>/dev/null

Wozu dient es?
Verwirft Fehlermeldungen.
Wo wird es verwendet?
Um erwartete, harmlose Fehler zu unterdrücken.
Warum ist es wichtig?
Hält die Ausgabe sauber, versteckt aber auch echte Probleme.
ls /nonexistent 2>/dev/null; echo $?

2>&1

Wozu dient es?
Leitet stderr an denselben Ort wie stdout.
Wo wird es verwendet?
Um Ausgabe und Fehler in einer Datei oder Pipeline zu sammeln.
Warum ist es wichtig?
Hält das vollständige Protokoll an einem Ort.
ls ~ /nonexistent > all.txt 2>&1

Fehlermeldungen lesen

Eine Fehlermeldung hat meist die Form Programm: Argument: Grund. Das erste Wort ist das Programm, das scheiterte, das zweite der problematische Pfad, das letzte der Grund.

No such file or directory: Der Pfad existiert nicht oder hat einen Tippfehler; prüfe mit ls und pwd, wo du bist. Permission denied: Der Pfad existiert, aber dir fehlt die Berechtigung; schau dir ls -l an. command not found (Code 127): falscher Befehlsname oder nicht installiert; prüfe mit type / which. Is a directory: Du hast einem Befehl, der eine Datei erwartet, einen Ordner gegeben.

ls -l

Wozu dient es?
Zeigt Dateirechte und Besitzer.
Wo wird es verwendet?
Bei der Suche nach der Ursache von Permission denied.
Warum ist es wichtig?
Du siehst, welche Berechtigung fehlt.
ls -l locked.txt

type

Wozu dient es?
Sagt, ob ein Name Befehl, Builtin oder Alias ist.
Wo wird es verwendet?
Bei command not found.
Warum ist es wichtig?
Zeigt, ob der Befehl existiert.
type ls
⛔ Gefahr

Tippe bei Permission denied nicht reflexartig sudo oder chmod 777. Verstehe zuerst die Ursache; unnötig weite Rechte sind eine Sicherheitslücke.

Bedingungen prüfen: test und [ ]

test (und das Gleiche als [ ... ]) prüft eine Bedingung und gibt nichts aus; das Ergebnis meldet es nur über den Exit-Status: 0 bei wahr, 1 bei falsch. Darum passt es so gut zu && / ||.

Häufig: -f normale Datei, -d Verzeichnis, -e existiert, -r/-w/-x lesbar/schreibbar/ausführbar, -z Zeichenkette leer. Für Zahlen -eq -ne -gt -lt, für Text = und !=. In [ ] sind die Leerzeichen neben den Klammern Pflicht.

test -f

Wozu dient es?
Erfolgreich, wenn der Pfad existiert und eine normale Datei ist.
Wo wird es verwendet?
Beim Prüfen, ob eine Datei existiert.
Warum ist es wichtig?
Du führst keinen Befehl auf einer fehlenden Datei aus und bekommst keinen Fehler.
test -f notes.txt && echo yes

[ -d ]

Wozu dient es?
Erfolgreich, wenn der Pfad ein Verzeichnis ist.
Wo wird es verwendet?
Z. B. um einen Ordner nur anzulegen, wenn er fehlt.
Warum ist es wichtig?
Ermöglicht bedingtes Handeln.
[ -d Documents ] && echo dir

[ -gt ]

Wozu dient es?
Vergleicht Zahlen (-eq -ne -gt -lt).
Wo wird es verwendet?
Bei numerischen Prüfungen.
Warum ist es wichtig?
Macht numerische Bedingungen zum Exit-Status.
[ 3 -gt 2 ] && echo gt
💡 Tipp

Klassisches Muster: test -d backup || mkdir backup. Es legt den Ordner an, falls er fehlt, und lässt ihn sonst in Ruhe.

Mach es in deiner VM

Die eigentliche Praxis findet auf echtem Linux statt: Führe die Befehle in deiner eigenen virtuellen Maschine (VirtualBox, UTM oder WSL) aus und vergleiche die Ausgabe.

Führe die folgenden Befehle auf deiner eigenen VM (Ubuntu/Rocky/Alma oder WSL) aus; wir nutzen nur sichere, lesende Befehle. Füge die Ausgabe ein und prüfe sie.

Erfolgs- und Fehlercode

Führe einen erfolgreichen und einen fehlschlagenden Befehl aus und lies jeweils danach den Code. Füge die gesamte Ausgabe ein.

ls /
echo $?
ls /nonexistent
echo $?

Beispiel der erwarteten Ausgabe

bin  boot  dev  etc ...
0
ls: cannot access '/nonexistent': No such file or directory
2
Meine Ausgabe sieht anders aus
  • Ein fehlgeschlagenes ls liefert 2 (GNU ls); andere Befehle liefern evtl. 1. Das ist in Ordnung, wichtig ist, dass es nicht 0 ist.
  • Ist die Meldung lokalisiert, kann sie in einer anderen Sprache erscheinen; der Code bleibt gleich.

command not found: 127

Führe einen nicht existierenden Befehl aus und lies den Exit-Status.

nonexistentcmd
echo $?

Beispiel der erwarteten Ausgabe

bash: nonexistentcmd: command not found
127
Meine Ausgabe sieht anders aus
  • Ubuntu schlägt bei „Command not found“ manchmal ein Paket vor; der Code ist trotzdem 127.
  • Wenn du echo $? zweimal tippst, ist das zweite Ergebnis 0; lies es nur direkt nach dem ersten Befehl.

Verhalten von && und ||

Probiere die Ketten aus und sieh, welche Seite läuft.

true && echo ok
false && echo never
false || echo fallback
true ; echo always

Beispiel der erwarteten Ausgabe

ok
fallback
always
Meine Ausgabe sieht anders aus
  • Erscheint never, hast du evtl. ; statt && getippt.
  • Wird nichts ausgegeben, suche nach einem Anführungszeichen- oder Leerzeichenfehler.

Permission denied

Öffne als normaler Benutzer eine Datei, die du nicht lesen darfst, und füge Fehler und Status ein (nur lesend, nichts ändert sich).

cat /etc/shadow
echo $?

Beispiel der erwarteten Ausgabe

cat: /etc/shadow: Permission denied
1
Meine Ausgabe sieht anders aus
  • Bist du root, wird die Datei geöffnet; wechsle zu einem normalen Benutzer (su - student oder ein neuer Benutzer).
  • Auf älteren Systemen kannst du statt /etc/shadow /etc/sudoers versuchen.

Bedingungen mit test

Prüfe Datei- und Verzeichnisbedingungen. Füge das Ergebnis als yes / no ein.

test -d /etc && echo yes || echo no
test -f /etc/nonexistent && echo yes || echo no

Beispiel der erwarteten Ausgabe

yes
no
Meine Ausgabe sieht anders aus
  • Erscheint zweimal yes, hast du evtl. -e statt -f getippt.
  • Bei [ -d /etc ] die Leerzeichen um [ und ] nicht vergessen.

Schnelle Übungen (Simulator)

Optional: Zum Aufwärmen vor der VM oder als Ersatz ohne VM nutzt du das virtuelle Terminal im Browser. Aufgaben werden automatisch geprüft.

Die Aufgaben steigen vom Aufwärmen bis zum Ticket an. Die Abzeichen zeigen den Schwierigkeitsgrad.

Aufwärmen

  1. AufwärmenLeicht

    Führe zuerst pwd aus und lies den Exit-Status sofort danach mit echo $?.

    Hinweis

    Tippe zwei getrennte Zeilen; der Code sollte 0 sein.

    Lösung
    pwd
echo $?

  2. AufwärmenLeicht

    Liste einen nicht existierenden Pfad auf: ls /nonexistent, und lies die Fehlermeldung.

    Hinweis

    Der Fehler geht nach stderr; er erscheint trotzdem auf dem Bildschirm.

    Lösung
    ls /nonexistent

  3. AufwärmenLeicht

    Führe false aus und lies den Status mit echo $?. Welche Zahl bekommst du?

    Hinweis

    false schlägt immer fehl.

    Lösung
    false
echo $?

Geführtes Lab

  1. Geführtes LabMittel

    Schreibe in einer Zeile mkdir lab && cd lab, um den Ordner anzulegen und zu betreten.

    Hinweis

    && führt den zweiten Befehl nur aus, wenn der erste erfolgreich war.

    Lösung
    mkdir lab && cd lab
cd ~

  2. Geführtes LabMittel

    Tippe cd /nonexistent || echo failed und überlege, warum failed ausgegeben wird.

    Hinweis

    Wenn cd fehlschlägt, führt || die rechte Seite aus.

    Lösung
    cd /nonexistent || echo failed

Vorhersagen

  1. VorhersagenMittel

    Vorhersage: Was gibt cat missing.txt; echo $? aus und welcher Code erscheint? Führe es dann zur Kontrolle aus.

    Hinweis

    cat gibt einen Fehler aus, wenn es die Datei nicht findet, und endet mit 1.

    Lösung
    cat missing.txt; echo $?

  2. VorhersagenMittel

    Vorhersage: Was gibt test -f notes.txt && echo yes || echo no aus? Führe es zur Kontrolle aus.

    Hinweis

    notes.txt existiert im Home und ist eine normale Datei.

    Lösung
    test -f notes.txt && echo yes || echo no

Fehler finden

  1. Fehler findenMittel

    cat locked.txt meldet „Permission denied“. Finde den Grund, behebe ihn mit chmod und lies die Datei.

    Hinweis

    Gib dir selbst Leserecht: chmod u+r locked.txt.

    Lösung
    chmod u+r locked.txt
cat locked.txt

  2. Fehler findenMittel

    cp notes.txt backup/ schlägt fehl, weil backup nicht existiert. Verkette: Ordner anlegen und Datei kopieren.

    Hinweis

    mkdir backup && cp notes.txt backup/.

    Lösung
    mkdir backup && cp notes.txt backup/

Mini-Projekt

  1. Mini-ProjektSchwer

    Mini-Projekt: (1) Schreibe den Fehler von ls /nonexistent in errors.txt, (2) schreibe die Ausgabe von ls ~ in files.txt, (3) lies den Status des letzten Befehls mit echo $?.

    Hinweis

    Nutze 2> für den Fehler und > für die Ausgabe.

    Lösung
    ls /nonexistent 2> errors.txt
ls ~ > files.txt
echo $?

  2. Mini-ProjektMittel

    Mini-Projekt: Lege in einer Zeile den Ordner project an, wechsle hinein, erstelle die Datei main.txt und gib zum Schluss built aus.

    Hinweis

    Verbinde vier Befehle mit &&; du kannst mkdir -p project nutzen.

    Lösung
    mkdir -p project && cd project && touch main.txt && echo built
cd ~

Herausforderung

  1. HerausforderungSchwer

    Herausforderung: Lege den Ordner backup an, falls er fehlt; kopiere notes.txt hinein; war das Kopieren erfolgreich, schreibe saved in status.txt, sonst failed.

    Hinweis

    test -d backup || mkdir backup und cp ... && echo saved > status.txt || echo failed > status.txt.

    Lösung
    test -d backup || mkdir backup
cp notes.txt backup/ && echo saved > status.txt || echo failed > status.txt

  2. HerausforderungSchwer

    Herausforderung: Enthält notes.txt das Wort hello? Prüfe es in einer Zeile und gib found oder missing aus; wirf die eigene Ausgabe von grep nach /dev/null.

    Hinweis

    grep hello notes.txt > /dev/null && echo found || echo missing.

    Lösung
    grep hello notes.txt > /dev/null && echo found || echo missing

Ticket

  1. TicketSchwer

    Ticket: Ein Kollege sagt „Ich kann meinen Bericht nicht lesen“ und hat cat Documents/raport.txt versucht. Finde den richtigen Namen mit ls Documents, lies die Datei mit cat und schreibe den Exit-Status in exit.txt.

    Hinweis

    Der richtige Name ist report.txt. cat Documents/report.txt; echo $? > exit.txt.

    Lösung
    ls Documents
cat Documents/report.txt; echo $? > exit.txt

Selbsttest

Welchen Exit-Status hat ein erfolgreich beendeter Befehl?

0 bedeutet Erfolg; jeder Wert ungleich 0 zeigt einen Fehler an.

Wann läuft B in der Zeile A && B?

&& verhält sich wie UND; B läuft nur, wenn A mit 0 endet.

Was zeigt der Exit-Status 127 an?

127 = command not found. Ein Rechteproblem ist 126, Strg+C ist 130.

Was bewirkt ls /nonexistent 2>/dev/null; echo $??

2>/dev/null verwirft nur die Meldung; der Befehl ist trotzdem fehlgeschlagen und $? ist nicht 0.

Zusammenfassung

  • Exit-Status: 0 ist Erfolg, alles andere ist ein Fehler. Lies ihn sofort mit echo $?.
  • && macht bei Erfolg weiter, || bei Fehler, ; in jedem Fall.
  • stdout wird mit >, stderr mit 2> umgeleitet; Umleitung ändert den Exit-Status nicht.
  • Fehlermeldung: Programm, Pfad, Grund. 127 = Befehl fehlt, Permission denied = keine Berechtigung.
  • test und [ ] machen Bedingungen zum Exit-Status.

Fachbegriffe

Exit-Status
Die Zahl, die ein Befehl beim Beenden hinterlässt; 0 = Erfolg.
stdout
Standardausgabe (Kanal 1); normale Ergebnisse.
stderr
Standardfehlerausgabe (Kanal 2); Fehlermeldungen.
&&
Operator, der die rechte Seite ausführt, wenn die linke erfolgreich war.
||
Operator, der die rechte Seite ausführt, wenn die linke fehlgeschlagen ist.
/dev/null
Eine Spezialdatei, die alles Geschriebene verschluckt.
