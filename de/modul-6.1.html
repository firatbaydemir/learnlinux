6.1 Netzwerk-Grundlagen — ip, ss, DNS, Ports

Lies deine Netzidentität: Adresse, Gateway, Port und Name. Fast alle Befehle in diesem Modul sind reine Lesebefehle.

Was lernst du in diesem Modul?

  • Du liest IP-Adresse, Präfix und Standardgateway mit ip a und ip r.
  • Du siehst mit ss -tulpn, welcher Dienst auf welchem Port und Interface lauscht.
  • Du kennst die Namensauflösungskette: /etc/hosts → /etc/resolv.conf → DNS-Server.
  • Du liest die Firewall (firewalld / ufw) zuerst und änderst sie, ohne dich auszusperren.
  • Du diagnostizierst "kein Internet" Schicht für Schicht (Adresse → Gateway → IP → Name).

Adresse und Routing: ip a, ip r

Jedes Netzwerk-Interface (eth0, ens3, enp0s3, lo) hat eine IP-Adresse und ein Präfix. 192.168.1.42/24 heißt: Die ersten 24 Bit sind das Netz, der Rest bezeichnet das Gerät (/24 = 255.255.255.0). lo ist das Loopback-Interface (127.0.0.1): die Maschine selbst, es verlässt nie den Rechner.

Liegt das Ziel nicht im lokalen Netz, geht das Paket zum Standardgateway. Die Zeile default via 192.168.1.1 in ip r verrät es. Nutze den modernen Befehl ip statt der alten ifconfig und route; er existiert auf Rocky/Alma und Ubuntu/Debian.

Interface-Namen hängen von Distribution und VM ab; deine Ausgabe zeigt evtl. ens3 oder enp0s3 statt eth0.

ip a

Wozu dient es?
Listet alle Interfaces mit IP-Adressen und Status (UP/DOWN).
Wo wird es verwendet?
Um die Adresse der Maschine zu erfahren oder zu prüfen, ob ein Interface aktiv ist.
Warum ist es wichtig?
Erste Anlaufstelle bei Netzproblemen; ohne Adresse funktioniert nichts darüber.
ip a

ip -br a

Wozu dient es?
Zeigt dieselben Infos als kurze Tabelle, eine Zeile pro Interface.
Wo wird es verwendet?
Für einen schnellen Blick, welches Interface welche Adresse hat.
Warum ist es wichtig?
Du musst keine lange Ausgabe lesen; sie passt auf den Bildschirm.
ip -br a

ip r

Wozu dient es?
Zeigt die Routing-Tabelle; die Zeile default via ist das Gateway.
Wo wird es verwendet?
Wenn du untersuchst, warum du externe Netze nicht erreichst.
Warum ist es wichtig?
Ohne Standardroute verlässt kein Paket das lokale Netz.
ip r

grep default

Wozu dient es?
Filtert Zeilen nach Text; hier findet es das Gateway in gespeicherter Routenausgabe.
Wo wird es verwendet?
Wenn du aus langer Ausgabe eine einzelne Zeile brauchst.
Warum ist es wichtig?
Derselbe Filter funktioniert bei ss-Ausgaben; im Simulator übst du mit Beispieldateien.
grep default ~/net/routes.txt
💡 Tipp

Kombiniere es mit Ausschneiden: grep default ~/net/routes.txt | cut -d' ' -f3 liefert nur die Gateway-Adresse.

⚠️ Achtung

Eine Interface-Adresse von Hand mit ip addr add/del zu ändern, kann deine Verbindung (auch SSH) sofort trennen. In diesem Modul lesen wir nur.

Ports und lauschende Dienste: ss

Die IP-Adresse wählt die Maschine, der Port den Dienst darauf: 22 SSH, 80 HTTP, 443 HTTPS, 53 DNS. Ein laufender Dienst lauscht (LISTEN) auf einer bestimmten Adresse und einem Port.

Buchstaben von ss -tulpn: t TCP, u UDP, l nur lauschende, p Prozessname, n numerische Ausgabe (keine Namensauflösung). Prozessnamen siehst du nur mit sudo.

Achte auf die lokale Adresse: 0.0.0.0:22 heißt auf jedem Interface erreichbar. 127.0.0.1:5432 ist nur von der Maschine selbst erreichbar. Lauscht eine Datenbank auf 0.0.0.0, ist sie evtl. aus dem Netz erreichbar, das ist ein Sicherheitsbefund.

ss hat das alte netstat -tulpn ersetzt; die Optionen sind fast gleich.

ss -tulpn

Wozu dient es?
Listet lauschende TCP/UDP-Sockets mit Ports und Prozessen.
Wo wird es verwendet?
Um "lauscht der Dienst wirklich, und auf welcher Adresse?" zu beantworten.
Warum ist es wichtig?
Ein Dienst kann laufen und trotzdem auf der falschen Adresse lauschen, dann scheitern Verbindungen.
sudo ss -tulpn

ss -tln

Wozu dient es?
Zeigt nur TCP-Listener, ohne Prozessinfo (kein sudo nötig).
Wo wird es verwendet?
Für schnelle Checks oder in Skripten.
Warum ist es wichtig?
Kurz und ohne Rechte; reicht, um zu sehen, ob ein Port offen ist.
ss -tln | grep 8080

curl -I

Wozu dient es?
Holt nur die Antwort-Header eines Webservers.
Wo wird es verwendet?
Um zu testen, ob der Dienst wirklich per HTTP antwortet.
Warum ist es wichtig?
Ein Port kann offen sein, ohne dass die Anwendung antwortet; ein Code wie 200 oder 301 zeigt es.
curl -I http://127.0.0.1:8080
💡 Tipp

Filtere die ss-Ausgabe: ss -tln | grep LISTEN | wc -l zählt, wie viele TCP-Ports lauschen.

⚠️ Achtung

Scanne keine Server, die dir nicht gehören. Das ist unethisch und auffällig; arbeite auf 127.0.0.1 deiner eigenen VM.

Namensauflösung: hosts, resolv.conf, DNS

Ein Name (example.com) wird in dieser Reihenfolge zur IP: Zuerst wird /etc/hosts geprüft, dann der DNS-Server aus /etc/resolv.conf gefragt (die Reihenfolge steht in der Zeile hosts: von /etc/nsswitch.conf).

/etc/hosts enthält lokale, handgeschriebene Zuordnungen: 192.168.1.50 intranet.lab. Gut zum Testen, wirkt aber nur auf diese Maschine.

/etc/resolv.conf wird meist von NetworkManager oder systemd-resolved erzeugt; manuelle Änderungen können beim Neustart überschrieben werden. Unter Ubuntu steht dort oft 127.0.0.53; den echten Server zeigt resolvectl status.

Wichtige Unterscheidung: Funktioniert ping 1.1.1.1, aber ping example.com nicht, ist dein Netz in Ordnung und das Problem ist DNS.

cat /etc/hosts

Wozu dient es?
Zeigt lokale Name-zu-Adresse-Zuordnungen.
Wo wird es verwendet?
Wenn ein Name zu einer unerwarteten Adresse führt.
Warum ist es wichtig?
/etc/hosts wird vor DNS gelesen; eine falsche Zeile überstimmt die gesamte Auflösung.
cat /etc/hosts

cat /etc/resolv.conf

Wozu dient es?
Zeigt die verwendeten DNS-Server (nameserver) und die Suchdomain (search).
Wo wird es verwendet?
Erste Datei, die du prüfst, wenn Namen nicht aufgelöst werden.
Warum ist es wichtig?
Eine falsche oder unerreichbare nameserver-Zeile zerstört die gesamte Namensauflösung.
cat /etc/resolv.conf

getent hosts

Wozu dient es?
Löst einen Namen so auf, wie es das System wirklich tut (hosts + DNS).
Wo wird es verwendet?
Um zu testen, was Anwendungen sehen werden.
Warum ist es wichtig?
Berücksichtigt auch /etc/hosts und ist genauer als Tools, die nur DNS fragen.
getent hosts localhost

resolvectl status

Wozu dient es?
Zeigt auf systemd-resolved-Systemen die DNS-Server pro Interface.
Wo wird es verwendet?
Unter Ubuntu und neueren Rocky/Alma, wenn resolv.conf zu wenig verrät.
Warum ist es wichtig?
Enthüllt den echten DNS-Server hinter 127.0.0.53.
resolvectl status
💡 Tipp

Vor Änderungen sichern: sudo cp /etc/hosts /etc/hosts.bak.

⚠️ Achtung

Eine falsche nameserver-Zeile zerstört die gesamte Namensauflösung. Auf Produktivsystemen konfigurierst du DNS über NetworkManager (nmcli) oder netplan statt /etc/resolv.conf zu bearbeiten.

Firewall: firewalld und ufw

Auch wenn ein Dienst lauscht, kann die Firewall den Port blockieren. Rocky/Alma/RHEL nutzen firewalld (firewall-cmd), Ubuntu/Debian ufw.

In firewalld sind Änderungen standardmäßig runtime: sofort wirksam, aber bei Reload oder Neustart weg. Dauerhaft wird es mit --permanent und anschließendem --reload. ufw-Regeln sind automatisch dauerhaft.

Zuerst lesen: firewall-cmd --list-all oder ufw status verbose. Dann ändern.

SELinux (Rocky) und AppArmor (Ubuntu) sind eine eigene Schicht; ein geöffneter Port heißt nicht immer, dass der Dienst ihn nutzen darf, das ist aber nicht Thema dieses Moduls.

firewall-cmd --list-all

Wozu dient es?
Zeigt erlaubte Dienste und Ports der aktiven Zone.
Wo wird es verwendet?
Auf Rocky/Alma/RHEL, wenn ein Port von außen nicht erreichbar ist.
Warum ist es wichtig?
Du siehst auf einen Blick, welche Dienste oder Ports erlaubt sind; nur lesend und sicher.
sudo firewall-cmd --list-all

firewall-cmd --add-port

Wozu dient es?
Öffnet einen Port; ohne --permanent gilt es nur zur Laufzeit.
Wo wird es verwendet?
Wenn du einen Dienst nach außen freigeben musst.
Warum ist es wichtig?
Erst zur Laufzeit testen, bei Erfolg dauerhaft machen; Fehler verschwinden mit einem Reload.
sudo firewall-cmd --add-port=8080/tcp --timeout=300

ufw status verbose

Wozu dient es?
Zeigt Firewall-Status und Regeln unter Ubuntu/Debian.
Wo wird es verwendet?
Beim Prüfen der Regeln auf einem Ubuntu-Server.
Warum ist es wichtig?
inactive heißt Firewall aus; active zeigt die Standardrichtlinie.
sudo ufw status verbose
💡 Tipp

Auf Rocky verschwindet eine mit --timeout=300 angelegte Regel nach 5 Minuten von selbst; bei einem Fehler repariert sich das System also selbst.

⚠️ Achtung

Wenn du die Firewall über SSH änderst, halte eine zweite SSH-Sitzung offen und nutze zuerst --timeout. Vor ufw enable erlaubst du SSH mit sudo ufw allow 22/tcp.

⛔ Gefahr

Eine Regel aus der Ferne anzuwenden, die den SSH-Port schließt oder die Standardrichtlinie auf deny setzt, sperrt dich aus. Erstelle vorher einen VM-Snapshot (Modul 0.2) und halte Konsolenzugriff bereit.

Diagnoseleiter: von unten nach oben

Löse "kein Internet" Schicht für Schicht; der erste fehlschlagende Schritt zeigt, wo das Problem liegt: (1) Ist das Interface UP und hat eine Adresse? (2) Geht ein Ping zum Gateway? (3) Geht ein Ping zu einer externen IP (1.1.1.1)? (4) Wird der Name aufgelöst? (5) Lauscht der Dienst und erlaubt die Firewall ihn?

ping nutzt ICMP; manche Netze blockieren ICMP, ein fehlgeschlagener Ping heißt also nicht immer keine Verbindung. Probiere auch den echten Dienst mit curl -I.

Dauerndes ping belastet das Ziel unnötig; begrenze die Anzahl mit -c 3.

ping -c 3

Wozu dient es?
Sendet 3 ICMP-Pakete an das Ziel und misst die Antwortzeit.
Wo wird es verwendet?
Um Gateway, externe IP und Name getrennt zu testen.
Warum ist es wichtig?
Zeigt nacheinander, welche Schicht gestört ist.
ping -c 3 1.1.1.1

cut -d

Wozu dient es?
Teilt eine Zeile an einem Trennzeichen in Felder und nimmt das gewünschte Feld.
Wo wird es verwendet?
Um einen Wert wie Adresse, Port oder Präfix aus Ausgabe zu holen.
Warum ist es wichtig?
Du gibst den Wert in eine Datei oder den nächsten Befehl, ohne von Hand zu kopieren.
echo 192.168.1.42/24 | cut -d/ -f2

sort -n | uniq

Wozu dient es?
Sortiert Zeilen numerisch und entfernt Duplikate.
Wo wird es verwendet?
Wenn du eine saubere Liste lauschender Ports erstellst.
Warum ist es wichtig?
Liefert eine übersichtliche, duplikatfreie Liste für Berichte und Vergleiche.
sort -n ~/net/ports.txt | uniq
💡 Tipp

Schreibe deine Ergebnisse in einen Bericht: hostname > ~/net/report.txt, dann mit >> anhängen. So lässt er sich leicht in ein Support-Ticket einfügen.

Mach es in deiner VM

Die eigentliche Praxis findet auf echtem Linux statt: Führe die Befehle in deiner eigenen virtuellen Maschine (VirtualBox, UTM oder WSL) aus und vergleiche die Ausgabe.

Diese Schritte laufen auf deiner eigenen VM und lesen nur. Die Ausgaben sind individuell; IPs und Interface-Namen können abweichen. Fehlt ein Befehl, installiere sudo dnf install iproute bind-utils auf Rocky oder sudo apt install iproute2 dnsutils auf Ubuntu.

Adresse und Gateway

Lies deine Interfaces und Route und füge die Ausgabe ein.

ip -br a
ip r

Beispiel der erwarteten Ausgabe

lo      UNKNOWN  127.0.0.1/8
ens3    UP       192.168.1.42/24
default via 192.168.1.1 dev ens3 proto dhcp metric 100
192.168.1.0/24 dev ens3 proto kernel scope link src 192.168.1.42
Meine Ausgabe sieht anders aus
  • Das Interface kann eth0, ens3 oder enp0s3 heißen; wichtig sind die Adresse und die Zeile default via.
  • Fehlt die default-Zeile, hat die Maschine kein Gateway; prüfe den Netzwerkmodus der VM (NAT/Bridge).

Lauschende Dienste

Liste auf, welche Dienste lauschen, und finde SSH.

sudo ss -tulpn
ss -tln

Beispiel der erwarteten Ausgabe

Netid State  Local Address:Port Process
tcp   LISTEN 0.0.0.0:22         users:(("sshd",pid=812,fd=3))
...
Meine Ausgabe sieht anders aus
  • Ohne sudo bleibt der Prozessname (Spalte Process) leer.
  • Fehlt ss, installiere iproute/iproute2; gibt es keine LISTEN-Zeile, läuft der Dienst nicht.

Namensauflösungskette

Lies hosts und resolv.conf und löse dann einen Namen so auf, wie es das System tut.

cat /etc/hosts
cat /etc/resolv.conf
resolvectl status | head -n 15
getent hosts localhost

Beispiel der erwarteten Ausgabe

127.0.0.1 localhost
nameserver 127.0.0.53
...
::1             localhost
Meine Ausgabe sieht anders aus
  • Fehlt resolvectl (altes oder minimales System), überspringe die Zeile; resolv.conf genügt.
  • nameserver 127.0.0.53 unter Ubuntu ist normal; der echte Server steht in resolvectl status.

Diagnoseleiter

Pinge nacheinander Gateway, externe IP und einen Namen, je 2 Pakete. Ersetze 192.168.1.1 durch dein eigenes Gateway.

ping -c 2 192.168.1.1
ping -c 2 1.1.1.1
ping -c 2 example.com

Beispiel der erwarteten Ausgabe

2 packets transmitted, 2 received, 0% packet loss
Meine Ausgabe sieht anders aus
  • Antwortet die IP, aber der Name nicht, liegt das Problem bei DNS (/etc/resolv.conf).
  • Antwortet nichts, prüfe zuerst Adresse/Gateway mit ip a und ip r; manche Netze blockieren ICMP, probiere auch curl -I https://example.com.

Eigenen Listener erzeugen und sehen

Starte einen temporären Webserver nur auf 127.0.0.1, sieh ihn mit ss, teste ihn mit curl und beende ihn.

python3 -m http.server 8080 --bind 127.0.0.1 &
sleep 1
ss -tln | grep 8080
curl -I http://127.0.0.1:8080
kill %1

Beispiel der erwarteten Ausgabe

LISTEN 0 5 127.0.0.1:8080 0.0.0.0:*
HTTP/1.0 200 OK
Meine Ausgabe sieht anders aus
  • Fehlt python3, muss es installiert werden; du kannst stattdessen deine ss -tln-Ausgabe einfügen.
  • Ist der Port belegt, nimm 8081. Prüfe danach mit jobs, dass kein Hintergrundjob übrig ist.

Firewall lesen (nicht ändern)

Lies den Firewall-Status deiner Distribution. Füge vorerst keine Regel hinzu. Vor Regeländerungen machst du einen VM-Snapshot (Modul 0.2) und hältst eine zweite SSH-Sitzung offen.

# Rocky / Alma / RHEL
sudo firewall-cmd --state
sudo firewall-cmd --list-all
# Ubuntu / Debian
sudo ufw status verbose

Beispiel der erwarteten Ausgabe

running
public (active)
  services: cockpit dhcpv6-client ssh
# oder: Status: inactive
Meine Ausgabe sieht anders aus
  • Der Befehl, der nicht zu deiner Distribution gehört, meldet command not found; das ist normal, führe den anderen aus.
  • not running oder inactive heißt, die Firewall ist aus; das musst du in diesem Lab nicht ändern.

Selbsttest

Welcher Befehl zeigt das Standardgateway?

ip r zeigt die Routing-Tabelle; die Zeile default via ... ist das Gateway. ip a zeigt Adressen, ss lauschende Ports, /etc/hosts Namenszuordnungen.

In der Ausgabe von ss -tulpn lauscht eine Datenbank auf 127.0.0.1:5432. Wer kann sich verbinden?

127.0.0.1 ist die Loopback-Adresse; der Dienst ist nur lokal erreichbar. Nach außen offen sind 0.0.0.0 oder die Adresse eines externen Interfaces.

In welcher Reihenfolge wird ein Name üblicherweise aufgelöst?

Die Zeile hosts: in nsswitch.conf legt die Reihenfolge fest; standardmäßig kommt zuerst die Datei (/etc/hosts), dann DNS.

Was passiert, wenn du firewall-cmd --add-port=8080/tcp ohne --permanent ausführst?

Standard ist die Runtime-Konfiguration: sofort wirksam, nicht dauerhaft. Für dauerhaft brauchst du --permanent und --reload.

Zusammenfassung

  • ip a zeigt Adressen, ip r die Routen und das Standardgateway.
  • ss -tulpn zeigt lauschende Dienste; 127.0.0.1 ist nur lokal, 0.0.0.0 jedes Interface.
  • Namensauflösung: /etc/hosts → /etc/resolv.conf → DNS-Server.
  • Lies die Firewall zuerst; trenne in firewalld Runtime von Permanent und nutze über SSH --timeout und eine zweite Sitzung.
  • Diagnose: Adresse → Gateway → externe IP → Name → Dienst und Firewall.

Fachbegriffe

IP-Adresse
Die Adresse eines Interfaces im Netz, z. B. 192.168.1.42.
Präfix / Subnetzmaske
Trennt Netz- und Geräteteil einer Adresse; /24 = 255.255.255.0.
Gateway
Die Router-Adresse, an die Pakete für Ziele außerhalb des lokalen Netzes gehen.
Loopback
Die Maschine selbst: das Interface lo, 127.0.0.1.
Port
Eine Nummer, die einen Dienst auf einer Maschine wählt; 22 SSH, 80 HTTP, 443 HTTPS.
LISTEN
Ein Dienst wartet auf einer bestimmten Adresse und einem Port auf Verbindungen.
DNS
Das System, das Namen in IP-Adressen übersetzt.
nameserver
Ein in /etc/resolv.conf eingetragener DNS-Server.
runtime / permanent
Temporäre (bis Reload) und dauerhafte Konfiguration in firewalld.
ICMP / ping
Ein einfaches Netzprotokoll, das Erreichbarkeit und Latenz misst.
