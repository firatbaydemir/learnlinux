6.6 Bash-Skript 2 — Schleifen, Funktionen, Fallstricke

Erledige dieselbe Arbeit nicht hundertmal: Baue Schleifen, case und Funktionen, räume temporäre Dateien mit trap auf und schreibe sichere Skripte ohne Quoting-Fallen.

Was lernst du in diesem Modul?

  • Du schreibst wiederholte Arbeit mit for und while.
  • Du liest eine Datei mit while IFS= read -r sicher Zeile für Zeile.
  • Du steuerst Argumente und Menüs mit case und gliederst Code mit Funktionen und local.
  • Du räumst mit mktemp und trap auf und verhinderst mit "${DIR:?}" die Katastrophe durch leere Variablen.
  • Du findest Fehler mit shellcheck, bash -n und bash -x.

Schleifen: for und while

Ein Skript ist mehr als Befehle der Reihe nach. Willst du dieselbe Arbeit für mehrere Server oder Dateien erledigen, nimmst du eine Schleife. for läuft für jedes Element einer Liste, while solange eine Bedingung wahr bleibt.

Die Quelle der Liste muss sicher sein: Dateimuster (./*.txt), feste Listen oder "$@". Gib niemals die Ausgabe von $(ls) an eine Schleife; Namen mit Leerzeichen werden zerlegt.

Hinweis: Der eingebaute Simulator führt keine Schleifen aus; du schreibst sie in Skriptdateien und führst sie in deiner VM aus.

for

Wozu dient es?
Führt die Befehle einmal für jedes Element der Liste aus.
Wo wird es verwendet?
Wenn du dieselbe Prüfung auf mehreren Servern machst oder Dateien eines Ordners verarbeitest.
Warum ist es wichtig?
Kürzt wiederholten Code und senkt die Fehlerquote.
for i in 1 2 3; do echo "n=$i"; done

while

Wozu dient es?
Wiederholt die Befehle, solange die Bedingung wahr ist.
Wo wird es verwendet?
Beim Warten auf ein Ereignis oder beim Lesen von Dateien.
Warum ist es wichtig?
Du musst die Rundenzahl nicht vorher kennen.
while [ -e /tmp/lock ]; do sleep 1; done

echo {1..5}

Wozu dient es?
Brace Expansion: erzeugt 1 2 3 4 5 (im Bereich keine Leerzeichen).
Wo wird es verwendet?
Für Zahlenbereiche oder nummerierte Dateireihen.
Warum ist es wichtig?
Erzeugt kurze Listen ohne Schleife; wird auch in for i in {1..5} genutzt.
echo {1..5}

break / continue

Wozu dient es?
break beendet die Schleife, continue springt zur nächsten Runde.
Wo wird es verwendet?
Beim Überspringen leerer Zeilen oder wenn das Gesuchte gefunden ist.
Warum ist es wichtig?
Vermeidet unnötige Arbeit und verschachtelte if.
[ -n "$line" ] || continue
💡 Tipp

Passt ein Dateimuster auf nichts, bleibt ./*.txt wörtlich stehen. Setze [ -e "$f" ] || continue an den Anfang des Schleifenrumpfs.

Eine Datei zeilenweise lesen

Das richtige Muster zum zeilenweisen Lesen ist while IFS= read -r line; do ... done < file. IFS= bewahrt führende und folgende Leerzeichen, -r interpretiert Backslashes nicht.

Schreibe nicht for line in $(cat file): Zeilen werden an Leerzeichen zerlegt, jedes Wort wird eine Runde. Die Umleitung done < ~/lab/servers.txt macht die Datei zur Eingabe der Schleife.

while IFS= read -r

Wozu dient es?
Liest die Eingabe zeilenweise und legt jede Zeile in eine Variable.
Wo wird es verwendet?
Bei Serverlisten, Logs oder CSV-Dateien.
Warum ist es wichtig?
Liest sicher, ohne Leerzeichen und Backslashes zu verändern.
while IFS= read -r host; do echo "$host"; done < servers.txt

done < file

Wozu dient es?
Leitet die Eingabe der Schleife aus einer Datei um.
Wo wird es verwendet?
In der letzten Zeile eines while read-Blocks.
Warum ist es wichtig?
Eine Pipe (cat | while) läuft in einer Subshell; Variablen sind nach der Schleife weg, bei der Umleitung nicht.
done < ~/lab/servers.txt

wc -l

Wozu dient es?
Gibt die Zeilenanzahl aus.
Wo wird es verwendet?
Wenn du wissen willst, wie viele Runden die Schleife dreht.
Warum ist es wichtig?
Du vergleichst deine Erwartung mit der echten Zahl.
wc -l ~/lab/servers.txt
⚠️ Achtung

Endet die letzte Zeile nicht mit \n, kann read sie überspringen. Füge bei Bedarf || [ -n "$host" ] hinzu.

Verzweigen mit case

case vergleicht einen Wert mit Mustern und ist viel lesbarer als eine lange if/elif-Kette. Jeder Zweig beginnt mit muster) und endet mit ;;; *) läuft, wenn nichts passt. Der Block endet mit esac.

Typisch: das erste Argument ($1) wie bei ./menu.sh start verzweigen oder je nach Präfix eines Servernamens anders handeln.

case ... esac

Wozu dient es?
Verzweigt einen Wert nach Mustern.
Wo wird es verwendet?
In Dienstskripten (start/stop/status) und Menüs.
Warum ist es wichtig?
Lesbar; unbekannte Eingaben fängst du mit *) ab.
case "$1" in start) echo go ;; *) echo usage ;; esac

$1 $@ $#

Wozu dient es?
Erstes Argument, alle Argumente und Anzahl der Argumente.
Wo wird es verwendet?
Wenn du dem Skript Werte von außen gibst.
Warum ist es wichtig?
Das Skript wird wiederverwendbar; "$@" bewahrt Argumente mit Leerzeichen.
echo "first: $1, count: $#"

chmod +x

Wozu dient es?
Gibt dem Skript das Ausführungsrecht.
Wo wird es verwendet?
Bevor du es mit ./menu.sh startest.
Warum ist es wichtig?
Ohne das Recht erhältst du Permission denied.
chmod +x ~/scripts/menu.sh
💡 Tipp

Mehrere Muster kombinierst du mit |, etwa start|restart).

Funktionen, local und Arrays

Eine Funktion gibt wiederholtem Code einen Namen: name() { ...; }. Variablen sind in Bash standardmäßig global; ohne local in der Funktion überschreibst du Variablen von außen.

return liefert nur einen Exit-Code von 0–255. Für Text nutze echo und fange ihn mit $(funktion) ab. Ein Array sammelt mehrere Werte unter einem Namen; in Schleifen immer "${arr[@]}" schreiben, damit Elemente mit Leerzeichen heil bleiben.

name() { ...; }

Wozu dient es?
Gibt einem Codeblock einen Namen, den du später aufrufst.
Wo wird es verwendet?
Wenn dieselbe Prüfung an mehreren Stellen im Skript läuft.
Warum ist es wichtig?
Gliedert den Code, beendet Wiederholung und erleichtert Tests.
log() { echo "[log] $1"; }

local

Wozu dient es?
Begrenzt eine Variable auf die Funktion.
Wo wird es verwendet?
Bei temporären Variablen in Funktionen.
Warum ist es wichtig?
Du überschreibst nicht versehentlich gleichnamige Variablen außerhalb.
local msg=$1

arr=(a b c)

Wozu dient es?
Definiert ein Array mit drei Elementen.
Wo wird es verwendet?
Bei Listen von Servern oder Optionen.
Warum ist es wichtig?
Die Liste steckt in einer Variablen; mit ${#arr[@]} erhältst du die Anzahl.
hosts=(web01 web02 db01)

"${arr[@]}"

Wozu dient es?
Expandiert jedes Element als eigenes, gequotetes Wort.
Wo wird es verwendet?
Beim Bau einer for-Schleife über ein Array.
Warum ist es wichtig?
Elemente mit Leerzeichen werden nicht zerlegt.
for h in "${hosts[@]}"; do echo "$h"; done
💡 Tipp

Arrays gibt es nur in Bash, nicht in sh (dash). Schreibe #!/usr/bin/env bash in die erste Zeile.

Sichere Skripte: set, mktemp, trap

Lege temporäre Dateien nicht mit festem Namen, sondern mit mktemp an: Der Name ist eindeutig und nicht vorhersagbar. Mit trap ... EXIT läuft die Aufräumfunktion, wie auch immer das Skript endet (Fehler, Ctrl+C, normal); kill -9 ist die Ausnahme.

set -euo pipefail macht das Skript strenger: Stopp bei Fehlern (-e), Stopp bei undefinierten Variablen (-u), Fehler in Pipelines bleiben sichtbar (pipefail).

mktemp -d

Wozu dient es?
Erzeugt ein temporäres Verzeichnis mit eindeutigem Namen und gibt den Pfad aus.
Wo wird es verwendet?
Wenn das Skript Zwischendateien braucht.
Warum ist es wichtig?
Verhindert Kollisionen und Angriffe über vorhersagbare Namen.
tmp=$(mktemp -d)

trap cleanup EXIT

Wozu dient es?
Führt die Funktion cleanup aus, wenn das Skript endet.
Wo wird es verwendet?
Bei temporären Verzeichnissen, Lock-Dateien oder Verbindungen.
Warum ist es wichtig?
Auch nach einem Fehler wird aufgeräumt.
trap cleanup EXIT

set -euo pipefail

Wozu dient es?
Stoppt das Skript bei Fehlern, undefinierten Variablen und Pipeline-Fehlern.
Wo wird es verwendet?
In den ersten Zeilen des Skripts.
Warum ist es wichtig?
Du stoppst sofort, statt still falsch weiterzumachen.
set -euo pipefail
⛔ Gefahr

Löschst du in trap, gilt dieselbe Regel: schreibe rm -rf "${tmp:?}". Ist tmp leer, wird aus rm -rf $tmp/ in Wahrheit rm -rf /. Teste zuerst mit echo rm -rf "$tmp".

Fallstricke und Fehlersuche

Der häufigste Fehler sind unquotierte Variablen: touch $F mit F="my notes.txt" erzeugt zwei Dateien (my und notes.txt). Regel: Setze Variablen immer als "$F" in Anführungszeichen.

Die gefährlichste Zeile ist rm -rf $DIR/*: Ist DIR leer, wird daraus rm -rf /*. "${DIR:?}" stoppt das Skript mit Fehler bei leerem oder undefiniertem Wert. Zeige den Pfad vor dem Löschen mit echo.

Fehlersuche: bash -n prüft die Syntax ohne Ausführung, bash -x zeigt jeden Befehl mit +-Präfix, shellcheck findet häufige Fallen.

"$var"

Wozu dient es?
Quotet die Variable; kein Word Splitting und keine Glob-Expansion.
Wo wird es verwendet?
Bei jeder Verwendung einer Variablen.
Warum ist es wichtig?
Dateinamen mit Leerzeichen bleiben ein Stück.
touch "$F"

"${DIR:?}"

Wozu dient es?
Bricht mit Fehler ab, wenn DIR leer oder undefiniert ist.
Wo wird es verwendet?
Bei rm -rf und anderen zerstörerischen Befehlen.
Warum ist es wichtig?
Verhindert, dass eine leere Variable den Pfad / löscht.
rm -rf "${DIR:?}/"*

shellcheck

Wozu dient es?
Analysiert das Skript statisch und meldet Fallen mit Code (SC2086).
Wo wird es verwendet?
Nach dem Schreiben, vor dem Commit.
Warum ist es wichtig?
Findet unquotierte Variablen und Ähnliches ohne Ausführung.
shellcheck ~/scripts/bad.sh

bash -n

Wozu dient es?
Prüft nur die Syntax, ohne das Skript auszuführen.
Wo wird es verwendet?
Bei Verdacht auf fehlendes done, fi oder esac.
Warum ist es wichtig?
Ungefährlich; es läuft kein Befehl.
bash -n ~/scripts/loop.sh

bash -x

Wozu dient es?
Schreibt jeden Befehl mit Expansionen und +-Präfix auf den Bildschirm.
Wo wird es verwendet?
Wenn sich das Skript unerwartet verhält.
Warum ist es wichtig?
Du siehst, was die Variablen wirklich enthalten.
bash -x ~/scripts/loop.sh
💡 Tipp

Lass einen zerstörerischen Befehl zuerst mit vorangestelltem echo laufen: echo rm -rf "$DIR". Stimmt die Ausgabe, entfernst du das echo.

⚠️ Achtung

ShellCheck installierst du unter Ubuntu/Debian mit sudo apt install shellcheck, unter Rocky/Alma mit EPEL: sudo dnf install epel-release, danach sudo dnf install ShellCheck.

Mach es in deiner VM

Die eigentliche Praxis findet auf echtem Linux statt: Führe die Befehle in deiner eigenen virtuellen Maschine (VirtualBox, UTM oder WSL) aus und vergleiche die Ausgabe.

Mache diese Aufgaben in deiner eigenen VM (Ubuntu, Rocky/Alma oder WSL). Alles passiert unter ~/scripts; fasse keine Systemdateien an. Bevor du etwas mit rm ausprobierst, erstelle einen VM-Snapshot (Modul 0.2) und setze echo vor den Löschbefehl.

Erste Schleife und bash -n

Schreibe eine for-Schleife, prüfe sie zuerst mit bash -n und führe sie dann aus. Füge die Ausgabe ein.

mkdir -p ~/scripts && cd ~/scripts
printf '#!/usr/bin/env bash\nfor i in 1 2 3; do\n  echo "n=$i"\ndone\n' > loop.sh
chmod +x loop.sh
bash -n loop.sh && ./loop.sh

Beispiel der erwarteten Ausgabe

n=1
n=2
n=3
Meine Ausgabe sieht anders aus
  • Meldet bash -n einen Fehler, prüfe mit cat loop.sh die Zeilen do und done.
  • Bei Permission denied hast du chmod +x loop.sh vergessen.

Schleife über Datei und case

Lies die Serverliste zeilenweise und gib mit case je nach Name eine Rolle aus.

cd ~/scripts
printf 'web01\nweb02\ndb01\ncache01\nmail01\n' > servers.txt
cat > readlines.sh <<'EOF'
#!/usr/bin/env bash
while IFS= read -r host; do
  case "$host" in
    web*) echo "$host: web" ;;
    db*) echo "$host: database" ;;
    *) echo "$host: other" ;;
  esac
done < servers.txt
EOF
bash readlines.sh

Beispiel der erwarteten Ausgabe

web01: web
web02: web
db01: database
cache01: other
mail01: other
Meine Ausgabe sieht anders aus
  • Ist die Ausgabe leer, prüfe mit ls, ob servers.txt im selben Ordner liegt.
  • Steht überall other, hast du dich in den case-Mustern (web*)) vertippt.

Funktion, local, mktemp, trap

Führe ein Skript aus, das ein temporäres Verzeichnis anlegt und beim Beenden aufräumt. Füge die Ausgabe ein.

cd ~/scripts
cat > safe.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp -d)
cleanup() {
  rm -rf "${tmp:?}"
  echo "cleanup: removed $tmp"
}
trap cleanup EXIT
log() {
  local msg=$1
  echo "work in $tmp: $msg"
}
log "hello"
EOF
bash safe.sh

Beispiel der erwarteten Ausgabe

work in /tmp/tmp.Ab12Cd: hello
cleanup: removed /tmp/tmp.Ab12Cd
Meine Ausgabe sieht anders aus
  • Der Verzeichnisname ist bei jedem Lauf anders; wichtig ist, dass beide Zeilen erscheinen.
  • Fehlt die cleanup-Zeile, prüfe, ob trap cleanup EXIT nach der Funktion steht.

Fallen mit shellcheck finden

Installiere ShellCheck und prüfe ein Skript mit unquotierter Variable. Füge die Warnung ein.

# Ubuntu/Debian
sudo apt install -y shellcheck
# Rocky/Alma (needs EPEL)
sudo dnf install -y epel-release && sudo dnf install -y ShellCheck

Beispiel der erwarteten Ausgabe

...
cd ~/scripts
printf '#!/usr/bin/env bash\nF="my notes.txt"\ntouch $F\n' > bad.sh
shellcheck bad.sh

Beispiel der erwarteten Ausgabe

In bad.sh line 3:
touch $F
      ^-- SC2086 (info): Double quote to prevent globbing and word splitting.
Meine Ausgabe sieht anders aus
  • Schlägt die Installation fehl, prüfe unter Rocky mit dnf repolist, ob epel-release aktiv ist.
  • Je nach ShellCheck-Version unterscheidet sich der Text leicht; der Code SC2086 genügt.

bash -x und sicherer Test

Verfolge mit bash -x jeden Schritt des Skripts; probiere danach rm mit leerem DIR nur mit echo aus (kein echtes Löschen).

cd ~/scripts
bash -x loop.sh 2>&1 | head -8
DIR=""
echo rm -rf $DIR/*

Beispiel der erwarteten Ausgabe

+ for i in 1 2 3
+ echo n=1
n=1
...
rm -rf /bin /boot /etc ...
Meine Ausgabe sieht anders aus
  • Zeilen mit + sind die Spur von bash -x; mehrere + zeigen verschachtelte Befehle.
  • Die letzte Zeile ist nur echo, es wird nichts gelöscht; sie zeigt nur, dass die leere Variable zu /* wird.

Schnelle Übungen (Simulator)

Optional: Zum Aufwärmen vor der VM oder als Ersatz ohne VM nutzt du das virtuelle Terminal im Browser. Aufgaben werden automatisch geprüft.

Die Aufgaben steigen vom Aufwärmen bis zum Ticket an. Die Abzeichen zeigen den Schwierigkeitsgrad.

Aufwärmen

  1. AufwärmenLeicht

    Erzeuge ~/scripts/loop.sh mit printf; die erste Zeile soll #!/usr/bin/env bash sein (Umleitung >).

    Hinweis

    printf '#!/usr/bin/env bash\n' > ~/scripts/loop.sh — das \n am Ende ist der Zeilenumbruch.

    Lösung
    printf '#!/usr/bin/env bash\n' > ~/scripts/loop.sh

  2. AufwärmenLeicht

    Wie viele Server stehen in ~/lab/servers.txt? Zähle mit wc -l und schätze, wie viele Runden eine Schleife drehen würde.

    Hinweis

    wc -l ~/lab/servers.txt gibt die Zeilenzahl aus.

    Lösung
    wc -l ~/lab/servers.txt

Geführtes Lab

  1. Geführtes LabLeicht

    Hänge mit >> (ohne Überschreiben) eine for i in 1 2 3; do ... done-Schleife an loop.sh an: drei Zeilen mit printf.

    Hinweis

    In einfachen Anführungszeichen wird $i von der Shell nicht expandiert. Nutze \n für Zeilenumbrüche.

    Lösung
    printf 'for i in 1 2 3; do\n  echo "n=$i"\ndone\n' >> ~/scripts/loop.sh

  2. Geführtes LabLeicht

    Mache loop.sh ausführbar (Rechte 755).

    Hinweis

    chmod 755 ~/scripts/loop.sh oder chmod +x; prüfe mit ls -l auf -rwxr-xr-x.

    Lösung
    chmod 755 ~/scripts/loop.sh

  3. Geführtes LabMittel

    Schreibe ~/scripts/readlines.sh mit dem Muster while IFS= read -r host; do ... done < ~/lab/servers.txt, das jeden Server mit echo ausgibt.

    Hinweis

    Schreibe mit einem einzigen printf vier Zeilen; die letzte ist done < ~/lab/servers.txt.

    Lösung
    printf '#!/usr/bin/env bash\nwhile IFS= read -r host; do\n  echo "checking $host"\ndone < ~/lab/servers.txt\n' > ~/scripts/readlines.sh

  4. Geführtes LabMittel

    Setze F="my notes.txt" und lege die Datei mit touch "$F" an. Was wäre ohne Anführungszeichen passiert?

    Hinweis

    Zwei Befehle: erst die Zuweisung, dann touch "$F". Prüfe mit ls.

    Lösung
    F="my notes.txt"
touch "$F"

  5. Geführtes LabMittel

    Schreibe ~/scripts/arr.sh: Es definiert das Array hosts=(web01 web02 db01) und gibt es mit for h in "${hosts[@]}"; do ... done aus.

    Hinweis

    Im einfach gequoteten printf steht "${hosts[@]}" unverändert.

    Lösung
    printf 'hosts=(web01 web02 db01)\nfor h in "${hosts[@]}"; do\n  echo "$h"\ndone\n' > ~/scripts/arr.sh

Vorhersagen

  1. VorhersagenLeicht

    Schätze die Ausgabe von ./scripts/count.sh | wc -l, bevor du es startest: wie viele Zeilen? Führe es dann aus und prüfe.

    Hinweis

    Das Skript enthält drei echo-Zeilen; sieh mit cat scripts/count.sh nach.

    Lösung
    ./scripts/count.sh | wc -l

  2. VorhersagenMittel

    Setze mit DIR= eine leere Variable und führe echo "rm -rf $DIR/" aus. Welchen Pfad würde es löschen? Schätze, dann prüfe.

    Hinweis

    Das leere $DIR verschwindet; übrig bleibt /. Darum schreibt man "${DIR:?}".

    Lösung
    DIR=
echo "rm -rf $DIR/"

Fehler finden

  1. Fehler findenLeicht

    ~/scripts/hello.sh läuft nicht (Permission denied). Repariere es und führe es aus.

    Hinweis

    ls -l ~/scripts zeigt die Rechte; chmod +x ergänzt sie; dann ~/scripts/hello.sh.

    Lösung
    chmod +x ~/scripts/hello.sh
~/scripts/hello.sh

  2. Fehler findenMittel

    Die Zeile rm -rf $DIR/* in ~/scripts/clean.sh ist gefährlich. Schreibe die Datei neu: DIR=/home/student/tmpwork bleibt, die Löschzeile nutzt "${DIR:?}/"*.

    Hinweis

    Sieh mit cat ~/scripts/clean.sh nach; schreibe dann die drei Zeilen mit printf neu.

    Lösung
    printf '#!/usr/bin/env bash\nDIR=/home/student/tmpwork\nrm -rf "${DIR:?}/"*\n' > ~/scripts/clean.sh

  3. Fehler findenMittel

    In ~/scripts/list_files.sh steht for f in $(ls *.txt); das zerlegt Namen mit Leerzeichen. Schreibe die Datei mit Glob neu: for f in ./*.txt; do.

    Hinweis

    Sieh den Inhalt mit cat an. Schreibe vier Zeilen mit printf; $f bleibt in einfachen Anführungszeichen.

    Lösung
    printf '#!/usr/bin/env bash\nfor f in ./*.txt; do\n  echo "$f"\ndone\n' > ~/scripts/list_files.sh

Mini-Projekt

  1. Mini-ProjektMittel

    Erzeuge ~/scripts/menu.sh: case "$1" in mit den Zweigen start), stop) und *), Ende mit esac; mache es danach ausführbar.

    Hinweis

    Schreibe die Datei mit einem printf, dann chmod 755. Jeder Zweig endet mit ;;.

    Lösung
    printf '#!/usr/bin/env bash\ncase "$1" in\n  start) echo starting ;;\n  stop) echo stopping ;;\n  *) echo "usage: $0 start|stop" ;;\nesac\n' > ~/scripts/menu.sh
chmod 755 ~/scripts/menu.sh

  2. Mini-ProjektSchwer

    Schreibe ~/scripts/safe.sh: temporäres Verzeichnis mit mktemp -d, eine Funktion cleanup(), trap cleanup EXIT und eine Funktion log() mit local.

    Hinweis

    Erst tmp=$(mktemp -d), dann cleanup() { rm -rf "${tmp:?}"; }, ganz am Ende trap cleanup EXIT.

    Lösung
    printf '#!/usr/bin/env bash\ntmp=$(mktemp -d)\ncleanup() {\n  rm -rf "${tmp:?}"\n}\ntrap cleanup EXIT\nlog() {\n  local msg=$1\n  echo "$msg"\n}\nlog "work in $tmp"\n' > ~/scripts/safe.sh

Herausforderung

  1. HerausforderungSchwer

    Welche Server haben in ~/lab/app.log einen ERROR gemeldet? Schreibe die eindeutigen, sortierten Servernamen in ~/lab/failed_hosts.txt.

    Hinweis

    grep ERROR, dann cut -d' ' -f4, sort -u; leite die Ausgabe mit > in die Datei um.

    Lösung
    grep ERROR ~/lab/app.log | cut -d' ' -f4 | sort -u > ~/lab/failed_hosts.txt

    Hinweis

    Ein printf mit fünf Zeilen, dann chmod 755. trap "echo cleanup done" EXIT genügt.

    Lösung

  2. TicketSchwer

    Ticket: Das Team möchte ein Skript, das jeden Server aus ~/lab/servers.txt prüft. Schreibe ~/scripts/check_all.sh: Funktion check_host() mit local, Schleife while IFS= read -r host; do, done < ~/lab/servers.txt; ausführbar.

    Hinweis

    Erst die Funktion, dann die Schleife; leere Zeilen mit [ -n "$host" ] || continue überspringen; zuletzt chmod 755.

    Lösung
    printf '#!/usr/bin/env bash\ncheck_host() {\n  local h=$1\n  echo "check $h"\n}\nwhile IFS= read -r host; do\n  [ -n "$host" ] || continue\n  check_host "$host"\ndone < ~/lab/servers.txt\n' > ~/scripts/check_all.sh

Selbsttest

Was passiert bei rm -rf $DIR/*, wenn DIR leer ist, und welche Schreibweise schützt?

Die leere Variable verschwindet und der Befehl wird zu rm -rf /*. ${DIR:?} stoppt das Skript bei leerem Wert.

Welches Muster liest eine Datei sicher zeilenweise?

for mit $(cat) zerlegt Zeilen in Wörter. while IFS= read -r liest die Zeile unverändert.

Was bewirkt local x=1 in einer Funktion?

local begrenzt den Geltungsbereich auf die Funktion; gleichnamige Variablen außerhalb bleiben unberührt.

Wann läuft trap cleanup EXIT?

Die EXIT-Falle läuft bei normalem Ende, Fehlern und den meisten Signalen; SIGKILL lässt sich nicht abfangen.

Zusammenfassung

  • for läuft für jedes Listenelement, while solange die Bedingung wahr ist; wähle eine sichere Quelle.
  • Lies Dateien mit while IFS= read -r line; do ... done < file, nicht mit $(cat).
  • case ... esac verzweigt Argumente und Menüs lesbar; *) ist der Standardzweig.
  • Nutze local in Funktionen; durchlaufe Arrays mit "${arr[@]}".
  • Lege temporäre Dateien mit mktemp an und räume mit trap cleanup EXIT auf.
  • Quote jede Variable; schreibe beim Löschen "${DIR:?}" und teste zuerst mit echo.
  • bash -n, bash -x und shellcheck zeigen Fehler ohne Ausführung oder Schritt für Schritt.
