Startseite / Stufe 6

6.8 Abschlussprojekt — Kleiner Firmenserver

Kombiniere alles auf einem Server: Benutzer, gemeinsames Verzeichnis, Webseite, Firewall, Backup, Timer und ein geprüfter Abgabebericht.

Was lernst du in diesem Modul?

  • Du planst zuerst den ganzen Server und erstellst einen VM-Snapshot, bevor du etwas änderst.
  • Du richtest die Benutzer alice, bob, carol, die Gruppen staff und admins und das gemeinsame Verzeichnis /srv/company mit setgid ein.
  • Du veröffentlichst eine Seite mit nginx, setzt das richtige Label (SELinux) oder prüfst AppArmor und öffnest die Ports 80/443, ohne dich aus SSH auszusperren.
  • Du automatisierst das Backup mit einem Skript und einem systemd-Timer.
  • Du prüfst jeden Schritt mit einer Checkliste und schreibst einen Abgabebericht.

1. Erst Plan und Sicherheit

Das Ziel: ein kleiner Firmenserver namens linux-lab. Drei Personen arbeiten darauf: alice (Admin), bob und carol. Alles liegt unter /srv/company: shared (Teamdateien), admin (nur Admins), web (die Seite), backup und scripts.

Arbeite in der VM, nie auf einer Produktivmaschine. Dieses Projekt legt Benutzer an und ändert Rechte, SELinux-Labels, Firewall-Regeln und systemd-Units. Erstelle vor dem Start einen Snapshot (Modul 0.2). Geht ein Schritt schief, bist du in Sekunden zurück.

Das eingebaute Terminal kann useradd, nginx, firewall-cmd oder systemctl nicht ausführen. Deshalb bauen die Simulator-Aufgaben die Dateien des Projekts (Rechtebaum, Skript, Unit-Dateien, Bericht) unter ~/srv/company nach, während die VM-Aufgaben das Echte in /srv/company tun.

Reihenfolge: 1) Plan + Snapshot, 2) Benutzer und Verzeichnisse, 3) Web, 4) Firewall, 5) Backup + Timer, 6) Prüfung + Bericht. RHEL/Rocky und Debian/Ubuntu unterscheiden sich nur in wenigen Befehlen; beide werden gezeigt.

⚠️ Achtung

Erstelle jetzt einen VM-Snapshot und nenne ihn before-company-project. Führe dieses Projekt nicht auf einem echten Server aus, den andere nutzen.

2. Benutzer, Gruppen und gemeinsames Verzeichnis

Lege die Gruppen staff (alice, bob, carol) und admins (nur alice) an. Für die Benutzer nimmst du useradd -m -G. Benutzer löschen gehört nicht zu diesem Projekt (userdel -r entfernt auch Home-Verzeichnisse).

Ein gemeinsames Verzeichnis braucht zwei Dinge. Setgid (chmod 2770) lässt neue Dateien die Gruppe des Verzeichnisses (staff) erben, sodass bob die Dateien von carol bearbeiten kann. Modus 770 hält alle anderen draußen. Optional sorgt eine Default-ACL (setfacl -d -m g:staff:rwx) dafür, dass neue Dateien auch bei strenger umask für die Gruppe schreibbar sind.

Prinzip der minimalen Rechte: web ist 755 (nginx muss lesen), scripts ist 750, backup ist 700. Im Simulator übst du dieselben Modi mit chmod auf ~/srv/company; ein normaler Benutzer kann dort kein chgrp, der Gruppenteil gibt es nur in der VM.

sudo useradd -m -s /bin/bash -G staff alice

Wozu dient es?
Legt einen Benutzer mit Home-Verzeichnis, Shell und Zusatzgruppe an.
Wo wird es verwendet?
Einmal für alice, bob, carol.
Warum ist es wichtig?
Echte Konten mit eigenen Home-Verzeichnissen.
sudo useradd -m -s /bin/bash -G staff alice

sudo chgrp staff /srv/company/shared

Wozu dient es?
Setzt die besitzende Gruppe des Verzeichnisses.
Wo wird es verwendet?
Bei shared und admin.
Warum ist es wichtig?
Die Gruppenzugehörigkeit gibt setgid an neue Dateien weiter.
sudo chgrp staff /srv/company/shared

chmod 2770

Wozu dient es?
Setzt rwx für Besitzer und Gruppe, nichts für andere, plus das setgid-Bit.
Wo wird es verwendet?
Bei shared und admin.
Warum ist es wichtig?
Neue Dateien erben die Gruppe; Außenstehende haben keinen Zugriff.
chmod 2770 ~/srv/company/shared

sudo setfacl -d -m g:staff:rwx

Wozu dient es?
Setzt eine Default-ACL, die neue Dateien im Verzeichnis erben.
Wo wird es verwendet?
Am Verzeichnis shared (Paket acl).
Warum ist es wichtig?
Die Gruppe bleibt schreibberechtigt, auch wenn jemand umask 077 hat.
sudo setfacl -d -m g:staff:rwx /srv/company/shared

ls -ld

Wozu dient es?
Zeigt das Verzeichnis selbst, nicht seinen Inhalt.
Wo wird es verwendet?
Beim Prüfen von Modus und Gruppe.
Warum ist es wichtig?
drwxrws--- bedeutet, dass setgid aktiv ist (das s).
ls -ld ~/srv/company/shared
💡 Tipp

Ein großes S in drwxr-S--- heißt: setgid ist gesetzt, aber die Gruppe hat kein Ausführungsrecht (x); korrigiere den Modus.

⚠️ Achtung

Löse Rechteprobleme nie mit chmod 777. Dann kann jeder die Dateien ändern oder löschen.

3. Webseite mit nginx, SELinux und AppArmor

Installiere nginx und lass es /srv/company/web ausliefern. Wir legen in /etc/nginx/conf.d/company.conf einen Server-Block namens company.local an (funktioniert in beiden Familien) und testen mit einem Host:-Header, damit die Standardseite nicht stört.

RHEL/Rocky: SELinux versieht jede Datei mit einem Label. Ein neues Verzeichnis unter /srv bekommt ein allgemeines Label, daher liefert nginx 403 Forbidden, obwohl die Unix-Rechte stimmen. Die Lösung ist das richtige Label: semanage fcontext speichert die Regel, restorecon wendet sie an. Nimm nicht setenforce 0 als Abkürzung; das schaltet den Schutz des ganzen Systems ab.

Debian/Ubuntu: Es gibt kein Label zu setzen. AppArmor ist aktiv, aber nginx wird normalerweise nicht durch ein Profil eingeschränkt; du prüfst nur den Status mit aa-status. Ein 403 ist dort ein normales Rechteproblem (prüfe die Verzeichnismodi bis hoch zu /srv).

sudo dnf install -y nginx

Wozu dient es?
Installiert nginx (RHEL, Rocky, Alma). Unter Ubuntu: sudo apt install -y nginx.
Wo wird es verwendet?
Erster Schritt im Web-Kapitel.
Warum ist es wichtig?
Der Paketmanager erledigt Dateien und Abhängigkeiten.
sudo dnf install -y nginx

sudo semanage fcontext -a -t httpd_sys_content_t "/srv/company/web(/.*)?"

Wozu dient es?
Speichert eine Regel: Dateien unter web bekommen das Web-Inhalt-Label.
Wo wird es verwendet?
RHEL-Familie (Paket policycoreutils-python-utils).
Warum ist es wichtig?
Das Label übersteht ein Relabel; chcon nicht.
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/company/web(/.*)?"

sudo restorecon -Rv /srv/company/web

Wozu dient es?
Wendet die gespeicherte Label-Regel auf vorhandene Dateien an.
Wo wird es verwendet?
Direkt nach semanage fcontext.
Warum ist es wichtig?
Ohne diesen Schritt existiert die Regel, aber die Dateien behalten das alte Label.
sudo restorecon -Rv /srv/company/web

ls -Zd /srv/company/web

Wozu dient es?
Zeigt das SELinux-Label des Verzeichnisses.
Wo wird es verwendet?
Zur Prüfung des Labels.
Warum ist es wichtig?
Du willst httpd_sys_content_t sehen.
ls -Zd /srv/company/web

sudo nginx -t

Wozu dient es?
Testet die nginx-Konfiguration ohne Neustart.
Wo wird es verwendet?
Vor jedem Start oder Reload.
Warum ist es wichtig?
Ein Tippfehler würde sonst die Seite lahmlegen.
sudo nginx -t
💡 Tipp

Warum SELinux etwas blockiert hat, siehst du mit: sudo ausearch -m avc -ts recent. Lies das Log, bevor du etwas änderst.

⚠️ Achtung

setenforce 0 ist bestenfalls ein Diagnosewerkzeug, nie eine Lösung. Setze stattdessen das Label.

4. Firewall: 80 und 443 öffnen, SSH behalten

RHEL/Rocky nutzt firewalld, Ubuntu nutzt ufw. Beide können dich aus deinem eigenen Server aussperren, wenn du per SSH verbunden bist. Regeln: SSH bleibt erlaubt, teste zuerst mit einer Runtime-Regel und mache sie erst nach dem Test dauerhaft.

firewalld: Regeln ohne --permanent verschwinden beim Reload oder Neustart; mit --timeout=300 löschen sie sich selbst. ufw: Regeln gelten sofort und werden gespeichert, also erlaube SSH vor ufw enable.

Halte beim Ändern der Firewall immer eine zweite SSH-Sitzung offen (oder die VM-Konsole). Sperren dich die neuen Regeln aus, funktionieren die offene Sitzung oder die Konsole weiter.

sudo firewall-cmd --list-services

Wozu dient es?
Listet die erlaubten Dienste der aktiven Zone.
Wo wird es verwendet?
Vor und nach jeder Änderung.
Warum ist es wichtig?
Bestätigt, dass ssh noch da ist.
sudo firewall-cmd --list-services

sudo firewall-cmd --permanent --add-service={http,https}

Wozu dient es?
Speichert dauerhafte Regeln für die Ports 80 und 443.
Wo wird es verwendet?
Nachdem der Runtime-Test funktioniert hat.
Warum ist es wichtig?
Übersteht Reload und Neustart; anwenden mit --reload.
sudo firewall-cmd --permanent --add-service={http,https}

sudo ufw allow OpenSSH

Wozu dient es?
Erlaubt SSH (Port 22) in ufw.
Wo wird es verwendet?
Ubuntu, immer vor ufw enable.
Warum ist es wichtig?
Verhindert die Aussperrung beim Einschalten der Firewall.
sudo ufw allow OpenSSH

sudo ufw allow 80/tcp

Wozu dient es?
Erlaubt HTTP; wiederhole mit 443/tcp für HTTPS.
Wo wird es verwendet?
Ubuntu-Webserver.
Warum ist es wichtig?
Öffnet nur die Ports, die die Seite braucht.
sudo ufw allow 80/tcp

ss -tulpn

Wozu dient es?
Listet lauschende TCP/UDP-Ports mit dem Prozess.
Wo wird es verwendet?
Um zu sehen, was der Server wirklich anbietet.
Warum ist es wichtig?
Jeder unerwartete Port ist ein Befund für deinen Bericht.
ss -tulpn
💡 Tipp

Übe das Lesen von ss-Ausgaben im Simulator: Die Audit-Dateien in deinem Home-Verzeichnis enthalten eine Beispielliste, die du mit grep und cut auswerten kannst.

⛔ Gefahr

Entferne nie den Dienst ssh und sperre nie Port 22, solange du per SSH verbunden bist. Prüfe ssh mit --list-services oder ufw status vor firewall-cmd --reload oder ufw enable. Bist du ausgesperrt, nutze die VM-Konsole und stelle bei Bedarf den Snapshot wieder her.

5. Backup-Skript und systemd-Timer

Das Backup ist ein kurzes Skript (Module 6.5/6.6): Es schreibt ein datiertes tar.gz-Archiv von shared, web und admin nach /srv/company/backup und löscht Archive, die älter als 7 Tage sind. In der Praxis wäre eine zweite Platte oder eine Remote-Kopie besser; für das Projekt reicht ein lokaler Ordner.

systemd führt das Skript aus: Eine .service mit Type=oneshot beschreibt, was läuft, ein .timer beschreibt, wann (OnCalendar=, Persistent=true). Aktiviere den Timer, nicht den Service. Nach dem Anlegen oder Ändern von Unit-Dateien führe systemctl daemon-reload aus.

Auf RHEL/Rocky hat ein Skript in /srv/company/scripts ein allgemeines Label, und systemd kann es verweigern (Status 203/EXEC). Gib ihm das Label bin_t mit semanage fcontext und restorecon, wie beim Web-Verzeichnis.

tar -czf

Wozu dient es?
Erstellt ein komprimiertes Archiv.
Wo wird es verwendet?
Im Backup-Skript.
Warum ist es wichtig?
Eine datierte Datei pro Backup lässt sich leicht ablegen und wiederherstellen.
tar -czf /srv/company/backup/company-test.tar.gz -C /srv/company shared web admin

systemctl daemon-reload

Wozu dient es?
Lässt systemd neue oder geänderte Unit-Dateien einlesen.
Wo wird es verwendet?
Nach dem Schreiben von Service und Timer.
Warum ist es wichtig?
Sonst kennt systemd die neuen Units nicht.
sudo systemctl daemon-reload

systemctl enable --now company-backup.timer

Wozu dient es?
Aktiviert den Timer beim Boot und startet ihn sofort.
Wo wird es verwendet?
Einmal, nach daemon-reload.
Warum ist es wichtig?
Das Backup läuft dann jede Nacht ohne dein Zutun.
sudo systemctl enable --now company-backup.timer

systemctl list-timers

Wozu dient es?
Zeigt Timer mit nächstem und letztem Lauf.
Wo wird es verwendet?
Zur Prüfung des Zeitplans.
Warum ist es wichtig?
Du siehst, wann das nächste Backup läuft.
systemctl list-timers company-backup.timer --no-pager

chmod 755 backup.sh

Wozu dient es?
Macht das Skript ausführbar.
Wo wird es verwendet?
Immer, wenn du ein Skript anlegst.
Warum ist es wichtig?
Ohne x-Bit kann der Service es nicht starten.
chmod 755 ~/srv/company/scripts/backup.sh
💡 Tipp

Starte den Service einmal von Hand mit sudo systemctl start company-backup.service und sieh dir ls -l /srv/company/backup an, bevor du auf den Timer wartest.

⛔ Gefahr

find ... -delete lässt sich nicht rückgängig machen. Teste die Zeile zuerst mit -print statt -delete und führe sie nur auf /srv/company/backup aus.

6. Prüf-Checkliste und Abgabebericht

Ein Server ist erst fertig, wenn du Belege hast. Gehe die Checkliste durch: Benutzer und Gruppen, setgid-Verzeichnis, Seite antwortet mit 200, SELinux-Label oder AppArmor-Status, Firewall hat ssh/80/443, Timer aktiv, Backup-Datei vorhanden, Backup-Verzeichnis 700.

Ein kleines Skript gibt pro Prüfung OK: oder FAIL: aus, damit das Ergebnis leicht zu lesen und einzufügen ist. Der Abgabebericht /srv/company/REPORT.txt enthält Hostnamen, Datum, die Prüfausgabe und die lauschenden Ports. Das gibst du ab.

Sagt eine Zeile FAIL, gehe zum passenden Kapitel zurück und behebe es. Bearbeite den Bericht nicht von Hand, um einen Fehler zu verstecken.

getent group staff

Wozu dient es?
Zeigt den Gruppeneintrag mit Mitgliedern.
Wo wird es verwendet?
Um die Gruppenmitgliedschaft zu belegen.
Warum ist es wichtig?
Liest aus der echten Benutzerdatenbank.
getent group staff

stat -c '%A %U:%G %n' /srv/company/shared

Wozu dient es?
Gibt Rechte, Besitzer und Gruppe in einer Zeile aus.
Wo wird es verwendet?
In Prüfungen und im Bericht.
Warum ist es wichtig?
Kurzer Beleg, dass der Modus drwxrws--- ist.
stat -c '%A %U:%G %n' /srv/company/shared

curl -I

Wozu dient es?
Holt nur die HTTP-Header.
Wo wird es verwendet?
Zum lokalen Testen der Webseite.
Warum ist es wichtig?
200 OK zeigt, dass nginx lokal geantwortet hat und Dateirechte/Labels den Zugriff erlauben; prüfe Firewall-Regeln separat und teste nach Möglichkeit von einem anderen Rechner.
curl -I -H 'Host: company.local' http://localhost

wc -l

Wozu dient es?
Zählt Zeilen.
Wo wird es verwendet?
Um zu prüfen, dass der Bericht nicht leer ist.
Warum ist es wichtig?
Ein Bericht braucht echten Inhalt.
wc -l ~/srv/company/REPORT.txt
💡 Tipp

Führe die Checkliste auch nach einem Neustart aus. Ein Dienst, der nur bis zum nächsten Neustart läuft, ist nicht fertig.

Mach es in deiner VM

Die eigentliche Praxis findet auf echtem Linux statt: Führe die Befehle in deiner eigenen virtuellen Maschine (VirtualBox, UTM oder WSL) aus und vergleiche die Ausgabe.

Mache das echte Projekt in deiner VM in dieser Reihenfolge. Erstelle zuerst einen Snapshot: Geht etwas schief, gehst du zurück. Füge die Ausgabe ein, wenn eine Aufgabe es verlangt. Bei Befehlen für RHEL oder Ubuntu führst du nur deine Variante aus.

Snapshot und Ausgangszustand

Erstelle in deinem VM-Programm einen VM-Snapshot namens before-company-project (Modul 0.2). Prüfe dann das System und füge die Ausgabe ein.

grep -E '^(ID|PRETTY_NAME)=' /etc/os-release
# RHEL / Rocky / Alma:
getenforce
# Debian / Ubuntu:
sudo aa-status | head -n 3

Beispiel der erwarteten Ausgabe

ID=rocky
PRETTY_NAME="Rocky Linux 9.4 (Blue Onyx)"
Enforcing
Meine Ausgabe sieht anders aus
  • getenforce: command not found unter Ubuntu ist normal; nimm die Zeile mit aa-status.
  • Sagt SELinux Permissive oder Disabled, notiere es und mache weiter, ändere den Modus aber nicht mit setenforce.

Benutzer, Gruppen, gemeinsames Verzeichnis

Lege Gruppen, Benutzer und den Verzeichnisbaum mit setgid an. Beweise es dann und füge die Ausgabe ein.

sudo groupadd staff
sudo groupadd admins
for u in alice bob carol; do sudo useradd -m -s /bin/bash -G staff $u; done
sudo usermod -aG admins alice
sudo mkdir -p /srv/company/{shared,admin,web,backup,scripts}
sudo chgrp staff /srv/company/shared
sudo chgrp admins /srv/company/admin
sudo chmod 2770 /srv/company/shared /srv/company/admin
sudo chmod 755 /srv/company/web
sudo chmod 750 /srv/company/scripts
sudo chmod 700 /srv/company/backup

sudo -u bob touch /srv/company/shared/from_bob.txt
ls -ld /srv/company/shared
ls -l /srv/company/shared
getent group staff
id alice
sudo -u carol ls /srv/company/admin

Beispiel der erwarteten Ausgabe

drwxrws--- 2 root staff 4096 ... /srv/company/shared
-rw-r--r-- 1 bob staff 0 ... from_bob.txt
staff:x:1002:alice,bob,carol
uid=1001(alice) gid=1001(alice) groups=1001(alice),1002(staff),1003(admins)
ls: cannot open directory '/srv/company/admin': Permission denied
Meine Ausgabe sieht anders aus
  • Gruppen-IDs unterscheiden sich zwischen Systemen; nur die Namen müssen stimmen.
  • Hat from_bob.txt die Gruppe bob statt staff, fehlt das setgid-Bit: wiederhole chmod 2770.
  • Optionale Default-ACL (installiere zuerst das Paket acl): sudo setfacl -d -m g:staff:rwx /srv/company/shared.

Webseite mit dem richtigen Label

Installiere nginx, füge Server-Block und Seite hinzu, teste, korrigiere das Label (RHEL) oder prüfe AppArmor (Ubuntu) und füge die letzte curl-Ausgabe ein.

# RHEL / Rocky / Alma:
sudo dnf install -y nginx policycoreutils-python-utils
# Debian / Ubuntu:
sudo apt install -y nginx

echo '<h1>Small Company</h1>' | sudo tee /srv/company/web/index.html
sudo tee /etc/nginx/conf.d/company.conf <<'EOF'
server {
    listen 80;
    server_name company.local;
    root /srv/company/web;
}
EOF
sudo nginx -t
sudo systemctl enable --now nginx
curl -sI -H 'Host: company.local' http://localhost | head -n 1

Beispiel der erwarteten Ausgabe

HTTP/1.1 403 Forbidden   (RHEL before the label fix)
HTTP/1.1 200 OK          (Ubuntu)
# RHEL / Rocky / Alma only:
ls -Zd /srv/company/web
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/company/web(/.*)?"
sudo restorecon -Rv /srv/company/web
ls -Zd /srv/company/web
# Debian / Ubuntu only:
sudo aa-status | grep -i nginx
# both:
curl -sI -H 'Host: company.local' http://localhost | head -n 1
curl -s -H 'Host: company.local' http://localhost

Beispiel der erwarteten Ausgabe

unconfined_u:object_r:default_t:s0 /srv/company/web
... httpd_sys_content_t ...
HTTP/1.1 200 OK
<h1>Small Company</h1>
Meine Ausgabe sieht anders aus
  • 403 nach der Label-Korrektur unter RHEL: prüfe ls -Zd erneut und die Modi von /srv und /srv/company (andere brauchen x).
  • semanage: command not found: installiere policycoreutils-python-utils.
  • Connection refused: sudo systemctl status nginx; Port 80 könnte von einem anderen Dienst belegt sein (ss -tulpn).

Firewall ohne Aussperren

Halte eine zweite SSH-Sitzung oder die Konsole offen. Erlaube die Web-Ports, ohne SSH zu verlieren, und füge dann die Regelliste ein.

# RHEL / Rocky / Alma (firewalld):
sudo firewall-cmd --list-services
sudo firewall-cmd --add-service={http,https} --timeout=300
curl -sI http://localhost | head -n 1
sudo firewall-cmd --permanent --add-service={http,https}
sudo firewall-cmd --reload
sudo firewall-cmd --list-services

Beispiel der erwarteten Ausgabe

cockpit dhcpv6-client http https ssh
# Debian / Ubuntu (ufw): SSH FIRST!
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status

Beispiel der erwarteten Ausgabe

Status: active
OpenSSH                    ALLOW       Anywhere
80/tcp                     ALLOW       Anywhere
443/tcp                    ALLOW       Anywhere
Meine Ausgabe sieht anders aus
  • Kein ssh in der Liste unter RHEL: füge es sofort hinzu mit sudo firewall-cmd --permanent --add-service=ssh und Reload.
  • ufw: command not found unter Rocky ist in Ordnung; dort nutzt du firewalld.
  • Ausgesperrt? Nutze die VM-Konsole oder stelle den Snapshot wieder her.

Backup-Skript und Timer

Erstelle das Backup-Skript und die systemd-Units, aktiviere den Timer, führe ein Backup von Hand aus und füge die Timer-Liste ein.

sudo tee /srv/company/scripts/backup.sh >/dev/null <<'EOF'
#!/bin/bash
set -euo pipefail
DEST=/srv/company/backup
tar -czf "$DEST/company-$(date +%F_%H%M).tar.gz" -C /srv/company shared web admin
find "$DEST" -name 'company-*.tar.gz' -mtime +7 -delete
EOF
sudo chmod 750 /srv/company/scripts/backup.sh

sudo tee /etc/systemd/system/company-backup.service >/dev/null <<'EOF'
[Unit]
Description=Company backup

[Service]
Type=oneshot
ExecStart=/srv/company/scripts/backup.sh
EOF
sudo tee /etc/systemd/system/company-backup.timer >/dev/null <<'EOF'
[Unit]
Description=Daily company backup

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]

Prüf-Checkliste und Abgabebericht

Schreibe das Checklisten-Skript, führe es als root aus und erzeuge den Abgabebericht. Alle Zeilen müssen OK sagen. Füge die verify-Ausgabe ein.

sudo tee /srv/company/scripts/verify.sh >/dev/null <<'EOF'
#!/bin/bash
set -o pipefail
chk() { local label=$1; shift; if "$@" >/dev/null 2>&1; then echo "OK: $label"; else echo "FAIL: $label"; fi; }
staff_ok() { id -nG alice | grep -qw staff && id -nG bob | grep -qw staff && id -nG carol | grep -qw staff; }
site_ok() { curl -fsS -H 'Host: company.local' http://localhost | grep -q Company; }
selinux_ok() { if ! command -v getenforce >/dev/null 2>&1 || [ "$(getenforce)" = Disabled ]; then return 0; fi; ls -Zd /srv/company/web | grep -q httpd_sys_content_t; }
firewall_ok() {
  if command -v firewall-cmd >/dev/null 2>&1 && firewall-cmd --state >/dev/null 2>&1; then
    local services
    services=$(firewall-cmd --list-services) || return 1
    for service in ssh http https; do [[ " $services " == *" $service "* ]] || return 1; done
  elif command -v ufw >/dev/null 2>&1; then
    local status
    status=$(ufw status) || return 1
    grep -q '^Status: active' <<<"$status" && grep -Eq '^OpenSSH[[:space:]]+ALLOW' <<<"$status" && grep -Eq '^80/tcp[[:space:]]+ALLOW' <<<"$status" && grep -Eq '^443/tcp[[:space:]]+ALLOW' <<<"$status"
  else
    return 1
  fi
}
backup_ok() { compgen -G '/srv/company/backup/company-*.tar.gz' >/dev/null; }
backup_mode_ok() { [[ $(stat -c %a /srv/company/backup) == 700 ]]; }
chk "alice bob carol are in staff" staff_ok
chk "shared has setgid" test -g /srv/company/shared
chk "site answers with Small Company" site_ok
chk "nginx enabled" systemctl is-enabled --quiet nginx
chk "web label (SELinux) or no SELinux" selinux_ok
chk "firewall allows SSH, HTTP and HTTPS" firewall_ok
chk "timer enabled" systemctl is-enabled --quiet company-backup.timer
chk "backup archive exists" backup_ok
chk "backup dir is 700" backup_mode_ok
EOF
sudo bash /srv/company/scripts/verify.sh

Selbsttest

Auf Rocky Linux liefert nginx 403 für Dateien in /srv/company/web, obwohl der Modus 755 ist. Was ist die wahrscheinlichste Ursache?

Ein geschlossener Port ergibt einen Timeout, kein 403. Ein allgemeines Label unter /srv blockiert nginx; behebe es mit semanage fcontext und restorecon, nicht mit setenforce 0.

Du bist per SSH mit einem Ubuntu-Server verbunden. Wie schaltest du ufw sicher ein?

ufw-Regeln gelten sofort. Ohne erlaubte SSH-Regel trennt das Einschalten der Firewall deine Sitzung.

Warum bekommt das gemeinsame Verzeichnis den Modus 2770 (setgid)?

Das setgid-Bit an einem Verzeichnis gibt dessen Gruppe an neue Dateien weiter. 770 hält andere draußen.

Du hast company-backup.service und company-backup.timer angelegt. Was musst du tun, damit das nächtliche Backup läuft?

systemd muss die Unit-Dateien neu einlesen (daemon-reload), und die Timer-Unit muss aktiviert und gestartet werden; den Service startet der Timer.

Zusammenfassung

  • Erst planen, VM-Snapshot erstellen, nur in der Test-VM arbeiten.
  • Gemeinsames Verzeichnis: Gruppe staff, Modus 2770 (setgid); sonst minimale Rechte: web 755, scripts 750, backup 700.
  • nginx braucht unter RHEL das Label httpd_sys_content_t (semanage fcontext + restorecon); unter Ubuntu prüfst du AppArmor.
  • Firewall: ssh behalten, mit Runtime-Regeln oder --timeout testen, zweite Sitzung offen halten; bei ufw allow OpenSSH vor enable.
  • Backup: Skript + Service (oneshot) + Timer; daemon-reload, den Timer mit enable --now aktivieren; unter RHEL das Skript mit bin_t labeln.
  • Zum Schluss Checkliste (OK/FAIL) und Abgabebericht als Beleg.

Fachbegriffe

Snapshot
Ein gespeicherter Zustand der VM, zu dem du zurückkehren kannst, wenn ein Schritt schiefgeht.
setgid (am Verzeichnis)
Neue Dateien erben die Gruppe des Verzeichnisses statt der Primärgruppe des Erstellers.
Default-ACL
Eine Zugriffsregel an einem Verzeichnis, die neue Dateien erben.
SELinux-Label
Ein Sicherheitskontext (etwa httpd_sys_content_t) an Dateien; er bestimmt, worauf ein Prozess zugreifen darf.
semanage fcontext
Speichert eine dauerhafte Label-Regel für Dateien; restorecon wendet sie an.
AppArmor
Pfadbasiertes Sicherheitssystem von Debian/Ubuntu; Prüfung mit aa-status.
firewalld / ufw
Firewall-Frontends der RHEL-Familie und von Ubuntu.
Runtime vs. dauerhaft
Runtime-Regeln verschwinden bei Reload oder Neustart; dauerhafte Regeln bleiben gespeichert.
systemd-Timer
Eine Unit, die einen Service nach Zeitplan startet (OnCalendar=).
Abgabebericht
Die Datei, die den fertigen Server und die Prüfergebnisse dokumentiert.
